# 만나(MANNA) 주간 점검 리포트 — 2026-07-27

## 📌 요약 (한 눈에 보기)
전반적으로 코드 품질과 보안 설계는 상당히 높은 수준입니다. 인증(로그인 검증), 접속 제한(과도한 요청 차단), 데이터 접근 통제(각 사용자가 자기 데이터만 봄)가 잘 갖춰져 있습니다. 다만 이번 주 가장 중요한 발견은 **"채팅 메시지가 저장되는 곳(테이블)이 코드마다 서로 다르게 지정되어 있어, 실제로 대화 기록이 저장·조회되지 않을 위험"**입니다. 또한 채팅 기록을 불러올 때 **성경 모드(bibleMode)가 항상 켜져 있도록 고정**되어 있어 사용자가 이 기능을 끌 수 없습니다. 서버에는 사용되지 않는 중복 파일(`selah-memory.ts`)이 남아 있고, 자동 점검 스크립트가 **존재하지 않는 AI 모델 이름**을 사용하고 있어 리포트 생성 자체가 실패할 수 있습니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 메시지 테이블 이름 불일치 — 대화가 저장/조회되지 않을 위험
- **파일 위치**: `src/lib/chat-data.ts` (`listMessages` 46번째 줄 부근, `saveMessage` 60번째 줄 부근) vs `src/app/journey/page.tsx` (`chat_messages` 조회, 105번째 줄 부근)
- **무슨 문제인가**: 데이터베이스에는 대화 내용을 담는 표(테이블)의 이름이 `messages`로 정의되어 있습니다(`supabase/migrations/0001_init.sql`). 그런데 코드 여러 곳에서 이름이 뒤죽박죽입니다.
  - `chat-data.ts`는 `messages` 테이블에 저장/조회합니다. (DB 정의와 일치 ✅)
  - `journey/page.tsx`는 `chat_messages`라는, **DB에 존재하지 않는 이름**으로 조회합니다. (34번째 줄 부근)
  - 또한 `journey/page.tsx`와 `chat-data.ts`는 메시지에 `user_id`(사용자 식별값)나 `created_at`(생성 시각) 같은 칸을 기대하지만, DB의 `messages` 테이블은 `session_id`(대화방 식별값) 기준으로만 소유권을 판별합니다. 즉 `messages`에는 `user_id` 칸 자체가 없습니다.
- **어떤 피해가 생기나**: 
  - "마음의 흐름"(감정 그래프) 페이지가 항상 **텅 빈 화면**으로 보입니다. 존재하지 않는 테이블을 조회하므로 데이터를 하나도 못 가져옵니다.
  - 감정 그래프는 `m.created_at`(생성 시각)에 의존하는데, 저장 시 이 값을 넣지 않으면 그래프가 정상 작동하지 않습니다.
- **권장 조치**: 
  1. 저장·조회에 사용하는 테이블 이름을 하나로 통일하세요. DB 정의(`messages`)를 기준으로 삼는 것이 안전합니다.
  2. `journey/page.tsx`의 `chat_messages`를 `messages`로 바꾸고, `user_id`로 거르는 대신 사용자의 세션 목록을 먼저 가져와 그 `session_id`들로 메시지를 조회하도록 수정하세요.
  3. 감정 그래프에 필요한 `created_at`이 실제로 조회되는지 개발팀과 함께 확인하세요.

### 자동 점검 스크립트가 존재하지 않는 AI 모델을 호출 — 리포트 생성 실패
- **파일 위치**: `scripts/weekly-review.mjs` (114번째 줄, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 주간 리포트를 만드는 스크립트가 `claude-opus-4-8`이라는 모델 이름을 사용합니다. 이는 실제로 존재하지 않는 이름입니다(앱 본체는 `claude-sonnet-4-6`을 사용). 존재하지 않는 모델을 부르면 AI 서버가 오류를 돌려줍니다.
- **어떤 피해가 생기나**: 매주 자동으로 코드를 점검해 리포트를 만드는 기능이 **매번 실패**할 수 있습니다. 운영자가 코드 상태를 정기적으로 파악하지 못하게 됩니다.
- **권장 조치**: 모델 이름을 실제 존재하는 값(예: 앱 본체와 동일한 `claude-sonnet-4-6` 또는 유효한 Opus 모델명)으로 바꾸세요.

### 채팅에서 "깊은 동행(성경 모드)" 끄기가 불가능 — 사용자 설정 무시
- **파일 위치**: `src/components/chat/chat-app.tsx` (`sendMessage` 내부, `bibleMode: true` 하드코딩, 약 218번째 줄)
- **무슨 문제인가**: 서버로 메시지를 보낼 때 `bibleMode: true`(깊은 동행 켬)가 코드에 고정값으로 박혀 있습니다. i18n 사전에는 "깊은 동행 켬/끔"(`bibleOn`/`bibleOff`)이라는 문구가 정의되어 있어 켜고 끌 수 있는 기능처럼 보이지만, 실제로 사용자가 이를 조절할 UI가 없고 항상 켜진 상태로만 동작합니다.
- **어떤 피해가 생기나**: 사용자가 원하지 않아도 항상 특정 방식의 응답이 나오며, 준비했던 켜기/끄기 기능이 사실상 죽어 있습니다. 기획 의도와 실제 동작이 어긋납니다.
- **권장 조치**: 이 기능을 정식으로 살릴지(토글 UI 추가) 아니면 없앨지(관련 문구·설정 제거) 방향을 정하세요. 지금처럼 "있는 척하지만 안 되는" 상태는 정리가 필요합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 사용되지 않는 중복 파일 — 혼란과 유지보수 위험
- **파일 위치**: `src/lib/selah-memory.ts` (파일 전체)
- **무슨 문제인가**: 이 파일은 `src/lib/manna-memory.ts`와 거의 완전히 동일한 복사본입니다. 실제 앱은 `manna-memory.ts`만 사용하며(`chat/route.ts`에서 import), `selah-memory.ts`는 아무 데서도 사용되지 않습니다.
- **어떤 피해가 생기나**: 나중에 개발자가 메모리(장기 기억) 로직을 고칠 때 어느 파일을 고쳐야 하는지 헷갈릴 수 있고, 한쪽만 수정하면 두 파일이 어긋나 버그를 낳습니다.
- **권장 조치**: 사용하지 않는 `selah-memory.ts`를 삭제하세요.

### 리마인더 발송 로직에 사용자별 시간 갱신 오류 가능성
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (약 175번째 줄, `last_sent_at` 갱신 부분)
- **무슨 문제인가**: 알림을 보낸 뒤 "오늘 이미 보냄" 표시(`last_sent_at`)를 갱신하는데, 조건이 `.eq("user_id", r.user_id)`로 사용자 기준입니다. 그런데 하루 중복 발송을 막는 판별(약 108번째 줄)은 사용자의 현지 시간대(timezone) 기준 날짜로 계산합니다. 시간대 계산이 조금이라도 어긋나면 같은 날 두 번 알림이 갈 여지가 있습니다. 또한 여러 사용자를 순차적으로 하나씩 `await`로 처리해 사용자가 많아지면 느려집니다.
- **어떤 피해가 생기나**: 드물게 하루에 알림이 두 번 갈 수 있고, 사용자가 늘면 알림 발송에 시간이 오래 걸립니다(크론 실행 시간 초과 가능).
- **권장 조치**: 하루 중복 방지 로직을 실제로 테스트로 검증하고, 향후 사용자가 많아지면 발송을 병렬 처리(묶음 처리)하도록 개선하세요.

### 이미지가 서버로 전송되나 저장은 되지 않음 — 새로고침 시 사라짐
- **파일 위치**: `src/components/chat/chat-app.tsx` (`sendMessage`, 이미지 저장 관련 주석, 약 200번째 줄)
- **무슨 문제인가**: 사용자가 첨부한 이미지는 AI에게 전달은 되지만 데이터베이스에는 저장되지 않습니다(용량 절약 목적). 화면 새로고침이나 재접속 시 이전에 보낸 사진이 대화 기록에서 사라집니다.
- **어떤 피해가 생기나**: 사용자가 사진을 다시 봤을 때 "내가 보낸 사진이 없어졌다"고 느껴 혼란스러울 수 있습니다. 다만 이는 의도된 설계이므로 치명적이지는 않습니다.
- **권장 조치**: 사용자에게 "사진은 저장되지 않습니다"를 명확히 안내하거나, 필요 시 이미지 저장 기능(스토리지 연동)을 검토하세요.

### 요청 제한이 서버 인스턴스별로만 동작 — 분산 환경에서 헐거움
- **파일 위치**: `src/lib/rate-limit.ts` (파일 전체, 특히 상단 주석)
- **무슨 문제인가**: 과도한 요청을 막는 기능(rate limit)이 서버 메모리에만 저장됩니다. Netlify 같은 서버리스 환경에서는 서버가 여러 개로 나뉘어 실행되므로, 실제 제한이 느슨하게 걸립니다(코드 주석에도 명시됨).
- **어떤 피해가 생기나**: 악의적 사용자가 여러 서버로 요청을 분산하면 AI 사용 비용(후원금으로 운영)이 예상보다 빠르게 소진될 수 있습니다.
- **권장 조치**: 사용량이 늘면 공유 저장소(예: Upstash Redis, DB 카운터)를 이용한 분산 제한으로 강화하세요.

- **권장 조치**: 장기적으로 번역을 별도 파일(JSON)이나 번역 관리 도구로 분리하는 것을 검토하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)**: ✅ 양호 — 채팅 API(`/api/chat`)와 리마인더·푸시 관련 API 모두 로그인 여부를 서버에서 확인하고, 미로그인 시 401(권한 없음)로 차단합니다.
- **API 키 관리**: ✅ 양호 — Anthropic(AI) 키와 Supabase 서비스 키는 서버 환경변수로만 사용되며 클라이언트에 노출되지 않습니다. 클라이언트에는 공개용 anon 키와 VAPID 공개 키만 노출됩니다(정상).
- **크론(예약 작업) 보호**: ✅ 양호 — 리마인더 발송 엔드포인트는 헤더의 비밀키(`x-cron-secret`)로만 접근 가능하며, URL 쿼리 방식을 의도적으로 제거해 로그 유출 위험을 줄였습니다.
- **데이터베이스 접근 제어(RLS)**: ✅ 양호 — 모든 테이블에 Row Level Security(행 수준 보안)가 적용되어, 각 사용자는 자기 데이터만 읽고 쓸 수 있습니다.
- **입력값 검증**: ⚠️ 주의 — 이미지 크기 제한, 시간 형식 검증(`/^\d{2}:\d{2}$/`), 메시지 길이 제한 등은 잘 되어 있으나, `push/subscribe` 등 일부 API는 `body: any`로 받아 최소한만 검증합니다. SQL 인젝션은 Supabase 쿼리 빌더 사용으로 위험이 낮습니다.
- **요청 남용 방지(Rate Limit)**: ⚠️ 주의 — 채팅 API에 사용자별 분당 20회 제한이 있으나, 서버 인스턴스별로만 동작해 분산 환경에서는 헐겁습니다(위 🟡 항목 참조).
- **보안 헤더**: ✅ 양호 — 클릭재킹 방지, MIME 스니핑 방지, HTTPS 강제(HSTS) 등 기본 보안 헤더가 잘 설정되어 있습니다.
