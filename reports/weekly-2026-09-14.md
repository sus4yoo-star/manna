# 만나(MANNA) 주간 점검 리포트 — 2026-09-14

## 📌 요약 (한 눈에 보기)
전반적으로 코드베이스는 완성도가 높고, 인증(로그인 검증)·데이터 접근 제어(RLS)·보안 헤더 등 핵심 방어 장치가 잘 갖춰져 있습니다. 다만 **자동 점검 스크립트(`scripts/weekly-review.mjs`)에 실제로 존재하지 않는 AI 모델명(`claude-opus-4-8`)이 하드코딩**되어 있어, 매주 자동 리포트가 오류로 실패할 가능성이 큽니다. 또한 **채팅 기록 저장·조회 코드가 실제 데이터베이스 테이블 이름과 어긋나 있어**(코드는 `messages`/`chat_messages`를 뒤섞어 사용), 대화 저장·복원 및 "마음의 흐름" 통계가 조용히 작동하지 않을 위험이 있습니다. 이 두 가지가 이번 주 가장 중요한 발견입니다.

## 🔴 즉시 해결이 필요한 문제

### 존재하지 않는 AI 모델명으로 인해 주간 자동 점검이 실패함
- **파일 위치**: `scripts/weekly-review.mjs` (약 115번째 줄, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 리포트를 자동 생성하는 스크립트가 Claude에게 요청할 때 `claude-opus-4-8`이라는 모델명을 사용합니다. 이 이름은 현재 실제로 제공되지 않는(존재하지 않는) 모델일 가능성이 매우 높습니다. 참고로 앱 본체(`src/lib/anthropic.ts`)는 `claude-sonnet-4-6`을 쓰고 있어 서로 다릅니다.
- **어떤 피해가 생기나**: 매주 돌아가는 자동 코드 점검이 "모델을 찾을 수 없음" 오류를 내며 리포트를 만들지 못합니다. 즉, 이 리포트 시스템 자체가 조용히 멈춰버릴 수 있습니다.
- **권장 조치**: `model: 'claude-opus-4-8'`을 실제 사용 가능한 모델명(예: 앱과 동일한 `claude-sonnet-4-6`, 또는 확인된 Opus 모델명)으로 교체하세요. 앱 본체처럼 환경변수(`ANTHROPIC_MODEL`)로 뽑아 쓰도록 하면 앞으로 한 곳만 바꾸면 됩니다.

### 채팅 기록 테이블 이름 불일치 — 대화가 저장/조회되지 않을 위험
- **파일 위치**:
  - `src/lib/chat-data.ts` (44번째 줄 `listMessages` → `.from("messages")`, 57번째 줄 `saveMessage` → `.from("messages")`)
  - `src/app/chat/page.tsx` (약 55번째 줄 → `.from("chat_sessions")`), `src/app/journey/page.tsx` (약 108~111번째 줄 → `.from("chat_messages")`)
  - 실제 DB 스키마: `supabase/migrations/0001_init.sql`는 테이블을 **`messages`**(세션 연결 컬럼은 `session_id`, 사용자 소유 여부는 세션을 통해 판정)로 정의함
- **무슨 문제인가**: 코드 곳곳에서 대화 메시지를 저장·조회할 때 사용하는 테이블 이름이 서로 다릅니다. 저장 코드(`chat-data.ts`)는 `messages` 테이블을 쓰는데, "마음의 흐름" 통계 페이지(`journey/page.tsx`)는 `chat_messages`라는 **다른 이름**의 테이블에서 데이터를 읽고 있고, 심지어 `user_id`로 직접 조회합니다. 그러나 실제로 만들어진 테이블(`messages`)에는 `user_id` 컬럼이 아예 없습니다(사용자 구분은 세션을 통해 간접적으로만 함).
- **어떤 피해가 생기나**: (1) `chat_messages` 테이블이 없다면 "마음의 흐름" 그래프가 항상 비어 있게 됩니다(사용자는 아무 기록도 안 보임). (2) 만약 별도로 `chat_messages` 테이블을 수동으로 만들어 운영 중이라면, `chat-data.ts`가 저장하는 `messages` 테이블과 서로 다른 곳에 데이터가 흩어져 대화 복원과 통계가 어긋납니다. 오류 없이 "조용히" 데이터가 사라지는 것처럼 보이므로 발견이 어렵습니다.
- **권장 조치**: 실제 운영 중인 Supabase에서 어떤 테이블이 존재하는지(`messages` vs `chat_messages`) 먼저 확인하세요. 그런 다음 앱 전체 코드가 **하나의 테이블 이름**과 **하나의 조회 방식**(세션 기준 or 사용자 기준)만 쓰도록 통일해야 합니다. 특히 `journey/page.tsx`의 `chat_messages` + `user_id` 조회는 스키마(`messages` + `session_id`)와 맞지 않으므로 반드시 수정이 필요합니다.

### 중복된 메모리 모듈 파일이 방치되어 혼선을 유발
- **파일 위치**: `src/lib/selah-memory.ts` (전체) — `src/lib/manna-memory.ts`와 거의 동일한 내용의 사본
- **무슨 문제인가**: 장기 기억 기능 코드가 `manna-memory.ts`와 `selah-memory.ts` 두 개로 거의 똑같이 존재합니다. 현재 실제로 쓰이는 것은 `manna-memory.ts`뿐이며(`chat/route.ts`가 이것을 import함), `selah-memory.ts`는 아무도 쓰지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 당장 오류는 없지만, 나중에 개발자가 잘못된 파일을 수정하면 "고쳤는데 반영이 안 된다"는 혼란이 생깁니다. 유지보수 실수의 원천입니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하세요. (즉시 위험은 아니지만 정리가 쉬우므로 이번에 함께 처리 권장)

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 대화 요청마다 추가 AI 호출이 발생해 비용·지연 증가
- **파일 위치**: `src/app/api/chat/route.ts` (스트림 종료 시 `persist()` → `updateUserMemory` 호출), `src/lib/manna-memory.ts` (`updateUserMemory` 내부에서 또 한 번 Anthropic API 호출)
- **무슨 문제인가**: 사용자가 메시지를 보낼 때마다, 답변 생성(1차 AI 호출)에 더해 "장기 기억 업데이트"를 위한 **2차 AI 호출**이 매번 일어납니다. 이는 후원으로 운영되는 무료 서비스에서 API 비용을 사실상 두 배로 만듭니다.
- **어떤 피해가 생기나**: 사용자가 늘수록 API 비용이 빠르게 증가합니다. 또한 기억 업데이트가 끝날 때까지 서버 함수가 살아 있어야 하므로 서버리스 환경에서 실행 시간·비용이 늘어납니다.
- **권장 조치**: 기억 업데이트를 매 턴마다가 아니라 "몇 턴에 한 번" 또는 "일정 글자 수 이상 대화가 쌓였을 때만" 실행하도록 조건을 추가하세요. 급한 문제는 아니지만 사용자 증가 전에 손보는 것이 좋습니다.

### 인메모리 방식 요청 제한은 서버 여러 대에서는 효과가 제한적
- **파일 위치**: `src/lib/rate-limit.ts` (전체), `src/app/api/chat/route.ts` (68번째 줄 부근 `rateLimit` 사용)
- **무슨 문제인가**: 한 사용자가 1분에 20회 이상 요청하지 못하도록 막는 장치가 "현재 실행 중인 서버 인스턴스의 메모리"에만 저장됩니다. Netlify 같은 서버리스 환경에서는 요청마다 다른 인스턴스가 처리할 수 있어, 실제로는 제한이 우회될 수 있습니다(코드 주석도 이를 인정하고 있음).
- **어떤 피해가 생기나**: 악의적 사용자나 오작동 클라이언트가 API를 과도하게 호출해 비용이 폭증할 여지가 남아 있습니다.
- **권장 조치**: 사용자 규모가 커지기 전이라면 현재 상태로 두어도 되지만, 정식 운영·홍보 단계에서는 공용 저장소(예: Upstash Redis) 기반의 제한으로 교체하는 것을 계획에 넣으세요.

### 이메일 회원가입 경로가 코드에 살아 있으나 약관은 "소셜 로그인만" 명시
- **파일 위치**: `src/app/login/page.tsx` (이메일/비밀번호 가입 `handleEmail`), 대비 `src/app/privacy/page.tsx` 제8조("비밀번호 미저장 (소셜 로그인만 사용)"), `src/app/terms/page.tsx` 제5조("Google 또는 Kakao 계정을 통해 회원가입")
- **무슨 문제인가**: 로그인 화면에는 이메일+비밀번호로 가입/로그인하는 기능이 완전히 구현되어 있는데, 개인정보처리방침과 이용약관에는 "소셜 로그인만 사용한다", "비밀번호를 저장하지 않는다"고 적혀 있습니다. 실제 동작과 법적 고지 문서가 서로 모순됩니다.
- **어떤 피해가 생기나**: 이메일 가입 사용자의 비밀번호는 실제로는 저장(관리)되는데 방침에는 "저장 안 함"이라 되어 있어, 개인정보 관련 고지 위반 소지가 있습니다. 감사·민원 시 문제가 될 수 있습니다.
- **권장 조치**: 정책상 소셜 로그인만 허용할 계획이면 이메일 가입 UI를 제거하고, 이메일 가입을 유지할 계획이면 방침·약관 문구를 실제 동작에 맞게 수정하세요. 둘 중 하나로 반드시 일치시켜야 합니다.

### 사용자 프로필 조회가 `.single()`이라 프로필이 없으면 조용히 실패
- **파일 위치**: `src/app/chat/page.tsx` (약 60번째 줄, `supabase.from("profiles").select("*").eq("id", user.id).single()`)
- **무슨 문제인가**: 프로필 행이 반드시 존재한다고 가정하고 `.single()`(정확히 1건)을 사용합니다. 신규 가입 직후 프로필 자동 생성(트리거)이 미처 반영되지 않은 짧은 순간에는 이 조회가 오류를 반환할 수 있습니다. `Promise.all`로 세션 조회와 함께 묶여 있어, 프로필 조회 오류가 세션 목록까지 함께 실패시킬 여지가 있습니다.
- **어떤 피해가 생기나**: 특정 타이밍에 로그인 직후 대화 목록이 안 뜨거나 예외가 발생할 수 있습니다(try/catch로 감싸져 있어 최악의 경우 로그인 화면으로 되돌아감).
- **권장 조치**: `.single()`을 `.maybeSingle()`(0건도 허용)로 바꾸세요. 다른 곳(`reminders/route.ts`)에서는 이미 `.maybeSingle()`을 쓰고 있어 일관성도 맞출 수 있습니다.

## 🟢 장기적으로 개선하면 좋은 점

### 타입 안전성을 낮추는 `any` 다수 사용
- **파일 위치**: `src/app/api/chat/route.ts` (예: `let supabase: any;`, `claudeMessages: any[]`), 여러 API 라우트의 `body: any`
- **무슨 문제인가**: 데이터 형태를 컴퓨터가 검증하지 못하게 하는 `any` 타입이 곳곳에 쓰였습니다. 당장 오류는 없지만, 실수로 잘못된 값을 넣어도 빌드 단계에서 걸러내지 못합니다.
- **어떤 피해가 생기나**: 향후 코드 수정 시 실수가 런타임(사용자가 쓰는 시점)에야 드러나 발견이 늦어질 수 있습니다.
- **권장 조치**: 시간이 날 때 핵심 API의 요청 본문 타입을 명시적으로 정의해 점진적으로 `any`를 줄이세요.

### 오류 로깅/모니터링 도구 부재
- **파일 위치**: 전반 (예: `src/app/error.tsx`는 `console.error`만, 각 API의 `catch {}`는 대부분 조용히 무시)
- **무슨 문제인가**: 사용자에게 오류가 발생해도 개발팀이 알 방법이 없습니다. 대부분의 오류를 조용히 삼키고 있어(`catch {}`), 문제가 쌓여도 감지되지 않습니다.
- **어떤 피해가 생기나**: 실제 사용자가 겪는 장애를 뒤늦게, 또는 민원을 통해서만 알게 됩니다.
- **권장 조치**: Sentry 같은 오류 모니터링 서비스(오류를 자동 수집해 알려주는 도구) 도입을 검토하세요.

### 프로필 언어 자동 업데이트가 반복 쓰기를 유발할 수 있음
- **파일 위치**: `src/components/chat/chat-app.tsx` (약 62번째 줄, 언어가 다를 때마다 `profiles` 업데이트)
- **무슨 문제인가**: UI 언어와 저장된 프로필 언어가 다르면 프로필을 업데이트하는데, `profile` 상태를 갱신하지 않아 같은 세션에서 언어가 바뀔 때마다 반복적으로 쓰기 요청이 나갈 수 있습니다.
- **어떤 피해가 생기나**: 불필요한 데이터베이스 쓰기가 소소하게 늘어납니다(치명적이지 않음).
- **권장 조치**: 업데이트 성공 후 로컬 `profile.language` 값을 함께 갱신하도록 정리하면 됩니다.

## 🔒 보안 점검 결과

- ✅ **인증(로그인 검증) — 양호**: `/api/chat`, 푸시·리마인더 API 모두 서버에서 `supabase.auth.getUser()`로 로그인 여부를 검증한 뒤에만 동작합니다. 미들웨어(`middleware.ts`)도 `/chat` 보호 경로를 막습니다.
- ✅ **데이터베이스 접근 제어(RLS) — 양호**: 모든 주요 테이블에 행 수준 보안(각 사용자가 자기 데이터만 접근)이 적용되어 있고, 리마인더 테이블의 누락된 삭제 정책도 별도 마이그레이션으로 보완했습니다.
- ✅ **비밀 키 관리 — 양호**: Anthropic API 키·서비스 롤 키는 서버에서만 사용되고 클라이언트로 노출되지 않습니다. `NEXT_PUBLIC_*` 접두사가 붙은 값만 클라이언트에 노출되며 이는 공개해도 되는 값들입니다.
- ✅ **보안 헤더 — 양호**: 클릭재킹 방지(X-Frame-Options), HTTPS 강제(HSTS), MIME 스니핑 방지 등 기본 방어 헤더가 잘 설정되어 있습니다.
- ✅ **크론(예약 작업) 보호 — 양호**: 리마인더 발송 크론이 헤더 기반 비밀키(`x-cron-secret`)로 보호되며, 쿼리스트링 노출 위험을 의식적으로 제거한 흔적이 있습니다.
- ⚠️ **입력값 검증 — 주의**: 이미지 크기·타입, 이메일·시간 형식 등 상당 부분 검증되어 있으나, 채팅 메시지 본문 자체에 길이 상한이 없습니다(과도하게 긴 입력 방어는 미흡). 큰 문제는 아니나 보완 여지가 있습니다.
- ⚠️ **요청 제한(남용 방지) — 주의**: 서버리스 환경에서 인메모리 방식이라 실효성이 제한적입니다(위 🟡 항목 참조).
