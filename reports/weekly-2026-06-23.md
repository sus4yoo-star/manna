# 만나(MANNA) 주간 점검 리포트 — 2026-06-23

## 📌 요약 (한 눈에 보기)
전체적으로 코드 품질은 양호하며, 인증(로그인 확인)·데이터 접근 제어(RLS)·보안 헤더 등 기본기가 탄탄하게 잡혀 있습니다. 다만 이번 점검에서 **실제로 동작하지 않을 가능성이 높은 치명적 문제 2건**이 발견되었습니다. 첫째, 채팅 메시지가 저장되는 데이터베이스 테이블 이름이 코드마다 서로 달라(`messages` vs `chat_messages`) **마음의 흐름(여정) 페이지가 항상 비어 보일 위험**이 큽니다. 둘째, **AI 모델 이름과 점검 스크립트 모델 이름이 실제 존재하지 않는 값으로 하드코딩**되어 있어, AI 응답이 통째로 실패할 수 있습니다. 이 두 가지는 출시 전 반드시 확인이 필요합니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 메시지 테이블 이름이 코드마다 달라 여정 페이지가 비어 보임
- **파일 위치**: `src/lib/chat-data.ts` (50번째 줄 부근, `from("messages")`) 와 `src/app/journey/page.tsx` (113번째 줄 부근, `from("chat_messages")`)
- **무슨 문제인가**: 채팅 내용을 저장하고 불러오는 코드(`chat-data.ts`)는 `messages`라는 이름의 표(테이블)를 사용합니다. 데이터베이스 설계 문서(`supabase/migrations/0001_init.sql`)에도 표 이름이 `messages`로 되어 있습니다. 그런데 "마음의 흐름"을 그려주는 여정 페이지(`journey/page.tsx`)는 `chat_messages`라는 **다른 이름의 표**에서 데이터를 읽으려 합니다. 또한 여정 페이지는 `messages` 표에 `user_id`(사용자 구분 칸)가 있다고 가정하지만, 실제 설계 문서의 `messages` 표에는 `session_id`만 있고 `user_id`가 없습니다.
- **어떤 피해가 생기나**: 사용자가 아무리 대화를 많이 나눠도 "마음의 흐름" 페이지가 항상 "아직 기록된 대화가 충분하지 않아요"라는 빈 화면만 보여줄 수 있습니다. 또한 채팅 저장(`saveMessage`) 자체도 실제 데이터베이스 표와 칼럼 구조가 일치하지 않으면 조용히 실패(저장 안 됨)할 수 있어, 로그인 후에도 이전 대화가 사라지는 현상이 생길 수 있습니다.
- **권장 조치**: 실제 Supabase 데이터베이스에 어떤 표(`messages` 또는 `chat_messages`)가 존재하는지, 그 표에 `user_id` 칸이 있는지 먼저 확인하세요. 그 후 모든 코드가 동일한 표 이름과 칼럼을 쓰도록 통일해야 합니다. (여정 페이지는 `chat_sessions`도 `user_id`로 조회하는데, 이 칸은 설계 문서에 존재하므로 일관성 점검이 필요합니다.)

### 존재하지 않는 AI 모델 이름이 하드코딩되어 응답 실패 위험
- **파일 위치**: `src/lib/anthropic.ts` (32번째 줄, `"claude-sonnet-4-6"`) 와 `scripts/weekly-review.mjs` (113번째 줄, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: AI 응답을 만들 때 사용하는 모델(AI 두뇌) 이름이 `claude-sonnet-4-6`으로, 주간 점검 스크립트는 `claude-opus-4-8`로 고정되어 있습니다. 이 이름들은 실제 Anthropic(AI 제공사)이 제공하는 정식 모델명과 다를 가능성이 매우 높습니다(예: 실제로는 `claude-sonnet-4-5` 형태). 모델 이름이 틀리면 AI 서버가 요청을 거부합니다.
- **어떤 피해가 생기나**: 환경 변수(`ANTHROPIC_MODEL`)로 올바른 이름을 따로 지정하지 않으면, 사용자가 메시지를 보내도 AI가 전혀 답하지 못하고 "잠시 문제가 생겼어요" 같은 오류만 반복될 수 있습니다. 앱의 핵심 기능 전체가 멈추는 셈입니다.
- **어떤 피해가 생기나(추가)**: 점검 스크립트도 동일하게 잘못된 모델명이면 매주 자동 리포트 생성이 실패합니다.
- **권장 조치**: Anthropic 공식 문서에서 현재 유효한 모델 이름을 확인하고, 코드의 기본값과 Netlify 환경 변수 `ANTHROPIC_MODEL` 값을 정확한 이름으로 맞춰주세요. 출시 전 실제로 채팅을 한 번 보내 응답이 오는지 테스트가 필수입니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 동일한 메모리 코드가 두 파일로 중복되어 혼란 유발
- **파일 위치**: `src/lib/manna-memory.ts` 전체, `src/lib/selah-memory.ts` 전체
- **무슨 문제인가**: 사용자의 장기 기억(반복되는 고민 등)을 처리하는 코드가 `manna-memory.ts`와 `selah-memory.ts` 두 파일에 거의 똑같이 복사되어 있습니다. 실제 사용되는 것은 `manna-memory.ts`이며, `selah-memory.ts`는 어디에서도 import(불러쓰기)되지 않는 죽은 코드로 보입니다.
- **어떤 피해가 생기나**: 향후 메모리 로직을 수정할 때 한쪽만 고치고 다른 쪽을 놓치면 일관성이 깨질 수 있습니다. 또한 두 파일 모두 점검 스크립트에 포함되면서 다른 분석에 들어갈 토큰(처리 용량)을 낭비합니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하거나, 공통 로직 하나만 남기고 정리하세요.

### 비밀번호 보호(PIN)가 형식적 수준이라 오해 소지 있음
- **파일 위치**: `src/components/chat/pin-gate.tsx` (37번째 줄 부근, `fnv1a` 함수)
- **무슨 문제인가**: 채팅 화면을 4자리 PIN으로 잠그는 기능이 있는데, PIN을 보호하는 방식(FNV-1a)은 암호학적 보안 기술이 아니라 단순 변환 방식입니다. 브라우저 개발자 도구를 아는 사람은 저장값을 우회할 수 있습니다.
- **어떤 피해가 생기나**: 코드 주석에도 "casual onlooker(가벼운 엿보기) 방지용"이라고 솔직하게 적혀 있어 의도된 설계지만, 사용자가 이를 강력한 보안으로 오해할 수 있습니다. 민감한 대화를 다루는 앱 특성상 기대치와 실제 보호 수준의 차이가 문제될 수 있습니다.
- **권장 조치**: 현재 의도(가벼운 가림막)는 유효하므로 코드 변경보다는, PIN 설정 화면에 "이것은 단순 가림 기능이며 완전한 보안은 아닙니다"라는 안내 문구를 추가하는 것을 권장합니다.

### 리마인더 발송 시 last_sent_at 갱신에 사용자별 시간대 미반영 가능성
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (140번째 줄 부근, `last_sent_at` 업데이트 + 중복 방지 로직)
- **무슨 문제인가**: 하루 한 번만 알림을 보내기 위해 "마지막 발송일"을 사용자 시간대 기준으로 비교하는데, 발송 직후 `last_sent_at`을 UTC(세계 표준시) 기준 현재 시각으로 저장합니다. 시간대 경계(자정 부근)에서 드물게 중복 발송 또는 누락이 생길 수 있는 구조입니다.
- **어떤 피해가 생기나**: 일부 사용자가 같은 날 알림을 두 번 받거나, 특정 날짜에 한 번도 못 받는 경우가 가끔 발생할 수 있습니다. 빈번하지는 않습니다.
- **권장 조치**: 현재 ±4분 허용 범위와 날짜 비교 로직은 대체로 잘 작동하므로 긴급하지는 않습니다. 운영 중 중복/누락 신고가 들어오면 이 로직을 정밀 점검하세요.

## 🟢 장기적으로 개선하면 좋은 점

### 속도 제한이 서버 인스턴스별로만 작동
- **파일 위치**: `src/lib/rate-limit.ts` (전체)
- **무슨 문제인가**: 한 사용자가 AI를 1분에 20번 이상 호출하지 못하게 막는 기능이 메모리(서버의 임시 기억)에만 저장됩니다. Netlify 같은 서버리스 환경은 요청마다 다른 서버가 처리할 수 있어, 실제 한도가 정확히 지켜지지 않을 수 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자가 여러 서버에 분산 요청하면 AI 비용(기부로 운영되는 예산)이 예상보다 빨리 소진될 수 있습니다. 코드 주석에도 이 한계가 솔직히 적혀 있습니다.
- **권장 조치**: 사용자가 늘어나면 Upstash Redis 같은 공유 저장소 기반 속도 제한으로 교체를 검토하세요. 현재 규모에서는 긴급하지 않습니다.

### 카카오 로그인 안내가 일부 문서에 누락
- **파일 위치**: `README.md` (Features 섹션)
- **무슨 문제인가**: 실제 코드(`login/page.tsx`)에는 카카오 로그인이 구현되어 있으나, README에는 "Google + email auth"만 언급되어 있습니다.
- **어떤 피해가 생기나**: 개발 문서와 실제 기능이 어긋나 신규 협업자나 운영자가 혼동할 수 있습니다.
- **권장 조치**: 문서를 실제 기능에 맞게 업데이트하세요.

- **API 키 관리**: ✅ 양호 — Anthropic 비밀 키는 서버에서만 사용되며, 클라이언트에 노출되지 않습니다. VAPID 공개 키만 노출되며 이는 정상입니다.
- **보안 헤더**: ✅ 양호 — 클릭재킹 방지, HTTPS 강제, MIME 스니핑 방지 등 기본 헤더가 잘 설정되어 있습니다.
- **크론(예약 작업) 보호**: ✅ 양호 — `x-cron-secret` 헤더로 보호하며, 쿼리스트링 노출을 의도적으로 차단한 점이 좋습니다.
- **입력값 검증**: ⚠️ 주의 — 리마인더의 시간/시간대는 검증하나, 푸시 구독 API 등 일부는 검증이 가벼운 편입니다(RLS로 보완됨). 이미지 크기 상한은 잘 설정되어 있습니다.
- **클라이언트 PIN 잠금**: ⚠️ 주의 — 위에 설명한 대로 암호학적 보안이 아닌 단순 가림 수준입니다.
- **SQL 인젝션**: ✅ 양호 — Supabase 라이브러리를 통해서만 DB에 접근하므로 직접적인 SQL 주입 위험은 없습니다.
