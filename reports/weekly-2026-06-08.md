# 만나(MANNA) 주간 점검 리포트 — 2026-06-08

## 📌 요약 (한 눈에 보기)

만나(MANNA) 앱은 전반적으로 잘 구성된 코드베이스로, 인증·보안·다국어 처리가 견고하게 구현되어 있고 30개 언어를 지원하는 점이 인상적입니다. 다만 이번 점검에서 **실제 동작에 영향을 주는 치명적 버그 2건**을 발견했습니다: ① 채팅 데이터 저장 코드가 데이터베이스 테이블 이름을 잘못 가리키고 있어(`messages` vs `chat_messages`) 화면별로 대화가 보이지 않는 불일치가 있고, ② 점검 자동화 스크립트에 **존재하지 않는 AI 모델 이름**이 하드코딩되어 있어 매주 리포트 생성이 실패할 수 있습니다. 또한 두 개의 거의 동일한 메모리 파일이 중복으로 존재해 유지보수 혼란을 일으킬 위험이 있습니다. 보안 측면은 대체로 양호하나, 채팅 API에 입력값 길이 제한이 없는 점은 비용 관리 차원에서 보완이 필요합니다.

## 🔴 즉시 해결이 필요한 문제

### 데이터베이스 테이블 이름 불일치 — 일부 화면에서 대화가 안 보일 수 있음
- **파일 위치**: `src/lib/chat-data.ts` (49번째 줄 `listMessages`, 64번째 줄 `saveMessage`) vs `src/app/journey/page.tsx` (113번째 줄), `src/app/chat/page.tsx` (62번째 줄)
- **무슨 문제인가**: 대화 메시지를 저장하고 불러오는 코드들이 **서로 다른 데이터베이스 표(테이블)** 이름을 사용하고 있습니다.
  - `chat-data.ts`는 `messages`라는 표를 사용합니다.
  - `journey/page.tsx`는 `chat_messages`라는 표를 사용합니다.
  - 데이터베이스 정의 파일(`supabase/migrations/0001_init.sql`)에는 `messages`만 만들어져 있고 `chat_messages`는 없습니다.
  - 또한 `chat/page.tsx`는 `chat_messages`가 아닌 다른 표를 조회하는 등 일관성이 깨져 있습니다.
- **어떤 피해가 생기나**: "마음의 흐름(journey)" 화면이 항상 비어 있게 됩니다. 실제 데이터베이스에는 `chat_messages`라는 표가 존재하지 않으므로, 사용자가 아무리 대화를 많이 나눠도 감정 그래프에 아무것도 표시되지 않습니다. 즉 핵심 기능 중 하나가 무용지물이 됩니다.
- **권장 조치**: 모든 코드가 **하나의 동일한 표 이름**을 쓰도록 통일해야 합니다. `0001_init.sql`이 `messages`를 만들고 있으므로, `journey/page.tsx`의 `chat_messages`(113번째 줄)와 `chat_messages` 조회 부분을 `messages`로 바꾸거나, 반대로 데이터베이스에 `chat_messages` 표를 추가하고 코드를 그쪽으로 통일하세요. 개발팀이 실제 운영 DB에 어떤 표가 있는지 먼저 확인한 뒤 결정해야 합니다.

### 주간 점검 스크립트에 존재하지 않는 AI 모델 이름이 박혀 있음
- **파일 위치**: `scripts/weekly-review.mjs` (123번째 줄)
- **무슨 문제인가**: 이 리포트를 자동 생성하는 스크립트가 `claude-opus-4-8`이라는 모델(AI 두뇌) 이름을 사용하는데, 이는 실제로 존재하지 않는 이름일 가능성이 매우 높습니다. 같은 코드베이스의 실제 앱(`src/lib/anthropic.ts`)은 `claude-sonnet-4-6`을 사용합니다.
- **어떤 피해가 생기나**: 매주 자동으로 코드 점검 리포트를 만들려고 할 때 API(외부 AI 서비스와 통신하는 통로)가 "그런 모델 없음" 오류를 반환하여 **리포트 생성이 통째로 실패**합니다. 운영 담당자가 정기 점검 결과를 받지 못하게 됩니다.
- **권장 조치**: 123번째 줄의 모델 이름을 실제로 사용 가능한 이름(예: 앱과 동일한 `claude-sonnet-4-6` 또는 검증된 최신 Opus 모델)으로 수정하세요. 한 줄만 고치면 됩니다.

### 중복된 메모리 파일이 두 개 존재 — 한쪽만 고치면 버그 발생
- **파일 위치**: `src/lib/manna-memory.ts`와 `src/lib/selah-memory.ts` (거의 100% 동일한 내용)
- **무슨 문제인가**: 사용자의 장기 기억(반복되는 고민, 최근 감정 등)을 다루는 코드가 두 파일에 거의 똑같이 복사되어 있습니다. 현재 실제로 사용되는 것은 `manna-memory.ts`이며(`chat/route.ts`에서 import), `selah-memory.ts`는 아무도 사용하지 않는 "죽은 파일"입니다.
- **어떤 피해가 생기나**: 당장은 동작에 문제가 없지만, 나중에 개발자가 실수로 `selah-memory.ts`를 수정하거나, 두 파일 중 하나만 고치면 동작이 어긋나게 됩니다. 또한 코드를 읽는 사람이 어느 것이 "진짜"인지 혼란스러워합니다.
- **권장 조치**: 사용되지 않는 `src/lib/selah-memory.ts` 파일을 삭제하세요. 삭제 전 어디서도 import하지 않는지 한 번 더 확인하면 안전합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 채팅 입력 텍스트에 길이 제한이 없음 — 과도한 비용 위험
- **파일 위치**: `src/app/api/chat/route.ts` (88~92번째 줄 본문 파싱 부분)
- **무슨 문제인가**: 사용자가 보내는 텍스트 메시지의 길이를 서버에서 제한하지 않습니다. 이미지는 700만 자로 제한(20번째 줄)하지만, 글자 메시지는 아무리 길어도 그대로 AI에게 전달됩니다.
- **어떤 피해가 생기나**: 악의적인 사용자가 수십만 자의 텍스트를 반복해서 보내면, 후원금으로 운영되는 AI 사용료(API 비용)가 빠르게 소진될 수 있습니다. 분당 20회 제한(rate limit)은 있지만, 한 번에 보내는 양 자체는 막지 못합니다.
- **권장 조치**: 메시지 한 건당 글자 수 상한(예: 8,000자)을 두고, 초과 시 잘라내거나 거부하도록 추가하세요. 간단한 한 줄 검증으로 해결됩니다.

### 채팅 API의 인증 클라이언트가 `any` 타입으로 처리됨
- **파일 위치**: `src/app/api/chat/route.ts` (47번째 줄 `let supabase: any`)
- **무슨 문제인가**: 데이터베이스 연결 객체를 타입스크립트의 "아무 타입이나 허용(any)"으로 선언했습니다. 이는 코드 작성 시 오타나 잘못된 사용을 컴파일러가 잡아주지 못하게 만듭니다.
- **어떤 피해가 생기나**: 당장 오류는 없지만, 향후 이 객체를 잘못 사용했을 때 빌드 단계에서 걸러지지 않고 실제 사용자 화면에서 오류가 터질 수 있습니다.
- **권장 조치**: 프로젝트 전반에 걸쳐 `any` 사용처를 점진적으로 명확한 타입으로 교체하는 것을 권장합니다. 우선순위는 낮지만 안정성에 도움이 됩니다.

### 리마인더 시간 비교에 분 단위 오차 허용 로직의 미세한 사각지대
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (97~104번째 줄)
- **무슨 문제인가**: 알림 발송 시각을 "±4분 오차 허용"으로 비교하는데, 이 비교가 같은 시(hour) 안에서만 단순 계산됩니다. 예를 들어 23:58과 00:02처럼 자정을 넘는 경계에서는 4분 차이임에도 "240분 차이"로 잘못 계산되어 알림이 누락될 수 있습니다.
- **어떤 피해가 생기나**: 자정 직전·직후로 알림 시간을 설정한 일부 사용자가 기도 리마인더를 받지 못할 수 있습니다.
- **권장 조치**: 자정을 넘는 경계 케이스를 처리하도록 시각 비교 로직을 보완하세요(분 차이의 절댓값을 1440에서 빼는 경우도 함께 비교).

## 🟢 장기적으로 개선하면 좋은 점

### 비율 제한(rate limit)이 서버 인스턴스별로만 작동함
- **파일 위치**: `src/lib/rate-limit.ts` (전체)
- **무슨 문제인가**: 분당 요청 횟수를 제한하는 기능이 서버의 메모리(임시 저장 공간)에만 기록됩니다. Netlify처럼 서버가 여러 개로 나뉘어 돌아가는 환경에서는 각 서버가 따로 카운트하므로, 실제로는 제한보다 더 많은 요청이 통과할 수 있습니다. 코드 주석에도 이 한계가 솔직히 적혀 있습니다.
- **어떤 피해가 생기나**: 대규모 악용 시 의도한 만큼 비용을 막지 못할 수 있습니다. 다만 일반 사용 환경에서는 충분합니다.
- **권장 조치**: 사용자가 크게 늘어나는 시점에 Upstash Redis 등 공유 저장소 기반의 제한으로 업그레이드를 검토하세요.

### `chat_messages`에 `user_id` 컬럼을 직접 조회하는 쿼리 존재
- **파일 위치**: `src/app/journey/page.tsx` (113~114번째 줄)
- **무슨 문제인가**: journey 화면은 `chat_messages` 표에서 `user_id`로 직접 필터링하는데, 정의된 `messages` 표에는 `user_id` 컬럼이 없습니다(세션을 통해 소유권을 추적). 위의 테이블 불일치 문제와 맞물려 데이터 모델 설계가 일관되지 않습니다.
- **어떤 피해가 생기나**: 향후 기능 추가 시 혼란과 버그의 원인이 됩니다.
- **권장 조치**: 데이터 모델을 하나로 정리할 때 메시지 소유권 추적 방식(직접 user_id vs 세션 경유)도 함께 통일하세요.
