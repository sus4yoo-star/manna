## 📌 요약 (한 눈에 보기)

전체적으로 코드 품질과 보안 설계 수준이 높은 편입니다. 특히 인증 검사, 사용량 제한(rate limit), 데이터베이스 접근 제어(RLS)가 잘 갖춰져 있습니다. 다만 **이번 주 가장 중요한 발견은 자동 점검 스크립트(`scripts/weekly-review.mjs`)에 실제로 존재하지 않는 AI 모델 이름이 적혀 있어, 매주 자동 리포트가 아예 실패하고 있을 수 있다는 점**입니다. 또한 채팅 화면과 마음 흐름(Journey) 화면이 서로 다른 데이터베이스 테이블 이름을 참조하고 있어 데이터가 아예 안 보이는 심각한 불일치가 있습니다. 그 외에 사용하지 않는 중복 파일(`selah-memory.ts`)이 남아 있어 혼란을 줄 수 있습니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 화면과 마음 흐름 화면이 서로 다른 테이블을 참조함 (데이터 불일치)
- **파일 위치**: `src/app/journey/page.tsx` (약 110~120번째 줄), `src/lib/chat-data.ts` (전체)
- **무슨 문제인가**: 데이터베이스에서 대화 기록을 저장하는 테이블 이름이 코드마다 다릅니다.
  - 실제 DB 정의(`supabase/migrations/0001_init.sql`)와 채팅 저장 코드(`chat-data.ts`)는 **`messages`** 테이블을 사용합니다.
  - 그런데 마음 흐름 화면(`journey/page.tsx`)은 **`chat_messages`** 라는 다른 이름의 테이블을 조회합니다. (`supabase.from("chat_messages")...`)
  - 또한 `messages` 테이블에는 `user_id` 컬럼이 없는데(세션 ID로만 연결됨), journey 화면은 `.eq("user_id", ...)`로 조회합니다.
- **어떤 피해가 생기나**: 마음 흐름(감정 그래프) 화면이 항상 "아직 기록이 충분하지 않아요"라는 빈 화면만 보여주게 됩니다. 사용자가 아무리 대화를 많이 해도 감정 흐름이 절대 나타나지 않습니다. 이 기능은 사실상 작동하지 않는 상태입니다.
- **권장 조치**: `journey/page.tsx`가 실제 테이블 이름(`messages`)과 실제 컬럼 구조에 맞게 조회하도록 수정해야 합니다. 세션을 먼저 불러오고, 그 세션들의 메시지를 세션 ID로 조회하는 방식으로 바꿔야 합니다. 개발팀이 실제 DB에 어떤 테이블이 있는지 먼저 확인한 뒤 코드를 맞춰야 합니다.

### 주간 자동 점검 스크립트에 존재하지 않는 AI 모델 이름 사용
- **파일 위치**: `scripts/weekly-review.mjs` (약 110번째 줄, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 리포트를 자동 생성하는 스크립트가 `claude-opus-4-8`이라는 모델 이름을 호출합니다. 그러나 이 이름은 실제로 존재하지 않는 것으로 보입니다(앱 본체는 `claude-sonnet-4-6`을 사용). AI 회사가 인식하지 못하는 이름이면 요청이 오류로 거부됩니다.
- **어떤 피해가 생기나**: 매주 실행되는 자동 코드 점검이 조용히 실패하여, 운영자가 문제를 발견하지 못한 채 넘어갈 수 있습니다. (리포트가 아예 생성되지 않음)
- **권장 조치**: 실제로 사용 가능한 모델 이름(예: 앱 본체와 동일한 `claude-sonnet-4-6` 또는 검증된 최신 모델명)으로 수정하세요. 간단한 수정입니다.

### 사용하지 않는 중복 메모리 파일 방치 (`selah-memory.ts`)
- **파일 위치**: `src/lib/selah-memory.ts` (파일 전체)
- **무슨 문제인가**: `src/lib/manna-memory.ts`와 거의 완전히 동일한 내용의 파일이 `selah-memory.ts`로 하나 더 존재합니다. 현재 앱은 `manna-memory.ts`만 사용하며, `selah-memory.ts`는 어디서도 import되지 않는 "죽은 코드"입니다.
- **어떤 피해가 생기나**: 당장 오류를 일으키지는 않지만, 개발자가 실수로 잘못된 파일을 수정하면 반영이 안 되어 시간을 낭비하게 됩니다. 두 파일이 서로 다르게 관리되면 나중에 혼란이 커집니다.
- **권장 조치**: `selah-memory.ts` 파일을 삭제하세요. (사용처가 없는지 최종 확인 후 제거)

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 사용량 제한(rate limit)이 서버 인스턴스별로만 작동
- **파일 위치**: `src/lib/rate-limit.ts` (전체), `src/app/api/chat/route.ts` (약 66번째 줄)
- **무슨 문제인가**: 한 사용자가 1분에 20번 이상 요청하는 것을 막는 기능이 있지만, 이 카운터가 서버 메모리(한 대의 서버 인스턴스)에만 저장됩니다. Netlify 같은 환경에서는 요청마다 다른 서버가 처리할 수 있어, 실제로는 제한이 느슨하게 적용됩니다. (파일 내 주석에도 이 한계가 명시되어 있습니다.)
- **어떤 피해가 생기나**: 악의적 사용자가 여러 요청을 분산시키면 제한을 우회하여, 기부금으로 운영되는 AI 사용료(비용)를 과도하게 소진시킬 수 있습니다.
- **권장 조치**: 이용자가 늘어나면 Upstash Redis나 Postgres 카운터 같은 공유 저장소로 제한을 옮기는 것을 검토하세요. 당장은 급하지 않지만 사용자 증가 시 필요합니다.

### 리마인더 발송 시 사용자별 순차 처리로 느려질 수 있음
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (약 150~175번째 줄)
- **무슨 문제인가**: 예약된 리마인더를 보낼 때, 사용자와 기기를 하나씩 순서대로(`for` 반복문 안에서 `await`) 처리합니다. 사용자가 많아지면 발송 시간이 길어집니다.
- **어떤 피해가 생기나**: 알림 대상자가 수백 명 이상으로 늘어나면 cron(정해진 시간에 자동 실행되는 작업) 하나가 시간 제한을 넘겨 일부 사용자는 알림을 못 받을 수 있습니다.
- **권장 조치**: 지금은 문제없지만, 사용자가 늘면 발송을 병렬 처리(여러 건 동시 발송)하거나 배치(묶음) 처리로 개선하세요.

### 마음 흐름 화면의 감정 그래프가 대량 메시지에서 느려질 수 있음
- **파일 위치**: `src/app/journey/page.tsx` (약 100~140번째 줄, `buildSeries`, `topFeelings`)
- **무슨 문제인가**: 사용자의 모든 메시지를 화면에서 직접 감정 분석합니다. 메시지가 수천 개가 되면 브라우저에서 계산량이 많아집니다. (다만 `useMemo`로 어느 정도 최적화는 되어 있습니다.)
- **어떤 피해가 생기나**: 오래 사용한 사용자의 마음 흐름 화면이 잠시 멈추거나 느리게 열릴 수 있습니다.
- **권장 조치**: 위의 테이블 불일치 문제를 먼저 고친 뒤, 조회 범위에 맞는 메시지만 DB에서 가져오도록(기간 필터링) 개선하세요.

### 채팅 저장 실패 시 사용자가 알 수 없음
- **파일 위치**: `src/components/chat/chat-app.tsx` (약 200번째, 240번째 줄 `saveMessage(...).catch(() => {})`)
- **무슨 문제인가**: 대화 내용을 DB에 저장하는 작업이 실패해도 조용히 무시됩니다(`.catch(() => {})`). 화면에는 대화가 보이지만 실제로는 저장 안 될 수 있습니다.
- **어떤 피해가 생기나**: 네트워크 문제 등으로 저장이 실패하면, 사용자가 나중에 다시 들어왔을 때 소중한 대화가 사라져 있을 수 있습니다. 사용자는 이를 알 방법이 없습니다.
- **권장 조치**: 저장 실패 시 조용한 재시도를 넣거나, 최소한 개발팀이 확인할 수 있도록 오류를 기록(로그)하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)** — ✅ 양호: 채팅 API(`chat/route.ts`)와 모든 push/reminder API가 요청 처리 전에 `getUser()`로 로그인을 검증합니다. 미들웨어(`middleware.ts`)도 `/chat` 경로를 보호합니다.
- **API 키 관리** — ✅ 양호: Anthropic API 키(`ANTHROPIC_API_KEY`)는 서버에서만 사용되며 브라우저로 노출되지 않습니다. Supabase 공개 키(anon key)만 클라이언트에 노출되는데 이는 정상 설계입니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: 모든 주요 테이블(profiles, chat_sessions, messages, push_subscriptions, prayer_reminders, user_memories)에 행 수준 보안(각 사용자가 자기 데이터만 접근)이 적용되어 있습니다.
- **cron(자동 작업) 엔드포인트 보호** — ✅ 양호: 리마인더 발송 엔드포인트가 비밀 키(`CRON_SECRET`)를 헤더로만 받도록 되어 있고, URL 쿼리로는 받지 않습니다(로그 유출 방지). 좋은 설계입니다.
- **입력값 검증** — ⚠️ 주의: 이미지 크기 제한(7MB), 리마인더 시간 형식 검증 등은 잘 되어 있으나, 채팅 텍스트 자체의 길이 제한이 명시적으로 보이지 않습니다. 매우 긴 입력에 대한 상한선 추가를 권장합니다.
- **SQL 인젝션** — ✅ 양호: Supabase 클라이언트 라이브러리를 통한 파라미터화된 쿼리만 사용하여 SQL 인젝션 위험이 없습니다.
- **보안 헤더** — ✅ 양호: 클릭재킹 방지, HTTPS 강제(HSTS), MIME 스니핑 방지 등 기본 보안 헤더가 `next.config.mjs`에 잘 설정되어 있습니다.
- **PIN 잠금** — ⚠️ 주의: 클라이언트 PIN 잠금은 FNV-1a라는 가벼운 해시를 사용합니다. 주석에 명시된 대로 "인증 대체가 아닌 엿보기 방지용"이므로 용도상 문제는 없으나, 보안 기능으로 오해되지 않도록 주의가 필요합니다.
