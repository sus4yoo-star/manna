# 만나(MANNA) 주간 점검 리포트 — 2026-09-28

## 📌 요약 (한 눈에 보기)
전체적으로 코드 품질과 보안 구조가 견고한 편입니다. 인증(로그인 확인), 요청 폭주 방지, 위기 상황 감지 같은 핵심 안전장치가 잘 갖춰져 있고, 개인정보처리방침·이용약관도 실제 서비스와 잘 맞습니다. 다만 **이번 주 가장 중요한 발견은 두 가지**입니다. 첫째, 채팅 기록을 저장하는 코드가 실제 데이터베이스 테이블 이름과 어긋나 있어(코드는 `chat_messages`/`messages`를 섞어 씀), 특정 화면에서 대화 기록이 비어 보일 위험이 있습니다. 둘째, 주간 점검 스크립트와 AI 모델 이름에 실제로 존재하지 않는 값(`claude-opus-4-8`, `claude-sonnet-4-6`)이 하드코딩되어 있어, 그대로라면 자동 점검이나 채팅 응답이 실패할 수 있습니다. 그 외에는 중복 파일 정리, 다국어 폴백 개선 등 장기적 정돈 사항이 남아 있습니다.

## 🔴 즉시 해결이 필요한 문제

### 데이터베이스 테이블 이름 불일치로 대화 기록이 안 보일 수 있음
- **파일 위치**: `src/lib/chat-data.ts` (46번째 줄 `from("messages")`, 66번째 줄 `from("messages")`) vs `src/app/journey/page.tsx` (약 122번째 줄 `from("chat_messages")`)
- **무슨 문제인가**: 대화 메시지를 읽고 저장하는 코드는 데이터베이스의 `messages`라는 테이블을 사용합니다. 그런데 "마음의 흐름"(journey) 화면을 그리는 코드는 `chat_messages`라는, 데이터베이스 설계 파일 어디에도 정의되지 않은 다른 이름의 테이블을 조회합니다. 즉 한쪽은 실제 존재하는 창고에서 물건을 꺼내는데, 다른 쪽은 존재하지 않는 창고를 열려고 시도합니다.
- **어떤 피해가 생기나**: 사용자가 "마음의 흐름" 화면에 들어가면 감정 그래프가 항상 비어 있게 됩니다(데이터가 없다고 표시됨). 사용자는 "며칠 동안 기록을 쌓았는데도 아무것도 안 나온다"고 느끼고, 기능이 고장 났다고 오해할 수 있습니다.
- **권장 조치**: `src/app/journey/page.tsx`의 `chat_messages`를 실제 테이블명인 `messages`로 통일하고, 조회 조건(`user_id` 필터 등)이 `messages` 테이블 구조(세션을 통해 소유권을 확인함)와 맞는지 확인해야 합니다. `messages` 테이블에는 `user_id` 컬럼이 없고 `session_id`만 있으므로, 조회 방식 자체도 재검토가 필요합니다.

### AI 모델 이름이 실제 존재하지 않는 값으로 하드코딩됨
- **파일 위치**: `src/lib/anthropic.ts` (약 33번째 줄 `"claude-sonnet-4-6"`), `scripts/weekly-review.mjs` (약 105번째 줄 `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: AI(챗봇 두뇌)를 부를 때 어떤 모델을 쓸지 이름으로 지정하는데, 코드에 적힌 `claude-sonnet-4-6`, `claude-opus-4-8`은 실제로 제공되지 않는(존재 여부가 불확실한) 이름입니다. 존재하지 않는 모델 이름으로 요청하면 서버가 "그런 모델 없음" 오류를 돌려줍니다.
- **어떤 피해가 생기나**: 만약 이 이름이 실제로 유효하지 않다면, 채팅 응답이 전혀 생성되지 않고 사용자에게 오류 메시지만 보이거나, 주간 점검 스크립트가 매번 실패합니다. 서비스의 핵심 기능이 마비될 수 있는 위험입니다.
- **권장 조치**: Anthropic이 실제 제공하는 모델 이름(예: 현재 유효한 Claude 모델명)으로 교체하거나, 최소한 환경변수(`ANTHROPIC_MODEL`)로 유효한 값이 반드시 설정되도록 배포 문서에 명시해야 합니다. 현재 운영 중이라면 실제로는 환경변수로 덮어써서 동작하고 있을 가능성이 높으니, 배포 환경 변수를 즉시 확인하시기 바랍니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 중복된 메모리 파일(selah-memory / manna-memory)이 혼란을 유발
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts` (내용이 거의 동일)
- **무슨 문제인가**: 사용자의 장기 대화 기억을 다루는 코드가 두 파일에 거의 똑같이 복사되어 있습니다. 실제로는 `manna-memory.ts`만 사용되고 `selah-memory.ts`는 아무 데서도 불러오지 않는 것으로 보입니다.
- **어떤 피해가 생기나**: 나중에 기억 로직을 고칠 때 한쪽만 수정하고 다른 쪽을 놓치면, 어느 파일이 진짜인지 헷갈려 버그를 만들 수 있습니다. 또한 프롬프트 안에 "MANNA's long-term ... memory"라고 적혀 있어 브랜드 문구도 정리가 필요합니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하거나, 두 앱을 공유한다면 하나의 공용 파일로 합치는 것이 좋습니다.

### 위기 상황(자살·자해) 감지 시 서버가 신호만 보내고 실제 활용은 클라이언트에 의존
- **파일 위치**: `src/app/api/chat/route.ts` (응답 헤더 `X-Manna-Crisis` 설정 부분) 및 `src/components/chat/chat-app.tsx` (`detectCrisis`로 카드 표시)
- **무슨 문제인가**: 사용자가 위기 신호가 담긴 문장을 보내면, 서버는 위기 여부를 계산해 응답에 표시(`X-Manna-Crisis` 헤더)만 하고, 실제 위기 도움 카드는 클라이언트(브라우저)가 별도로 다시 판단해 띄웁니다. 서버가 계산한 위기 신호 헤더를 클라이언트가 실제로 읽어 쓰지는 않습니다.
- **어떤 피해가 생기나**: 감지 로직이 두 곳(서버·클라이언트)에 나뉘어 있어, 나중에 한쪽 규칙만 바뀌면 실제 위험한 순간에 도움 카드가 안 뜨는 경우가 생길 수 있습니다. 생명과 직결될 수 있는 기능이라 일관성이 특히 중요합니다.
- **권장 조치**: 서버가 이미 계산한 위기 신호를 클라이언트가 응답 헤더에서 읽어 카드 표시에 함께 활용하도록 통합하거나, 감지 규칙을 한 곳에서만 관리하도록 정리하는 것이 안전합니다.

### 다국어 기능 문구(feature strings)가 한국어·영어만 있어 나머지 언어는 영어로 표시
- **파일 위치**: `src/lib/feature-strings.ts` (맨 아래 `TABLE: Partial<Record<...>> = { ko, en }`)
- **무슨 문제인가**: 앱은 30개 언어를 지원한다고 표시하지만, "마음의 흐름", "리마인더", 위기 안내 카드 등 비교적 새로 추가된 기능의 문구는 한국어와 영어만 번역되어 있습니다. 태국어·스페인어 등으로 앱을 쓰는 사용자는 이 부분만 갑자기 영어로 보이게 됩니다.
- **어떤 피해가 생기나**: 해외 사용자가 특정 화면에서만 영어를 만나면 완성도가 떨어져 보이고, 특히 위기 안내(hotlines)는 한국어/영어 외에는 미국 번호로 폴백되어 실제 도움을 받기 어려울 수 있습니다.
- **권장 조치**: 주요 사용 국가 언어부터 순차적으로 기능 문구와 위기 상담 전화번호를 현지화하는 것을 권장합니다.

### 크론(자동 알림) 작업의 순차 처리로 사용자 증가 시 느려질 수 있음
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (`for (const r of due)` 반복 안에서 `await sendPush` 순차 호출)
- **무슨 문제인가**: 예약된 알림을 보낼 때, 사용자와 기기를 하나씩 차례로 처리하며 매번 응답을 기다립니다. 사용자가 많아지면 한 번의 크론 실행에서 처리해야 할 건수가 많아져 시간이 오래 걸립니다.
- **어떤 피해가 생기나**: 알림 대상이 수백 명 이상으로 늘면, 크론 실행 시간이 길어져 일부 사용자는 예약 시간보다 늦게 알림을 받거나, 실행 제한 시간을 초과해 누락될 수 있습니다.
- **권장 조치**: 지금 규모에서는 문제없지만, 사용자가 늘기 전에 여러 알림을 병렬(동시)로 보내도록 개선하거나 배치 처리를 도입하는 것을 계획해두면 좋습니다.

## 🟢 장기적으로 개선하면 좋은 점

### 요청 폭주 방지가 서버 인스턴스별로만 동작
- **파일 위치**: `src/lib/rate-limit.ts` (전체)
- **무슨 문제인가**: 한 사용자가 짧은 시간에 너무 많이 요청하는 것을 막는 장치가 있으나, 이는 서버 한 대의 메모리 안에서만 세어집니다. 서버가 여러 대로 나뉘어 돌아가는 환경(서버리스)에서는 사용자가 여러 서버에 나눠 요청하면 제한이 느슨해질 수 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자가 이를 악용하면 AI 사용 비용(후원금으로 운영)이 예상보다 많이 나갈 수 있습니다. 현재는 기본 방어로 충분하지만 규모가 커지면 구멍이 될 수 있습니다.
- **권장 조치**: 코드 주석에도 언급된 대로, 향후 Redis 같은 공유 저장소 기반의 전역 제한으로 업그레이드를 검토하십시오.

### 이미지가 데이터베이스에 저장되지 않아 대화 재방문 시 사진이 사라짐
- **파일 위치**: `src/components/chat/chat-app.tsx` (`sendMessage` 내 "The image itself is not persisted" 주석 부분)
- **무슨 문제인가**: 사용자가 보낸 사진은 저장 용량 절약을 위해 저장하지 않고, 텍스트 표시(예: "사진을 보냈어요")만 기록합니다. 의도된 설계이지만, 나중에 그 대화를 다시 열면 사진은 보이지 않습니다.
- **어떤 피해가 생기나**: 사용자가 "내가 올렸던 사진이 사라졌다"고 느낄 수 있습니다. 기능 결함은 아니나 사용자 기대와 어긋날 수 있습니다.
- **권장 조치**: 현재 정책을 유지하되, UI에 "사진은 저장되지 않습니다" 같은 안내를 보태면 오해를 줄일 수 있습니다.

### 백워드 호환용 shim 파일들이 다수 존재
- **파일 위치**: `src/components/chat/font-size-control.tsx`, `src/components/font-size-provider.tsx`
- **무슨 문제인가**: 예전 이름으로 코드를 부르던 부분을 위해 새 파일을 가리키는 얇은 연결 파일이 남아 있습니다. 동작에는 문제가 없습니다.
- **어떤 피해가 생기나**: 코드베이스가 조금 복잡해 보이고, 신규 개발자가 어떤 파일이 진짜인지 파악하는 데 시간이 더 걸립니다.
- **권장 조치**: 여유가 있을 때 옛 이름 사용처를 새 이름으로 바꾸고 shim 파일을 제거하면 깔끔해집니다.

## 🔒 보안 점검 결과

- **인증(로그인 검증)** — ✅ 양호: 채팅 API(`/api/chat`)와 알림 관련 API 모두 로그인 여부를 서버에서 확인하고, 비로그인 시 401(권한 없음)로 차단합니다. 미들웨어에서 `/chat` 경로를 보호합니다.
- **API 키 관리** — ✅ 양호: Anthropic API 키(`ANTHROPIC_API_KEY`)와 VAPID 개인키는 서버에서만 사용하고 클라이언트로 노출되지 않습니다. 공개해도 되는 키(anon, VAPID 공개키)만 브라우저에 전달됩니다.
- **입력값 검증** — ⚠️ 주의: 이미지 크기 제한, 리마인더 시간 형식 검증 등은 잘 되어 있으나, 채팅 메시지 본문·피드백 텍스트는 길이 제한 정도만 있고 내용 검증은 AI에 의존합니다. 현재 구조상 큰 위험은 아니나 인지해둘 필요가 있습니다.
- **SQL 인젝션(악의적 DB 조작)** — ✅ 양호: 모든 데이터베이스 접근이 Supabase 라이브러리를 통해 이루어져 직접 SQL 문자열을 조립하지 않으므로 인젝션 위험이 낮습니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: 모든 테이블에 Row Level Security가 켜져 있고, 사용자는 자신의 데이터만 읽고 쓸 수 있도록 정책이 세밀하게 설정되어 있습니다.
- **크론 엔드포인트 보호** — ✅ 양호: 자동 알림 엔드포인트는 비밀키(`CRON_SECRET`)를 헤더로만 받도록 하여 로그 유출 위험을 줄였습니다.
- **보안 헤더** — ✅ 양호: 클릭재킹 방지, HTTPS 강제(HSTS), MIME 스니핑 방지 등 기본 보안 헤더가 모든 경로에 적용됩니다.
- **PIN 잠금** — ⚠️ 주의: 채팅 화면의 4자리 PIN은 가벼운 해시(FNV-1a)로 저장되어 있어, 가족 등 우연한 접근을 막는 용도로는 충분하나 강력한 보안은 아닙니다. 코드 주석에도 "인증을 대체하지 않는다"고 명시되어 있어 의도된 설계입니다.
