# 만나(MANNA) 주간 점검 리포트 — 2026-09-21

## 📌 요약 (한 눈에 보기)
전체적으로 코드 품질과 보안 설계가 매우 견고한 프로젝트입니다. 인증(로그인 검증), 요청 제한, 개인정보 보호(RLS)가 잘 갖춰져 있고, 다국어·접근성·설치 가이드까지 세심하게 준비되어 있습니다. 다만 **채팅 기능이 실제로는 저장·불러오기가 안 되는 심각한 버그**가 발견되었습니다. 코드가 데이터베이스의 존재하지 않는 테이블/컬럼을 참조하고 있어, 사용자가 대화를 저장하거나 나중에 다시 볼 수 없는 상태입니다. 또한 자동 리포트 생성 스크립트에 실제로 존재하지 않는 AI 모델 이름이 하드코딩되어 있어 리포트 생성이 실패합니다. 이 두 가지가 이번 주 최우선 해결 과제입니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 저장·불러오기가 사용하는 테이블/컬럼 이름이 실제 DB와 어긋남
- **파일 위치**: `src/lib/chat-data.ts` (전체), `src/app/chat/page.tsx` (약 55번째 줄), `src/app/journey/page.tsx` (약 115번째 줄)
- **무슨 문제인가**: 코드가 대화 내용을 저장·조회할 때 사용하는 데이터베이스 테이블 이름이 서로 다릅니다.
  - 실제로 만들어진 테이블(‘설계도’)은 `messages`(`supabase/migrations/0001_init.sql`)이고, 이 테이블에는 `session_id`(대화방 식별자)만 있고 `user_id`(사용자 식별자)는 없습니다.
  - 그런데 `chat-data.ts`의 `saveMessage`/`listMessages`는 `messages` 테이블을 쓰지만, `chat/page.tsx`는 `chat_messages`라는 **다른 이름의 테이블**을, `journey/page.tsx`도 `chat_messages` 테이블에서 `user_id`로 조회하려 합니다.
  - 즉, 저장은 `messages`에 하고, 마음의 흐름(journey) 화면은 `chat_messages`에서 읽으려 하니 항상 비어 있게 됩니다.
- **어떤 피해가 생기나**: 사용자가 대화를 나눠도 "마음의 흐름" 그래프가 항상 텅 비어 보이고, 상황에 따라 대화 자체가 저장되지 않거나 조회 시 오류가 날 수 있습니다. 이 앱의 핵심 가치인 "대화를 기억하고 이어가기"가 작동하지 않습니다.
- **권장 조치**: 세 파일의 테이블 이름을 하나로 통일해야 합니다. `messages` 테이블에는 `user_id` 컬럼이 없으므로, (1) journey 화면을 `messages` 테이블 + `session_id` 기준으로 다시 조회하거나, (2) 데이터베이스에 `user_id` 컬럼을 추가하는 방식 중 하나로 개발팀이 결정해 통일해야 합니다. 배포 전 반드시 실제로 대화 저장→로그아웃→재로그인→기록 확인 테스트를 거쳐야 합니다.

### 자동 점검 스크립트에 존재하지 않는 AI 모델명이 하드코딩됨
- **파일 위치**: `scripts/weekly-review.mjs` (약 110번째 줄, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 주간 리포트를 자동으로 만드는 스크립트가 `claude-opus-4-8`이라는 모델(AI 두뇌 버전)을 호출하도록 되어 있는데, 이는 실제로 존재하지 않는 이름입니다. (앱 본체인 `src/lib/anthropic.ts`는 `claude-sonnet-4-6`을 씁니다.)
- **어떤 피해가 생기나**: 주간 자동 점검 리포트 생성이 API 오류로 실패합니다. 운영진이 정기 점검 결과를 받지 못하게 됩니다.
- **권장 조치**: `scripts/weekly-review.mjs`의 모델명을 실제 사용 가능한 모델(예: 앱과 동일한 `claude-sonnet-4-6`)로 수정하세요. 간단한 한 줄 수정입니다.

### 코드에 서로 다른 두 개의 "기억 모듈"이 중복 존재
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts` (두 파일이 거의 동일)
- **무슨 문제인가**: 대화 기억을 다루는 코드가 `manna-memory.ts`(실제 사용됨)와 `selah-memory.ts`(사용 안 됨) 두 벌로 존재합니다. `selah-memory.ts`는 아무데서도 불러쓰지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 당장 오류를 내진 않지만, 나중에 한쪽만 고치고 다른 쪽을 잊어버리면 혼란과 버그의 원인이 됩니다. 유지보수 시 어느 파일이 진짜인지 헷갈립니다.
- **권장 조치**: 사용하지 않는 `src/lib/selah-memory.ts`를 삭제하세요. (즉시 위험은 아니나, 위 두 항목과 함께 정리하는 것이 안전합니다.)

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 요청 제한(rate limit)이 여러 서버에 걸쳐 정확하지 않음
- **파일 위치**: `src/lib/rate-limit.ts` (전체), `src/app/api/chat/route.ts` (약 68번째 줄)
- **무슨 문제인가**: 한 사용자가 1분에 20번까지만 AI를 호출하도록 제한하는 장치가 있으나, 이 카운트가 서버 메모리(‘그 순간 돌아가는 컴퓨터의 임시 기억’)에만 저장됩니다. Netlify 같은 환경은 요청마다 다른 서버 인스턴스가 처리할 수 있어, 실제로는 20번보다 훨씬 많이 호출될 수 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자나 오작동 클라이언트가 AI를 대량 호출하면, 후원금으로 운영되는 API 비용이 예상보다 크게 늘 수 있습니다.
- **권장 조치**: 코드 주석에도 이미 언급되어 있듯, 사용량이 늘어나면 공유 저장소(예: Upstash Redis)를 이용한 분산 제한으로 교체하는 것을 권장합니다. 초기 소규모 운영 단계에서는 급하지 않습니다.

### 대화 기억(memory) 업데이트가 매 응답마다 추가 AI 호출을 발생시킴
- **파일 위치**: `src/app/api/chat/route.ts` (약 250번째 줄 `persist` 함수), `src/lib/manna-memory.ts` (`updateUserMemory`)
- **무슨 문제인가**: 사용자가 메시지를 주고받을 때마다, 답변 생성과는 별개로 "기억 정리"를 위해 AI를 한 번 더 호출합니다. 즉 대화 1회당 API 호출이 사실상 2회입니다.
- **어떤 피해가 생기나**: API 비용이 약 2배로 늘어납니다. 후원 기반 무료 서비스에서 비용 부담이 커질 수 있습니다.
- **권장 조치**: 매번이 아니라 일정 대화 수마다(예: 5턴에 한 번) 또는 감정적으로 의미 있는 대화일 때만 기억을 갱신하도록 조정하면 비용을 크게 줄일 수 있습니다.

### 크론(자동 실행) 작업의 데이터 처리가 사용자 수 증가 시 느려질 수 있음
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (약 95번째 줄부터)
- **무슨 문제인가**: 알림 발송 작업이 "알림을 켠 모든 사용자"를 한꺼번에 불러온 뒤, 각 사용자마다 순서대로(하나씩 기다리며) 푸시를 보냅니다. 사용자가 많아지면 이 순차 처리가 오래 걸립니다.
- **어떤 피해가 생기나**: 사용자가 수천 명 규모로 늘면 알림이 제 시간에 도착하지 못하거나, 크론 실행이 시간 초과될 수 있습니다.
- **권장 조치**: 현재 규모에서는 문제없으나, 성장 시 여러 알림을 병렬로 보내거나 배치(묶음) 처리로 개선하세요.

### 이미지가 서버 메모리에 통째로 담겨 처리됨
- **파일 위치**: `src/app/api/chat/route.ts` (약 15번째 줄 `MAX_IMAGE_CHARS = 7_000_000`)
- **무슨 문제인가**: 사용자가 첨부한 이미지를 최대 약 7MB 텍스트 크기까지 허용하며, 이를 서버 메모리에 담아 AI로 전달합니다. 클라이언트에서 압축(약 3.6MB 제한)을 하고 있어 실제로는 더 작지만, 상한이 넉넉합니다.
- **어떤 피해가 생기나**: 동시에 큰 이미지 요청이 몰리면 서버 메모리 사용량이 높아질 수 있습니다.
- **권장 조치**: 현재 클라이언트 압축이 있어 위험도는 낮습니다. 서버 상한을 클라이언트 상한(약 3.6MB)에 맞춰 낮추는 것을 검토하세요.

## 🟢 장기적으로 개선하면 좋은 점

### 코드 곳곳에서 타입을 `any`(아무 형식이나 허용)로 처리
- **파일 위치**: `src/app/api/chat/route.ts` (약 46번째 줄 `let supabase: any;`), 여러 API 라우트의 `body: any` 등
- **무슨 문제인가**: 데이터의 형태를 엄격하게 검사하지 않는 `any` 타입이 여러 곳에 있습니다. TypeScript의 오류 사전 감지 이점을 일부 포기하는 방식입니다.
- **어떤 피해가 생기나**: 당장 문제는 없으나, 예상치 못한 데이터 형태가 들어올 때 오류를 미리 잡지 못해 런타임 버그로 이어질 수 있습니다.
- **권장 조치**: 여유가 있을 때 주요 API의 입력값에 구체적인 타입을 정의하면 안정성이 높아집니다.

### 오래된(구버전) 데이터 형식 호환 코드가 계속 누적됨
- **파일 위치**: `src/lib/format.ts` (약 90번째 줄 이후 `analysis/wisdom/comfort/verse` 처리), `src/components/chat/message-bubble.tsx`
- **무슨 문제인가**: 과거 버전 AI 응답 형식을 계속 지원하기 위한 코드가 남아 있습니다. 지금은 유용하지만 시간이 지날수록 복잡도가 늘어납니다.
- **어떤 피해가 생기나**: 직접적 피해는 없으나 코드 이해와 유지보수가 점점 어려워집니다.
- **권장 조치**: 구버전 데이터가 충분히 사라진 시점에 호환 코드를 정리하세요.

## 🔒 보안 점검 결과

- ✅ **인증(로그인 검증)**: 채팅 API(`/api/chat`)와 모든 푸시/리마인더 API가 로그인 여부를 먼저 확인합니다. 로그인하지 않으면 AI 호출이 차단되어 API 키가 보호됩니다. **양호**
- ✅ **데이터베이스 접근 제어(RLS)**: 모든 테이블에 "본인 데이터만 읽기/쓰기 가능" 규칙(Row Level Security)이 걸려 있습니다. 프로필, 대화, 알림 구독, 기억 모두 사용자별로 격리됩니다. **양호**
- ✅ **API 키 관리**: Anthropic(AI) 키와 서비스 롤 키는 서버 환경변수로만 관리되고, 클라이언트에는 노출되는 값(Supabase 공개 키, VAPID 공개 키)만 전달됩니다. 올바른 설계입니다. **양호**
- ✅ **크론 엔드포인트 보호**: 알림 발송 자동 작업이 비밀 키(헤더 방식)로 보호되며, 쿼리스트링 노출을 막기 위해 헤더만 허용하는 세심함이 있습니다. **양호**
- ✅ **입력값 검증**: 리마인더의 시간·타임존·메시지 길이 등을 서버에서 검증하고, 이미지 데이터 형식과 크기를 확인합니다. **양호**
- ✅ **SQL 인젝션**: Supabase 클라이언트를 통한 파라미터화된 쿼리만 사용하므로 SQL 주입 위험은 없습니다. **양호**
- ✅ **보안 헤더**: 클릭재킹 방지, HTTPS 강제, 권한 제한 등 기본 보안 헤더가 설정되어 있습니다. **양호**
- ⚠️ **요청 제한의 실효성**: 위에서 설명했듯 rate limit이 단일 서버 메모리 기반이라 분산 환경에서 정확하지 않습니다. 비용 남용 방어 측면에서 **주의**가 필요합니다.
- ⚠️ **PIN 잠금의 강도**: `src/components/chat/pin-gate.tsx`의 4자리 PIN은 가벼운 해시(FNV-1a)로 브라우저에만 저장됩니다. 코드 주석에도 명시되어 있듯 이는 "가족이 잠깐 보는 것"을 막는 프라이버시 기능일 뿐 실제 보안 수단이 아닙니다. 의도된 설계이므로 문제는 아니나, 사용자에게 오해가 없도록 안내 유지 권장. **주의(설계상 의도됨)**
