전체적으로 코드 품질은 준수하며, 보안(로그인 검증, API 키 보호, 데이터베이스 접근 제어)의 기본기가 탄탄합니다. 다만 이번 점검에서 **가장 중요한 발견은 두 가지**입니다. 첫째, 실제 서비스에서 사용하는 데이터베이스 테이블 이름(`chat_sessions`, `chat_messages`, `messages`)이 코드 파일마다 서로 달라 **대화 기록과 마음 흐름 그래프가 제대로 저장·조회되지 않을 위험**이 있습니다. 둘째, 코드 점검 자동화 스크립트(`weekly-review.mjs`)에 **실제로는 존재하지 않는 AI 모델 이름**이 하드코딩되어 있어 리포트 생성이 실패할 수 있습니다. 그 외에 미완성 기능(예: 마음일지 PDF)과 중복 파일이 발견되었습니다.

## 🔴 즉시 해결이 필요한 문제

### 데이터베이스 테이블 이름이 파일마다 달라 대화·감정 기록이 누락될 수 있음
- **파일 위치**:
  - `src/lib/chat-data.ts` (46번째 줄 부근) — `messages` 테이블 사용
  - `src/app/journey/page.tsx` (110번째 줄 부근) — `chat_messages` 테이블 사용
  - `src/app/chat/page.tsx` (56번째 줄 부근) — `chat_sessions` 테이블 사용 (필터 없음)
  - `supabase/migrations/0001_init.sql` — 실제로는 `messages` 테이블만 정의됨
- **무슨 문제인가**: 데이터베이스에는 대화 내용을 저장하는 상자(테이블)가 있는데, 그 상자의 이름을 코드마다 다르게 부르고 있습니다. 실제로 만들어진 상자 이름은 `messages`(위 SQL 파일 기준)인데, 마음 흐름 그래프를 그리는 화면(`journey/page.tsx`)에서는 존재하지 않는 `chat_messages`라는 이름으로 데이터를 찾습니다. 이름이 맞지 않으면 데이터가 있어도 못 찾습니다.
- **어떤 피해가 생기나**: "마음의 흐름" 페이지가 실제로 대화를 나눈 사용자에게도 항상 "아직 기록된 대화가 충분하지 않아요"라고 빈 화면을 보여줄 수 있습니다. 사용자는 자신의 감정 기록이 사라졌다고 느끼고 앱을 신뢰하지 못하게 됩니다.
- **권장 조치**: 실제 데이터베이스에 어떤 이름의 테이블이 존재하는지 먼저 확인한 뒤, 모든 코드가 **동일한 하나의 이름**을 쓰도록 통일해야 합니다. 특히 `journey/page.tsx`의 `chat_messages`가 `messages`와 일치하는지, 컬럼(user_id 등)이 실제로 존재하는지 개발팀이 즉시 확인해야 합니다.

### 대화 저장이 로그인 화면 밖에서는 조용히 실패함(세션 없이 채팅 시)
- **파일 위치**: `src/components/chat/chat-app.tsx` (`sendMessage` 함수, 세션 생성 실패 처리 부분)
- **무슨 문제인가**: 새 대화를 시작할 때 데이터베이스에 대화방(session)을 만드는 데 실패하면, 코드는 오류를 무시하고 "메모리에만 임시로 저장"하는 방식으로 넘어갑니다(`sessionId = null`). 이 경우 사용자가 나눈 대화는 화면을 벗어나는 순간 영구히 사라집니다.
- **어떤 피해가 생기나**: 사용자는 깊은 감정을 나눴는데, 페이지를 새로고침하거나 다른 대화로 이동하면 그 기록이 통째로 없어집니다. 사용자에게 아무런 안내도 없이 조용히 사라지므로 신뢰를 크게 잃습니다.
- **권장 조치**: 세션 생성이 실패했을 때 사용자에게 "지금은 저장되지 않는 상태입니다" 같은 안내를 보여주거나, 저장 실패를 로그로 남겨 개발팀이 원인을 추적할 수 있게 해야 합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 주간 점검 자동화 스크립트에 존재하지 않는 AI 모델 이름이 적혀 있음
- **파일 위치**: `scripts/weekly-review.mjs` (`callClaude` 함수, `model: 'claude-opus-4-8'` 부분)
- **무슨 문제인가**: 이 리포트를 자동으로 만들어주는 스크립트가 `claude-opus-4-8`이라는 AI 모델을 호출하는데, 이 이름은 실제 존재하지 않는 모델일 가능성이 매우 높습니다(앱 본체는 `claude-sonnet-4-6`을 씁니다). 모델 이름이 틀리면 AI 서버가 요청을 거부합니다.
- **어떤 피해가 생기나**: 매주 자동으로 코드 점검 리포트를 받으려 해도, 스크립트가 오류를 내며 리포트를 만들지 못합니다.
- **권장 조치**: 앱 본체가 사용하는 것과 동일한, 실제로 존재하는 모델 이름으로 수정해야 합니다.

### 동일한 기능의 파일이 두 벌 존재함(관리 혼란)
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts` / `src/components/AddToHomePrompt.tsx` 와 `src/components/install-prompt.tsx`
- **무슨 문제인가**: 사용자의 장기 기억을 다루는 코드(`manna-memory.ts`)와 거의 똑같은 내용의 옛 파일(`selah-memory.ts`)이 함께 남아 있습니다. 앱 설치 안내 팝업도 두 종류(`AddToHomePrompt`, `install-prompt`)가 존재합니다. 실제로는 `manna-memory.ts`와 `install-prompt`만 사용됩니다.
- **어떤 피해가 생기나**: 나중에 기능을 수정할 때 어느 파일을 고쳐야 하는지 혼동이 생기고, 실수로 사용되지 않는 파일만 고쳐 "고쳤는데 안 바뀐다"는 문제가 발생할 수 있습니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`와 `AddToHomePrompt.tsx`가 정말 어디서도 쓰이지 않는지 확인 후 삭제하는 것이 좋습니다.

### 리마인더 알림 발송 시 순차 처리로 인한 지연 가능성
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (알림 발송 반복문 부분)
- **무슨 문제인가**: 정해진 시간에 여러 사용자에게 알림(푸시)을 보낼 때, 한 명씩 차례대로(순차적으로) 처리합니다. 사용자가 많아지면 한 사람 처리를 기다렸다가 다음 사람으로 넘어가므로 전체 발송이 느려집니다.
- **어떤 피해가 생기나**: 사용자가 늘어나면 예약한 시간(예: 오전 8시)보다 알림이 늦게 도착할 수 있습니다. 현재 규모에서는 큰 문제가 아니나, 성장 시 병목이 됩니다.
- **권장 조치**: 당장은 아니어도, 사용자 규모가 커지기 전에 여러 알림을 동시에 처리하는 방식으로 개선을 검토하는 것이 좋습니다.

### 마음일지 PDF 기능이 문구만 있고 실제 동작이 없음
- **파일 위치**: `src/lib/feature-strings.ts` (`journalExport`, `journalExporting`, `journalReady` 문구 정의)
- **무슨 문제인가**: "마음일지 PDF"라는 기능에 대한 안내 문구는 준비되어 있으나, 실제로 PDF를 만들어주는 코드는 어디에도 연결되어 있지 않습니다(미완성).
- **어떤 피해가 생기나**: 현재는 화면에 버튼이 노출되지 않아 직접적 피해는 없으나, 실수로 노출되면 사용자가 눌러도 아무 일이 일어나지 않는 "죽은 버튼"이 됩니다.
- **권장 조치**: 기능을 완성하거나, 계획이 없다면 관련 문구를 정리하는 것이 좋습니다.

## 🟢 장기적으로 개선하면 좋은 점

### 요청 제한(rate limit)이 서버 재시작 시 초기화됨
- **파일 위치**: `src/lib/rate-limit.ts`
- **무슨 문제인가**: 한 사용자가 짧은 시간에 너무 많은 요청을 보내지 못하도록 막는 장치가 있는데, 이 기록이 서버의 임시 메모리에만 저장됩니다. 서버가 새로 켜지거나(클라우드 환경에서 자주 발생) 여러 대로 나뉘면 이 기록이 초기화됩니다.
- **어떤 피해가 생기나**: 악의적 사용자가 이 허점을 이용해 AI 호출을 과도하게 일으켜 후원금으로 운영되는 API 비용을 낭비시킬 수 있습니다. 코드 주석에도 이미 이 한계가 명시되어 있습니다.
- **권장 조치**: 비용 부담이 커지면 Redis 같은 공유 저장소 기반의 요청 제한으로 전환을 검토하세요.

### PIN 잠금이 약한 방식으로 저장됨
- **파일 위치**: `src/components/chat/pin-gate.tsx` (`fnv1a` 함수)
- **무슨 문제인가**: 화면 잠금용 4자리 PIN을 저장할 때 보안이 약한 방식(FNV-1a)을 씁니다. 코드 주석에도 "인증을 대체하지 않는 개인정보 보호용"이라고 명시되어 있어 의도된 설계이긴 합니다.
- **어떤 피해가 생기나**: 기기에 접근한 사람이 저장된 값을 통해 PIN을 추측할 여지가 있습니다. 다만 이는 로그인 인증이 아닌 "가족이 옆에서 훔쳐보는 것 방지" 수준의 기능이므로 심각도는 낮습니다.
- **권장 조치**: 현 용도로는 충분하나, 향후 민감도가 높아지면 더 안전한 방식을 고려하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)**: ✅ 양호 — 채팅 API(`/api/chat`)와 모든 알림 관련 API가 요청 처리 전에 로그인 여부를 확인합니다. 미들웨어에서 `/chat` 경로를 보호합니다.
- **API 키 관리**: ✅ 양호 — Anthropic(Claude) API 키는 서버에서만 사용되며 클라이언트에 노출되지 않습니다. 로그인한 사용자만 AI를 호출할 수 있어 키가 보호됩니다.
- **데이터베이스 접근 제어(RLS)**: ✅ 양호 — 모든 테이블에 행 수준 보안(RLS)이 적용되어 사용자는 자신의 데이터만 읽고 쓸 수 있습니다. 크론 작업만 서비스 키로 우회하며, 이는 의도된 설계입니다.
- **크론(예약 작업) 엔드포인트 보호**: ✅ 양호 — 비밀 키를 헤더로만 받고, 쿼리스트링(URL에 노출되는 방식)은 거부하도록 개선되어 있습니다.
- **입력값 검증**: ⚠️ 주의 — 이미지 용량 제한, 시간 형식 검증, 메시지 길이 제한 등 대체로 잘 되어 있으나, 피드백/문의 저장 시 이메일 형식 검증이 없어 잘못된 값이 들어갈 수 있습니다(심각도 낮음).
- **SQL 인젝션**: ✅ 양호 — Supabase 라이브러리를 통해서만 데이터베이스에 접근하며, 직접 SQL 문자열을 조립하는 부분이 없어 위험이 낮습니다.
- **보안 헤더**: ✅ 양호 — 클릭재킹 방지, HTTPS 강제 등 기본 보안 헤더가 잘 설정되어 있습니다.
