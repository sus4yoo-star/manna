# 만나(MANNA) 주간 점검 리포트 — 2026-09-07

## 📌 요약 (한 눈에 보기)
전체적으로 코드 품질과 보안 기반이 탄탄한 프로젝트입니다. 인증(로그인 확인), 사용자별 데이터 격리(RLS), API 키 보호, 요청 제한 장치가 모두 갖춰져 있습니다. 다만 이번 점검에서 **데이터베이스 테이블 이름 불일치로 인한 채팅 기록 저장·조회 실패 가능성**이라는 심각한 문제가 발견되었습니다. 코드가 두 개의 서로 다른 테이블(`messages`와 `chat_messages`)을 참조하고 있어, 화면에 따라 저장한 대화가 보이지 않거나 마음의 흐름 그래프가 항상 비어 보일 수 있습니다. 또한 앱 전체에 남아 있는 `SELAH`/`MANNA` 정체성 혼재, 사용하지 않는 중복 파일(`selah-memory.ts`)도 정리가 필요합니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 메시지 테이블 이름 불일치 — 대화 저장·조회가 어긋남
- **파일 위치**: `src/lib/chat-data.ts` (48번째, 63번째 줄) vs `src/app/journey/page.tsx` (118~119번째 줄)
- **무슨 문제인가**: 대화를 저장하고 불러오는 핵심 코드(`chat-data.ts`)는 데이터베이스의 `messages`라는 테이블을 사용합니다. 그런데 "마음의 흐름"(감정 그래프) 화면(`journey/page.tsx`)은 `chat_messages`라는 **다른 이름의 테이블**을 조회합니다. 실제 데이터베이스 설계 파일(`supabase/migrations/0001_init.sql`)에는 `messages` 테이블만 정의되어 있고 `chat_messages`는 존재하지 않습니다.
- **어떤 피해가 생기나**: 마음의 흐름 그래프가 **항상 "기록된 대화가 충분하지 않아요"라고만 표시**되어 정상 작동하지 않습니다. 사용자가 아무리 오래 대화해도 감정 통계가 절대 나타나지 않습니다. 이 기능은 앱의 핵심 차별점 중 하나인데 완전히 죽어 있는 상태일 수 있습니다.
- **권장 조치**: `journey/page.tsx`의 `chat_messages`를 `messages`로 통일하거나, 반대로 전체 코드를 하나의 테이블 이름으로 맞춰야 합니다. 또한 `messages` 테이블에는 `user_id` 컬럼이 없는데(세션을 통해 소유권이 연결됨) journey 화면은 `.eq("user_id", ...)`로 직접 조회하고 있어, 테이블 이름을 고쳐도 이 조회 조건이 맞지 않습니다. 데이터 구조를 개발팀과 함께 재확인해야 합니다.

### 채팅 페이지가 사용자별 필터 없이 전체 세션을 조회
- **파일 위치**: `src/app/chat/page.tsx` (63~66번째 줄)
- **무슨 문제인가**: 채팅 목록을 불러올 때 `chat_sessions` 테이블에서 `.eq("user_id", ...)` 같은 **본인 필터 없이** 전체를 조회합니다. 현재는 데이터베이스의 RLS(행 단위 보안, 각 사용자가 자기 데이터만 보게 막는 장치)가 이를 막아주고 있어 실제 유출은 없습니다. 하지만 만약 RLS 설정이 실수로 꺼지거나 마이그레이션이 누락되면, **모든 사용자의 대화 제목이 서로에게 노출**될 수 있습니다.
- **어떤 피해가 생기나**: 보안의 "이중 방어" 원칙이 무너진 상태입니다. RLS 한 겹에만 의존하고 있어, 설정 실수 하나로 심각한 개인정보 유출이 발생할 수 있습니다. 만나는 마음속 이야기를 다루는 앱이라 피해가 특히 큽니다.
- **권장 조치**: journey 화면처럼 `.eq("user_id", user.id)` 조건을 명시적으로 추가해, 코드 레벨에서도 본인 데이터만 조회하도록 방어선을 하나 더 두는 것이 안전합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 사용되지 않는 중복 메모리 파일(selah-memory.ts) 방치
- **파일 위치**: `src/lib/selah-memory.ts` (전체)
- **무슨 문제인가**: `src/lib/manna-memory.ts`와 거의 100% 동일한 내용의 파일이 `selah-memory.ts`라는 이름으로 하나 더 존재합니다. 실제 채팅 코드는 `manna-memory.ts`만 사용하고, `selah-memory.ts`는 어디서도 불러오지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 향후 메모리 로직을 수정할 때 한쪽만 고치고 다른 쪽을 잊으면 혼란이 생깁니다. 또한 코드를 처음 보는 개발자가 "어느 게 진짜인지" 헷갈려 유지보수 시간이 늘어납니다.
- **권장 조치**: `selah-memory.ts` 파일을 삭제하세요. 사용처가 없으므로 삭제해도 앱 동작에 영향이 없습니다.

### 리마인더 발송 시 last_sent_at 갱신이 사용자 단위로만 이뤄짐
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (155~158번째 줄)
- **무슨 문제인가**: 알림을 성공적으로 보낸 뒤 "오늘 이미 보냈음"을 표시하는 `last_sent_at` 갱신이 `.eq("user_id", ...)` 조건으로 실행됩니다. `prayer_reminders` 테이블은 사용자당 한 줄이므로 현재는 문제없이 동작합니다. 다만 로직 구조상, 만약 알림 발송이 실패(모든 기기가 만료)하면 갱신되지 않아 크론이 매 실행마다 계속 재시도합니다.
- **어떤 피해가 생기나**: 죽은(만료된) 구독만 남은 사용자에 대해 크론이 매번 발송을 시도해 불필요한 처리 부담이 쌓일 수 있습니다. 사용자 수가 많아지면 크론 작업이 느려질 수 있습니다.
- **권장 조치**: 발송 시도 결과와 무관하게 하루 한 번은 처리 완료로 표시하거나, 만료된 구독은 즉시 정리(이미 부분적으로 구현됨)한 뒤 갱신 로직을 보완하는 것이 좋습니다.

### 브랜드 정체성(SELAH/MANNA) 혼재
- **파일 위치**: `README.md`, `src/lib/share-card.ts` (CardVariant "selah"), `src/lib/feature-strings.ts` (crossLinkSelahToMannaTitle 등), `supabase/001_user_memories.sql` (주석 "SELAH 2.1")
- **무슨 문제인가**: 앱은 MANNA로 출시되었지만 코드 곳곳에 이전 이름 SELAH가 남아 있습니다. README는 아예 SELAH 2.0 문서이고, 공유 카드 생성 코드에는 사용하지 않는 "selah" 테마가 포함되어 있으며, 데이터베이스 주석에도 SELAH가 남아 있습니다.
- **어떤 피해가 생기나**: 당장 사용자에게 보이는 오류는 아니지만, 새로운 개발자나 협업자가 두 서비스의 관계를 오해할 수 있고, 실수로 SELAH용 링크(`selah.theamov.com`)나 문구가 사용자에게 노출될 위험이 있습니다.
- **권장 조치**: README를 MANNA 기준으로 갱신하고, 사용하지 않는 SELAH 관련 코드 경로를 정리하세요.

### 크론 시크릿 미설정 시 알림 기능이 조용히 죽음
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (73~76번째 줄)
- **무슨 문제인가**: `CRON_SECRET` 환경변수가 설정되지 않으면 알림 발송 엔드포인트가 항상 503(서비스 불가)을 반환합니다. 이는 보안상 올바른 설계지만, 운영자가 이 설정을 빠뜨리면 **알림 기능 전체가 아무 경고 없이 작동하지 않습니다.**
- **어떤 피해가 생기나**: 사용자는 리마인더를 켜고 저장까지 성공하지만, 실제 정해진 시간에 알림이 오지 않습니다. 사용자는 "설정했는데 왜 안 오지?"라며 앱을 신뢰하지 못하게 됩니다.
- **권장 조치**: 배포 체크리스트에 `CRON_SECRET`, VAPID 키 설정을 명확히 포함하고, 운영자가 알림 발송 상태를 점검할 수 있는 간단한 방법(로그 확인 등)을 마련하세요.

## 🟢 장기적으로 개선하면 좋은 점

### 요청 제한(rate limit)이 서버 인스턴스 메모리에만 저장됨
- **파일 위치**: `src/lib/rate-limit.ts` (전체)
- **무슨 문제인가**: 한 사용자가 1분에 20회까지만 AI를 호출하도록 막는 장치가 서버의 임시 메모리에만 저장됩니다. Netlify 같은 서버리스 환경에서는 요청마다 다른 서버가 처리할 수 있어, 실제로는 이 제한이 느슨하게 적용됩니다. 코드 주석에도 이미 이 한계가 명시되어 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자가 여러 서버 인스턴스에 요청을 분산하면 제한을 우회해 AI API 비용을 크게 소모시킬 수 있습니다. 후원으로 운영되는 앱이라 비용 폭증은 실질적 위협입니다.
- **권장 조치**: 사용자가 늘어나면 Upstash Redis나 데이터베이스 기반의 공유 요청 제한으로 전환을 검토하세요. 당장은 시급하지 않습니다.

### PIN 잠금이 약한 해시 방식 사용
- **파일 위치**: `src/components/chat/pin-gate.tsx` (fnv1a 함수, 34~40번째 줄)
- **무슨 문제인가**: 화면 잠금용 4자리 PIN을 FNV-1a라는 매우 단순한 방식으로 저장합니다. 4자리 숫자는 경우의 수가 1만 개뿐이라, 저장된 값만 있으면 순식간에 원래 PIN을 알아낼 수 있습니다.
- **어떤 피해가 생기나**: 코드 주석에도 명시되어 있듯 이 PIN은 인증이 아니라 "가족이 잠깐 볼 때 막는 용도"입니다. 실제 보안 방어선은 아니므로 피해는 제한적입니다. 다만 사용자가 이를 강력한 보안으로 오해할 수 있습니다.
- **권장 조치**: 현재 용도 내에서는 수용 가능합니다. 다만 UI에서 "간단한 개인정보 보호용"임을 명확히 안내하면 좋습니다.

### 이미지가 데이터베이스에 저장되지 않음
- **파일 위치**: `src/components/chat/chat-app.tsx` (194~196번째 줄 부근)
- **무슨 문제인가**: 사용자가 대화 중 첨부한 사진은 AI 분석에만 쓰이고 저장되지 않습니다. 대화 기록을 다시 열면 이미지는 사라지고 "[사진을 보냈어요]" 텍스트만 남습니다. 이는 저장 비용 절감을 위한 의도된 설계입니다.
- **어떤 피해가 생기나**: 사용자가 과거 대화를 다시 봤을 때 어떤 사진이었는지 기억나지 않아 맥락이 끊길 수 있습니다.
- **권장 조치**: 현재는 의도된 동작이므로 문제는 아닙니다. 향후 사용자 요청이 많으면 저장 옵션을 검토할 수 있습니다.

## 🔒 보안 점검 결과

- **인증(로그인 검증)**: ✅ 양호 — 채팅 API(`/api/chat`), 알림 API 모두 로그인 여부를 확인합니다. 미들웨어에서 `/chat` 경로를 보호합니다.
- **API 키 관리**: ✅ 양호 — Anthropic API 키는 서버에서만 사용되고 클라이언트에 노출되지 않습니다. 크론은 시크릿 헤더로 보호됩니다.
- **데이터베이스 접근 제어(RLS)**: ⚠️ 주의 — RLS 정책은 잘 설계되어 있으나, `chat/page.tsx`가 코드 레벨에서 본인 필터를 생략해 RLS 한 겹에만 의존합니다. 이중 방어 권장.
- **입력값 검증**: ✅ 양호 — 이미지 크기 제한, 시간·타임존 형식 검증, 메시지 길이 제한 등이 적절히 구현되어 있습니다.
- **SQL 인젝션**: ✅ 양호 — Supabase 클라이언트를 통한 파라미터화된 쿼리만 사용해 직접적인 SQL 조립이 없습니다.
- **보안 헤더**: ✅ 양호 — 클릭재킹 방지, HTTPS 강제, MIME 스니핑 차단 등 기본 보안 헤더가 설정되어 있습니다.
- **크론 시크릿 노출 방지**: ✅ 양호 — 쿼리스트링이 아닌 헤더로만 시크릿을 받아 로그 유출 위험을 줄였습니다.
- **개인 데이터 서드파티 처리**: ✅ 양호 — 개인정보처리방침에 위탁업체가 투명하게 명시되어 있습니다.
