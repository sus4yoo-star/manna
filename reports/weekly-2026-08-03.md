# 만나(MANNA) 주간 점검 리포트 — 2026-08-03

## 📌 요약 (한 눈에 보기)

전반적으로 코드 품질과 보안이 매우 우수한 성숙한 코드베이스입니다. 로그인 인증, 데이터 접근 제어(사용자별 데이터 격리), API 키 보호가 잘 되어 있습니다. 다만 이번 점검에서 **가장 심각한 발견은 채팅 메시지 저장 로직이 실제로 동작하지 않는다는 점**입니다. 앱은 `messages` 테이블을 사용하는 코드와 `chat_messages` 테이블을 사용하는 코드가 뒤섞여 있어, 사용자의 대화 기록이 저장되지 않거나 마음의 흐름(Journey) 화면이 항상 비어 보일 가능성이 큽니다. 또한 자동 리포트 생성 스크립트에 존재하지 않는 AI 모델명이 하드코딩되어 있어 리포트 자동화가 실패하고 있을 수 있습니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 메시지 저장/조회 테이블 이름 불일치 (대화 기록이 사라질 위험)

- **파일 위치**: `src/lib/chat-data.ts` (48번째 줄, 66번째 줄) vs `src/app/journey/page.tsx` (120~121번째 줄), `src/app/chat/page.tsx` (58번째 줄)
- **무슨 문제인가**: 대화 내용을 저장·조회하는 곳마다 사용하는 데이터베이스 테이블 이름이 서로 다릅니다.
  - 실제 저장/조회 함수(`chat-data.ts`)와 데이터베이스 설계도(`supabase/migrations/0001_init.sql`)는 **`messages`** 라는 테이블을 씁니다.
  - 그런데 마음의 흐름 화면(`journey/page.tsx`)은 **`chat_messages`** 라는 (설계도에 존재하지 않는) 테이블을 조회합니다.
  - 또한 채팅 목록 화면(`chat/page.tsx` 58번째 줄)은 **`chat_sessions`** 를 사용자ID 필터 없이 조회하는데, 반면 journey 화면은 `chat_sessions`를 `user_id`로 필터링합니다.
- **어떤 피해가 생기나**: 
  - "마음의 흐름(Journey)" 그래프 화면이 데이터가 있어도 **항상 비어 있게** 보일 수 있습니다(`chat_messages` 테이블이 없으면 조회 결과가 빈 값).
  - 반대로 `messages` 테이블에는 대화가 정상 저장되지만, 감정 흐름 분석 기능이 그 데이터를 전혀 못 읽습니다.
  - 사용자는 "며칠 동안 마음을 나눴는데 왜 아무 기록도 안 보이지?"라는 혼란을 겪습니다.
- **권장 조치**: 앱 전체에서 메시지 테이블 이름을 **하나로 통일**해야 합니다. `chat-data.ts`와 설계도가 `messages`를 쓰므로, `journey/page.tsx`의 `chat_messages`를 `messages`로 바꾸는 것이 가장 안전합니다. 단, `messages` 테이블에는 `user_id` 컬럼이 없고 `session_id`만 있으므로(설계도 확인 필요), journey 화면의 조회 방식도 세션을 거쳐 조회하도록 수정해야 합니다. 실제 운영 DB에 어떤 테이블이 존재하는지 먼저 확인하는 것이 급선무입니다.

### 자동 리포트 생성 스크립트에 존재하지 않는 AI 모델명 사용

- **파일 위치**: `scripts/weekly-review.mjs` (120번째 줄)
- **무슨 문제인가**: 주간 코드 점검 리포트를 자동 생성하는 스크립트가 `claude-opus-4-8` 이라는 모델명을 호출합니다. 이는 실제로 존재하지 않는 모델명입니다(현재 코드베이스 다른 곳에서는 `claude-sonnet-4-6`을 사용). 마찬가지로 `src/lib/anthropic.ts`의 주석에도 `claude-opus-4-7` 같은 존재하지 않는 모델명이 언급되어 있습니다.
- **어떤 피해가 생기나**: 주간 자동 점검 리포트 생성이 **매번 실패**하여, 운영진이 코드 상태를 자동으로 파악하지 못합니다. AI API가 "존재하지 않는 모델" 오류를 반환합니다.
- **권장 조치**: `scripts/weekly-review.mjs` 120번째 줄의 모델명을 실제 존재하는 최신 모델명(예: `claude-sonnet-4-6` 또는 확인된 Opus 모델명)으로 수정하세요. 개발팀이 Anthropic 공식 문서에서 현재 유효한 모델명을 확인 후 반영하는 것이 안전합니다.

### 메모리 관리 로직이 매 대화마다 별도 AI 호출을 발생시켜 비용·지연 증가

- **파일 위치**: `src/app/api/chat/route.ts` (238~248번째 줄, `persist` 함수), `src/lib/manna-memory.ts` (`updateUserMemory`)
- **무슨 문제인가**: 사용자가 메시지를 하나 보낼 때마다, 답변 생성용 AI 호출 외에 **"장기 기억 업데이트"용 AI를 한 번 더** 호출합니다. 즉 대화 1회당 AI가 2번 실행됩니다.
- **어떤 피해가 생기나**: 
  - 기부금으로 운영되는 앱에서 **API 비용이 사실상 2배**로 늘어납니다.
  - 스트리밍이 끝난 뒤 기억 업데이트 호출이 완료될 때까지 응답 흐름이 지연될 수 있습니다.
- **권장 조치**: 기억 업데이트를 매번 하지 말고, 예를 들어 3~5개 대화마다 한 번, 혹은 의미 있는 대화일 때만 실행하도록 조건을 추가하는 것을 권장합니다. 당장 출시 차단 요소는 아니지만 비용 관점에서 빠르게 검토가 필요합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 중복된 메모리 파일 (selah-memory.ts와 manna-memory.ts가 거의 동일)

- **파일 위치**: `src/lib/selah-memory.ts` 와 `src/lib/manna-memory.ts`
- **무슨 문제인가**: 두 파일이 거의 완전히 동일한 코드입니다(내용이 SELAH/MANNA만 다를 뿐 로직 동일). `selah-memory.ts`는 실제로 어디서도 import되지 않는 것으로 보이는 죽은 코드(dead code)입니다.
- **어떤 피해가 생기나**: 한쪽만 수정하고 다른 쪽을 잊으면 혼란이 생기며, 유지보수 시 어느 파일이 진짜인지 헷갈립니다. 당장 사용자 피해는 없습니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하여 코드베이스를 정리하세요.

### 인메모리 방식 사용량 제한(rate limit)이 서버리스 환경에서 불완전

- **파일 위치**: `src/lib/rate-limit.ts` 전체, `src/app/api/chat/route.ts` (69번째 줄)
- **무슨 문제인가**: 사용자별 "1분에 20회" 요청 제한을 서버 메모리에만 저장합니다. Netlify 같은 서버리스 환경은 요청마다 다른 서버 인스턴스가 처리할 수 있어, 제한이 인스턴스별로 따로 세어집니다(코드 주석에도 이 한계가 명시되어 있음).
- **어떤 피해가 생기나**: 악의적 사용자가 여러 인스턴스로 분산 요청하면 제한을 우회할 수 있어, AI API 비용 폭증 가능성이 있습니다. 일반 사용자에게는 문제가 없습니다.
- **권장 조치**: 사용량이 늘어나기 전에, 공유 저장소(예: Upstash Redis, Supabase 카운터 테이블) 기반의 제한으로 교체하는 것을 권장합니다. 현재는 기본 방어 수준으로 봐도 됩니다.

### 채팅 페이지에서 로그인 판정 시 getSession() 폴백의 보안적 여유

- **파일 위치**: `src/app/chat/page.tsx` (37~48번째 줄)
- **무슨 문제인가**: 로그인 확인 시, 정식 검증(`getUser()`)이 실패하면 쿠키에서 세션을 그대로 신뢰(`getSession()`)합니다. 이는 "로그인 두 번 해야 하는 버그"를 막기 위한 의도적 조치이며 주석에도 잘 설명되어 있습니다.
- **어떤 피해가 생기나**: 실제 데이터 접근은 데이터베이스의 접근 제어(RLS)로 보호되므로 심각한 위험은 아니지만, 이론적으로 화면 진입 판정이 정식 검증보다 느슨합니다.
- **권장 조치**: 현재 RLS가 실제 데이터를 보호하고 있으므로 유지해도 무방합니다. 다만 이 폴백이 정말 필요한지 정기적으로 재확인하고, 불필요해지면 제거하는 것을 권장합니다.

### 이미지가 서버로는 전달되지만 저장은 되지 않음 (기능 설계상 의도이나 사용자 혼란 여지)

- **파일 위치**: `src/components/chat/chat-app.tsx` (206~211번째 줄 주석)
- **무슨 문제인가**: 사용자가 첨부한 사진은 AI 응답에는 쓰이지만 저장되지 않습니다. 대화를 나중에 다시 열면 사진은 사라지고 "[사진을 보냈어요]" 표시만 남습니다.
- **어떤 피해가 생기나**: 사용자가 예전 대화의 사진을 다시 보려 할 때 없어서 당황할 수 있습니다. 저장 용량 절약을 위한 의도된 설계입니다.
- **권장 조치**: 의도된 동작이라면 그대로 두되, 사용자에게 "사진은 저장되지 않습니다" 같은 안내를 첨부 시점에 표시하는 것을 고려하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)** — ✅ 양호: 채팅 API(`/api/chat`)와 알림 관련 API 모두 로그인하지 않은 사용자를 401 오류로 차단합니다. AI 모델 접근 전에 반드시 로그인을 확인합니다.
- **API 키 관리** — ✅ 양호: Anthropic API 키(AI 통신 키)와 Supabase 서비스 키는 서버 환경변수로만 다루며, 클라이언트에 노출되지 않습니다. 클라이언트에는 공개용 anon 키와 VAPID 공개키만 전달됩니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: 모든 주요 테이블(프로필, 세션, 메시지, 알림, 기억)에 사용자별 행 수준 보안(RLS)이 설정되어 있어, 사용자는 자신의 데이터만 읽고 씁니다. 데이터베이스 설계가 견고합니다.
- **입력값 검증** — ⚠️ 주의: 이미지 크기 제한, 시간 형식 검증(정규식), 타임존 검증은 잘 되어 있습니다. 다만 채팅 메시지 텍스트 자체의 길이 제한이 명시적이지 않아, 아주 긴 텍스트가 들어올 여지가 있습니다(단, 최근 16개 메시지만 사용하도록 제한됨).
- **SQL 인젝션** — ✅ 양호: Supabase 클라이언트 라이브러리를 통해서만 데이터베이스에 접근하므로 직접적인 SQL 조작이 없어 인젝션 위험이 없습니다.
- **크론 엔드포인트 보호** — ✅ 양호: 알림 발송 크론(`/api/cron/send-reminders`)은 비밀 키(`x-cron-secret` 헤더)로 보호되며, 쿼리스트링이 아닌 헤더로만 받도록 되어 있어 로그 유출 위험도 낮췄습니다.
- **보안 헤더** — ✅ 양호: 클릭재킹 방지, MIME 스니핑 방지, HTTPS 강제 등 기본 보안 헤더가 모두 설정되어 있습니다.
- **사용량 제한(남용 방지)** — ⚠️ 주의: 위 🟡 항목에서 설명한 대로 서버리스 환경에서 완벽하지 않습니다.
