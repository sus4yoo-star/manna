# 만나(MANNA) 주간 점검 리포트 — 2026-08-10

## 📌 요약 (한 눈에 보기)
전체적으로 코드 완성도가 높고, 인증·권한·보안 기본기(로그인 검증, 데이터베이스 접근 제어, 요청 속도 제한, 보안 헤더)가 잘 갖춰져 있습니다. 다만 이번 점검에서 **가장 심각한 문제 3가지**가 발견되었습니다: (1) 대화 저장 기능이 실제로는 작동하지 않을 가능성이 높은 데이터베이스 테이블 이름 불일치, (2) 자동화된 코드 점검 스크립트가 존재하지 않는 AI 모델 이름을 사용해 매주 실패하는 문제, (3) 채팅 저장 시 로그인한 사용자와 세션 소유자가 일치하는지 서버에서 검증하지 않는 잠재적 보안 허점입니다. 이 중 첫 번째는 사용자에게 직접 피해가 가는 문제로 즉시 확인이 필요합니다.

## 🔴 즉시 해결이 필요한 문제

### 대화 기록이 저장/조회되지 않을 수 있는 테이블 이름 불일치
- **파일 위치**: `src/lib/chat-data.ts` (49번째 줄, `listMessages` 함수 / 61번째 줄, `saveMessage` 함수) 와 `supabase/migrations/0001_init.sql` (메시지 테이블 정의 부분)
- **무슨 문제인가**: 데이터베이스(사용자 정보를 저장하는 창고)에 대화 메시지를 담는 테이블(창고 안의 서랍) 이름이 설계도(`0001_init.sql`)에는 **`messages`** 로 만들어져 있습니다. 그런데 앱의 여러 부분이 서로 다른 이름으로 이 서랍을 찾습니다.
  - `src/lib/chat-data.ts`는 **`messages`** 라는 이름으로 조회/저장합니다 (설계도와 일치).
  - 반면 `src/app/journey/page.tsx` (114번째 줄 부근)는 **`chat_messages`** 라는 다른 이름으로 조회합니다.
  - 즉, 두 곳이 서로 다른 서랍을 열고 있어, 한쪽은 반드시 실패합니다.
- **어떤 피해가 생기나**: "마음의 흐름(감정 그래프)" 페이지에서 사용자의 과거 대화를 불러오지 못해 **항상 빈 그래프**가 표시될 가능성이 높습니다. 사용자가 며칠 동안 마음을 나눴는데도 "아직 기록된 대화가 충분하지 않아요"라는 메시지만 계속 보게 되어, 앱의 핵심 가치(마음의 흐름 추적)가 무너집니다.
- **권장 조치**: 실제 Supabase 데이터베이스에 있는 테이블 이름을 확인한 뒤, 모든 코드가 **하나의 동일한 이름**을 쓰도록 통일해야 합니다. `journey/page.tsx`의 `chat_messages`를 `messages`로 바꾸거나, 반대로 통일하세요. 또한 `journey/page.tsx`는 `user_id`로 직접 조회하는데, `messages` 테이블에는 `user_id` 컬럼이 없고 `session_id`만 있으므로(설계도 기준) 조회 방식 자체도 재검토가 필요합니다.

### 주간 자동 점검 스크립트가 존재하지 않는 AI 모델을 호출해 매번 실패
- **파일 위치**: `scripts/weekly-review.mjs` (Claude API 호출 부분, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 리포트를 자동 생성하는 스크립트가 AI 모델 이름으로 **`claude-opus-4-8`** 을 지정하고 있습니다. 이는 실제로 존재하지 않는 이름입니다(앱 본체는 `claude-sonnet-4-6`을 사용). 존재하지 않는 모델을 부르면 AI 서버가 오류를 돌려줍니다.
- **어떤 피해가 생기나**: 매주 자동으로 코드 점검 리포트를 만들려는 시도가 **매번 실패**하여, 운영자가 문제를 조기에 발견할 기회를 잃습니다. (이번 리포트가 생성된 것은 별도 환경에서 실행되었기 때문일 수 있습니다.)
- **권장 조치**: `scripts/weekly-review.mjs`의 모델 이름을 실제 사용 가능한 이름(예: 앱과 동일한 `claude-sonnet-4-6` 또는 검증된 최신 모델)으로 수정하세요.

### 채팅 저장 시 세션 소유자 검증이 서버에서 이루어지지 않음
- **파일 위치**: `src/lib/chat-data.ts` (전체) 및 `src/app/api/chat/route.ts` (`sessionId`를 받지만 검증에 사용하지 않는 부분)
- **무슨 문제인가**: 대화를 저장할 때, 앱은 "이 대화방(세션)이 정말 지금 로그인한 사람의 것인가?"를 확인해야 합니다. 현재는 데이터베이스의 접근 제어 규칙(RLS)에 이 검증을 전적으로 의존하고 있습니다. RLS 규칙 자체는 잘 설정되어 있으나(설계도상 세션 소유권을 통해 메시지 접근을 막음), 앱 코드(`chat-data.ts`)에는 별도의 방어 장치가 없습니다.
- **어떤 피해가 생기나**: 만약 데이터베이스 규칙 설정에 실수가 생기거나 향후 규칙이 완화되면, 악의적 사용자가 다른 사람의 대화방 번호를 추측해 메시지를 끼워 넣거나 조회를 시도할 여지가 생깁니다. 현재는 RLS가 막고 있어 실제 피해 확률은 낮지만, "이중 잠금"이 없는 상태입니다.
- **권장 조치**: 데이터베이스 RLS 규칙이 프로덕션에서 반드시 활성화되어 있는지 재확인하고(가장 중요), 추가로 서버 측(`chat-data.ts` 또는 API)에서 `sessionId`가 현재 사용자 소유인지 한 번 더 확인하는 방어 코드를 넣는 것을 권장합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 사용하지 않는 중복 파일이 남아 혼란 유발
- **파일 위치**: `src/lib/selah-memory.ts` (전체)
- **무슨 문제인가**: 이 파일은 `src/lib/manna-memory.ts`와 거의 완전히 동일한 내용(장기 기억 관리 기능)입니다. 앱은 `manna-memory.ts`만 사용하고 `selah-memory.ts`는 어디서도 불러 쓰지 않습니다. 과거 이름(SELAH)의 잔재로 보입니다.
- **어떤 피해가 생기나**: 나중에 개발자가 기억 기능을 수정할 때 어느 파일을 고쳐야 할지 헷갈려 한쪽만 고치는 실수를 할 수 있고, 코드가 불필요하게 무거워집니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts` 파일을 삭제하세요.

### 대화 저장 시 원본 이미지가 저장되지 않아 재방문 시 사라짐
- **파일 위치**: `src/components/chat/chat-app.tsx` (`saveMessage` 호출 부분, "The image itself is not persisted" 주석)
- **무슨 문제인가**: 사용자가 사진(예: 카카오톡 대화 캡처)을 올려 상담하면, 그 사진은 저장되지 않고 "[사진을 보냈어요]"라는 글자만 저장됩니다(저장 공간 절약 목적).
- **어떤 피해가 생기나**: 사용자가 나중에 그 대화를 다시 열면 자신이 무슨 사진을 올렸는지 볼 수 없어 대화 맥락을 잃습니다. 의도된 설계이나, 사용자 입장에서는 혼란스러울 수 있습니다.
- **권장 조치**: 저장 정책은 유지하되, 재방문 시 "사진은 보관되지 않습니다"라는 안내를 표시하거나, 저장 비용을 감안해 이미지 보관 기능을 검토하세요.

### 요청 속도 제한이 서버 재시작 시 초기화됨
- **파일 위치**: `src/lib/rate-limit.ts` (전체) 및 `src/app/api/chat/route.ts` (`rateLimit` 사용 부분)
- **무슨 문제인가**: 한 사용자가 1분에 20회 이상 요청하지 못하게 막는 장치가 있으나, 이 기록이 **서버 메모리에만** 저장됩니다. Netlify 같은 환경은 서버가 자주 새로 뜨는데, 그때마다 기록이 사라집니다. (파일 내 주석에도 이 한계가 명시되어 있습니다.)
- **어떤 피해가 생기나**: 악용하려는 사용자가 여러 서버 인스턴스에 분산 요청하면 제한을 우회할 수 있어, AI 사용료(후원금으로 운영)가 예상보다 많이 나갈 수 있습니다.
- **권장 조치**: 후원 규모가 커지거나 남용 징후가 보이면, 여러 서버가 공유하는 저장소(예: Upstash Redis, Postgres 카운터)로 속도 제한을 옮기세요. 현재 규모에서는 낮은 우선순위입니다.

### 로그인 직후 세션 인증의 임시방편적 처리
- **파일 위치**: `src/app/chat/page.tsx` (`getUser()` 실패 시 `getSession()`으로 대체하는 부분) 및 `src/app/login/page.tsx` (`waitForSession` 함수)
- **무슨 문제인가**: 로그인 직후 인증 정보가 서버에 전파되기 전에 화면이 넘어가면 "로그인을 두 번 해야 하는" 문제가 생기는데, 이를 막기 위해 최대 1.5초 기다리거나(`waitForSession`), 검증이 덜 엄격한 방식(`getSession`)으로 우회하고 있습니다.
- **어떤 피해가 생기나**: 현재는 잘 작동하나, 이는 타이밍에 의존하는 임시방편입니다. 네트워크가 느린 환경에서는 여전히 로그인이 한 번에 안 될 수 있고, `getSession`은 서버에서 토큰을 실제 검증하지 않아 이론적으로 신뢰도가 낮습니다.
- **권장 조치**: 현 방식이 실제 사용자에게서 문제를 일으키는지 모니터링하고, 문제가 반복되면 Supabase의 인증 콜백 흐름을 재점검하세요.

## 🟢 장기적으로 개선하면 좋은 점

### 다국어 지원이 일부 기능에서 영어로만 표시됨
- **파일 위치**: `src/lib/feature-strings.ts` (`TABLE` 정의, 한국어·영어만 존재)
- **무슨 문제인가**: 앱은 30개 언어를 지원한다고 하지만, "마음의 흐름", "리마인더", "위기 상황 안내 카드" 등 나중에 추가된 기능의 문구는 **한국어와 영어만** 번역되어 있고, 나머지 언어 사용자는 영어를 보게 됩니다(파일 주석에도 명시).
- **어떤 피해가 생기나**: 태국어·스페인어 등 다른 언어 사용자는 일부 화면에서 영어를 만나 어색함을 느낄 수 있습니다. 핵심 채팅은 정상 번역되므로 치명적이지는 않습니다.
- **권장 조치**: 사용자 언어 통계를 보고 사용량이 많은 언어부터 점진적으로 번역을 추가하세요.

### 위기 상황(자살 위험 등) 안내 전화번호가 한국·미국에만 최적화
- **파일 위치**: `src/lib/feature-strings.ts` (`hotlinesFor` 함수)
- **무슨 문제인가**: 위기 감지 시 안내되는 상담 전화가 한국어 사용자는 한국 번호, 그 외 모든 언어는 미국 번호(988, 911)로 나옵니다.
- **어떤 피해가 생기나**: 태국·인도 등 다른 국가 사용자가 위기 상황에서 자국이 아닌 미국 번호를 안내받아 실질적 도움을 받기 어렵습니다. 생명과 직결될 수 있는 부분입니다.
- **권장 조치**: 서비스 대상 국가별 실제 위기 상담 번호를 조사해 언어별로 추가하는 것을 중장기 과제로 두세요.

### 채팅 저장을 기다리지 않아 실패해도 사용자가 모름
- **파일 위치**: `src/components/chat/chat-app.tsx` (`saveMessage(...).catch(() => {})` 부분)
- **무슨 문제인가**: 대화 저장이 실패해도 조용히 무시하도록(`.catch(() => {})`) 되어 있습니다. 앱이 멈추지 않게 하려는 의도입니다.
- **어떤 피해가 생기나**: 저장이 계속 실패하는 상황(예: 위에 언급한 테이블 이름 문제)에서도 사용자와 운영자 모두 이를 알아채지 못해 문제가 오래 방치될 수 있습니다.
- **권장 조치**: 저장 실패가 반복될 경우 최소한 개발자 로그나 모니터링 도구에 기록을 남기도록 개선하세요.

## 🔒 보안 점검 결과

- ✅ **양호 — 인증(로그인 검증)**: 채팅 API(`src/app/api/chat/route.ts`)는 로그인하지 않은 사용자를 확실히 차단합니다. 미들웨어(`src/lib/supabase/middleware.ts`)도 `/chat` 경로를 보호합니다.
- ✅ **양호 — 데이터베이스 접근 제어(RLS)**: 모든 주요 테이블(프로필, 대화방, 메시지, 리마인더, 기억)에 "사용자는 자기 데이터만 접근" 규칙이 꼼꼼히 설정되어 있습니다.
- ✅ **양호 — API 키 관리**: AI 키(`ANTHROPIC_API_KEY`)는 서버에서만 사용되며 화면에 노출되지 않습니다. 웹 푸시 공개키만 클라이언트에 노출되는데 이는 정상입니다.
- ✅ **양호 — 관리자 권한 키 보호**: 크론 작업(`cron/send-reminders`)은 공유 비밀번호(`CRON_SECRET`)를 헤더로만 받고, 쿼리 문자열 사용을 명시적으로 막았습니다(로그 유출 방지).
- ✅ **양호 — 보안 헤더**: `next.config.mjs`에 클릭재킹 방지, HTTPS 강제 등 기본 보안 헤더가 잘 설정되어 있습니다.
- ✅ **양호 — 요청 속도 제한**: 기본적인 남용 방지 장치가 존재합니다(단, 위 🟡 항목의 한계 있음).
- ⚠️ **주의 — 입력값 검증**: 대부분의 API가 입력을 검증하나(리마인더 시간 형식, 이미지 크기 상한 등), 채팅 저장 시 세션 소유권 검증을 앱 코드에서 하지 않고 RLS에만 의존합니다(위 🔴 항목).
- ⚠️ **주의 — 피드백 저장 시 이메일 신뢰**: 문의(`feedback-modal.tsx`)에서 사용자가 입력한 이메일을 그대로 저장하는데, 검증이 없습니다. 심각하진 않으나 잘못된 주소로 답변 불가 상황이 생길 수 있습니다.
- ❌ **위험 없음 — SQL 인젝션**: Supabase 라이브러리를 통해 안전하게 쿼리하므로 직접적인 SQL 인젝션 위험은 발견되지 않았습니다.
