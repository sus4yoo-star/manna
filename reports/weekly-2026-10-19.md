## 📌 요약 (한 눈에 보기)
전반적으로 코드 품질이 높고 보안 기본기(로그인 검증, 데이터 접근 제어, 보안 헤더, 요청 제한)가 탄탄하게 갖춰져 있습니다. 다만 **이번 주 가장 중요한 발견은 채팅 기록 저장이 실제로는 동작하지 않을 가능성이 높다는 점**입니다. 데이터베이스 테이블 이름이 코드마다 `messages`와 `chat_messages`로 엇갈려 있어, 사용자가 로그인 후 과거 대화를 다시 열어보는 핵심 기능이 깨질 수 있습니다. 또한 자동 점검 스크립트에 **실제로 존재하지 않는 AI 모델 이름**이 하드코딩되어 있어 주간 리포트 자동 생성이 실패할 위험이 있습니다. 그 외에는 미세한 중복 코드와 운영 안정성 관련 개선 여지가 있는 수준입니다.

## 🔴 즉시 해결이 필요한 문제

### 데이터베이스 테이블 이름 불일치로 대화 기록·여정 화면이 깨질 수 있음
- **파일 위치**: `src/lib/chat-data.ts` (49번째 줄 부근의 `from("messages")`), `src/app/journey/page.tsx` (약 110번째 줄의 `from("chat_messages")`), `supabase/migrations/0001_init.sql` (테이블명 `messages`로 정의)
- **무슨 문제인가**: 앱이 대화 메시지를 저장·조회할 때 사용하는 "서랍장 이름"이 코드마다 다릅니다. 데이터베이스 설계 파일(`0001_init.sql`)에는 서랍장 이름이 `messages`로 되어 있는데, 실제 대화를 불러오는 코드 중 일부(`chat-data.ts`)는 `messages`를 쓰고, "마음의 흐름"(여정) 화면(`journey/page.tsx`)은 존재하지 않는 `chat_messages`라는 다른 이름을 찾고 있습니다.
- **어떤 피해가 생기나**: 
  - "마음의 흐름" 화면이 항상 "아직 기록된 대화가 충분하지 않아요"라고만 표시되어 **감정 그래프 기능이 통째로 작동하지 않습니다**.
  - 만약 운영 DB에 `chat_messages` 테이블로 만들어져 있다면 반대로 `chat-data.ts`의 대화 저장/불러오기가 전부 실패해, 사용자가 과거 대화를 다시 열 수 없습니다. 둘 중 하나는 반드시 깨져 있는 상태입니다.
- **권장 조치**: 실제 Supabase에 어떤 이름의 테이블이 있는지 먼저 확인하고, 모든 코드와 마이그레이션 파일에서 **단 하나의 이름으로 통일**하세요. (저장 코드가 `messages`를 쓰고 있으므로 `journey/page.tsx`의 `chat_messages`를 `messages`로 고치는 것이 가장 안전합니다.) 더불어 `journey/page.tsx`는 메시지 데이터에 `session_id`만 있고 `user_id` 컬럼이 없는데 `.eq("user_id", ...)`로 조회하고 있어, 테이블명을 고쳐도 조회가 실패할 수 있습니다. 이 조건도 함께 점검해야 합니다.

### 자동 점검 스크립트에 존재하지 않는 AI 모델명이 박혀 있음
- **파일 위치**: `scripts/weekly-review.mjs` (약 110번째 줄, `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 매주 코드를 자동 점검해 리포트를 만드는 스크립트가 AI에게 요청할 때 `claude-opus-4-8`이라는 모델 이름을 사용하는데, 이는 실제로 존재하지 않는 이름입니다. (앱 본체는 `src/lib/anthropic.ts`에서 `claude-sonnet-4-6`을 쓰고 있어 서로 다릅니다.)
- **어떤 피해가 생기나**: 주간 자동 점검 리포트 생성이 "모델을 찾을 수 없음" 오류로 **매번 실패**합니다. 운영자가 코드 상태를 주기적으로 파악하려던 목적이 달성되지 않습니다.
- **권장 조치**: `scripts/weekly-review.mjs`의 모델 이름을 실제 사용 가능한 모델(예: 앱 본체와 같은 `claude-sonnet-4-6` 또는 유효한 Opus 모델명)로 교체하세요.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 메모리 관련 코드가 두 벌로 중복되어 혼란·유지보수 위험
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts` (거의 동일한 내용)
- **무슨 문제인가**: 사용자의 장기 대화 기억을 다루는 코드가 `manna-memory.ts`와 `selah-memory.ts`에 거의 똑같이 두 번 들어 있습니다. 실제로는 `manna-memory.ts`만 사용되고 `selah-memory.ts`는 쓰이지 않는 것으로 보입니다.
- **어떤 피해가 생기나**: 나중에 한쪽만 수정하고 다른 쪽을 빠뜨리면 버그로 이어집니다. 또한 두 파일 모두 같은 DB 테이블 `user_memories`를 사용하는데, 메모리 저장 SQL 파일(`supabase/001_user_memories.sql`)이 "SELAH 2.1"용으로만 설명되어 있어, 이 테이블이 운영 DB에 실제로 생성되지 않았다면 기억 기능이 조용히 비활성화됩니다(코드가 오류를 삼키도록 설계됨).
- **권장 조치**: 사용하지 않는 `selah-memory.ts`를 삭제하고, `user_memories` 테이블이 운영 DB에 실제로 만들어져 있는지 확인하세요.

### 보안 헤더에 콘텐츠 보안 정책(CSP)이 빠져 있음
- **파일 위치**: `next.config.mjs` (headers 설정 부분)
- **무슨 문제인가**: 클릭재킹 방지, HTTPS 강제 등 좋은 보안 헤더들이 설정돼 있지만, 외부 스크립트 주입 공격을 막아주는 CSP(Content-Security-Policy, 어떤 출처의 코드만 실행할지 제한하는 규칙)가 없습니다.
- **어떤 피해가 생기나**: 만약 어딘가에서 악성 스크립트가 주입되는 취약점이 생기면, CSP가 있었다면 막혔을 공격이 통할 수 있습니다. 당장의 취약점은 아니지만 방어막 한 겹이 빠진 상태입니다.
- **권장 조치**: Supabase·Anthropic 도메인만 허용하는 CSP 헤더를 단계적으로 도입하세요. (한 번에 엄격하게 넣으면 정상 기능이 깨질 수 있어 테스트하며 적용 권장)

### AI 응답 상류 요청에 타임아웃(시간 제한)이 없음
- **파일 위치**: `src/app/api/chat/route.ts` (약 190번째 줄, Anthropic으로 `fetch` 호출 부분)
- **무슨 문제인가**: AI 서버(Anthropic)에 답변을 요청할 때 "몇 초 안에 응답이 없으면 포기한다"는 제한 시간이 설정돼 있지 않습니다.
- **어떤 피해가 생기나**: AI 서버가 응답을 지연시키면 사용자는 로딩 화면에서 하염없이 기다리게 되고, 서버 자원도 묶여 있게 됩니다.
- **권장 조치**: AI 요청에 적절한 타임아웃(예: 30~60초)을 추가하고, 초과 시 사용자에게 친절한 재시도 안내를 보여주세요.

## 🟢 장기적으로 개선하면 좋은 점

### 요청 제한(rate limit)이 서버 인스턴스별로만 동작
- **파일 위치**: `src/lib/rate-limit.ts`
- **무슨 문제인가**: 한 사용자가 1분에 20회로 요청을 제한하는 기능이 있으나, 이는 서버 한 대의 메모리에만 저장됩니다. Netlify처럼 여러 서버가 뜨는 환경에서는 사용자가 여러 서버에 분산되면 실제 제한이 느슨해질 수 있습니다. (코드 주석도 이 한계를 이미 인지하고 있습니다.)
- **어떤 피해가 생기나**: 악의적 사용자가 AI 비용(후원금으로 운영)을 빠르게 소모시킬 여지가 있습니다. 당장 심각하진 않습니다.
- **권장 조치**: 트래픽이 커지면 Upstash Redis 같은 공유 저장소 기반 제한으로 교체를 검토하세요.

### 자동 삭제가 세션(대화방)만 지우고 메시지 정리는 DB 연쇄삭제에 의존
- **파일 위치**: `src/components/chat/chat-app.tsx` (자동 삭제 로직 부분)
- **무슨 문제인가**: 오래된 대화 자동 삭제 기능이 화면이 켜질 때 한 번만 실행되고, 사용자가 로그인해 있지 않으면 아예 동작하지 않습니다. 설계상 큰 문제는 아니지만 "30일 후 삭제" 약속이 즉시 보장되지는 않습니다.
- **어떤 피해가 생기나**: 개인정보처리방침상 자동 삭제를 명시했다면, 실제 삭제 시점이 사용자 재방문 여부에 의존해 지연될 수 있습니다.
- **권장 조치**: 중요하게 다룬다면 서버 측 예약 작업(cron)으로 자동 삭제를 보강하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)** — ✅ 양호: `/api/chat`, 알림, 리마인더 등 모든 민감 API가 `supabase.auth.getUser()`로 로그인 여부를 먼저 확인합니다. 미들웨어도 `/chat` 경로를 보호합니다.
- **API 키 관리** — ✅ 양호: Anthropic API 키는 서버(`process.env.ANTHROPIC_API_KEY`)에서만 사용되고 클라이언트로 노출되지 않습니다. VAPID 공개키만 클라이언트에 노출되는데 이는 의도된 안전한 설계입니다.
- **입력값 검증** — ⚠️ 주의: 이미지 크기 제한, 리마인더 시간 형식 검증 등은 잘 되어 있으나, `journey/page.tsx`의 DB 조회 조건(`user_id`) 불일치 문제가 기능 오류로 이어질 수 있어 함께 점검이 필요합니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: 모든 테이블에 Row Level Security가 켜져 있고, 사용자는 자기 데이터만 읽고 쓸 수 있도록 정책이 촘촘히 설정돼 있습니다.
- **크론(예약작업) 엔드포인트 보호** — ✅ 양호: `send-reminders`는 헤더의 비밀키(`x-cron-secret`)로 보호되며, 쿼리스트링 노출 위험까지 제거한 세심한 설계입니다.
- **서비스 롤 키 사용 범위** — ✅ 양호: RLS를 우회하는 강력한 서비스 롤 키는 크론 작업에서만 제한적으로 사용됩니다.
- **SQL 인젝션** — ✅ 양호: Supabase 쿼리 빌더만 사용하며 직접 SQL 문자열을 조합하지 않아 위험이 낮습니다.
- **보안 헤더** — ⚠️ 주의: 기본 헤더는 훌륭하나 CSP가 빠져 있습니다(위 🟡 참조).
