# 만나(MANNA) 주간 점검 리포트 — 2026-10-26

## 📌 요약 (한 눈에 보기)

전체적으로 안정적이고 잘 구조화된 코드베이스입니다. 인증(로그인 검증), 데이터 접근 제어(사용자별 데이터 격리), 보안 헤더 등 핵심 보안 요소가 대부분 양호합니다. 다만 **이번 주 가장 중요한 발견은, 채팅 기록을 저장하는 데이터베이스 테이블 이름이 코드마다 서로 달라 실제로 대화가 저장되지 않거나 불러와지지 않을 수 있는 심각한 불일치**입니다. 또한 주간 점검 스크립트가 존재하지 않는 AI 모델명을 사용하고 있어 자동 리포트 생성이 실패할 가능성이 있습니다. 전반적인 사용자 경험과 다국어 지원은 매우 뛰어난 수준입니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 저장 테이블 이름 불일치 — 대화가 저장·복원되지 않을 위험

- **파일 위치**: `src/lib/chat-data.ts` (49번째 줄, 66번째 줄) vs `src/app/chat/page.tsx` (56번째 줄), `src/app/api/chat/route.ts` (전반), `src/app/journey/page.tsx` (113번째 줄)
- **무슨 문제인가**: 앱에는 사용자의 대화 메시지를 저장하는 "서랍(데이터베이스 테이블)"이 있습니다. 그런데 코드마다 서랍 이름을 다르게 부르고 있습니다.
  - `chat-data.ts`에서는 메시지를 `messages`라는 테이블에 저장/조회합니다.
  - 그런데 `journey/page.tsx`에서는 `chat_messages`라는 이름으로 조회합니다.
  - 데이터베이스 설계도(`supabase/migrations/0001_init.sql`)에는 `messages`만 정의되어 있고 `chat_messages`는 존재하지 않습니다.
  - 또한 `journey/page.tsx`와 `chat-data.ts`가 조회할 때 `messages` 테이블에 `user_id` 컬럼이 있다고 가정하는 부분이 있는데(`journey`는 `chat_messages`에 `.eq("user_id", ...)` 사용), 실제 설계도의 `messages` 테이블에는 `user_id` 컬럼이 없습니다(세션을 거쳐 소유권을 확인함).
- **어떤 피해가 생기나**: "마음의 흐름(감정 그래프)" 페이지가 항상 "아직 기록된 대화가 충분하지 않아요"라고 비어 보이거나, 오류가 납니다. 사용자가 며칠간 마음을 나눠도 그래프가 전혀 채워지지 않아, 핵심 기능 중 하나가 작동하지 않는 것처럼 보입니다.
- **권장 조치**: 테이블 이름을 하나로 통일해야 합니다. `journey/page.tsx` 113번째 줄의 `chat_messages`를 `messages`로 바꾸고, 메시지에 `user_id`가 필요하다면 데이터베이스 설계도(`0001_init.sql`)의 `messages` 테이블에 `user_id` 컬럼을 추가하는 마이그레이션을 작성하거나, 세션을 거쳐 조회하도록 쿼리를 수정해야 합니다. 개발팀이 실제 Supabase에 어떤 테이블이 존재하는지 먼저 확인한 뒤 코드를 맞추는 것이 가장 안전합니다.

### 주간 점검 스크립트가 존재하지 않는 AI 모델을 호출함

- **파일 위치**: `scripts/weekly-review.mjs` (108번째 줄)
- **무슨 문제인가**: 이 주간 리포트를 자동 생성하는 스크립트가 AI 모델 이름을 `claude-opus-4-8`로 지정하고 있습니다. 이는 현재 존재하지 않는 모델명입니다. (본 앱이 사용하는 `src/lib/anthropic.ts`의 실제 모델은 `claude-sonnet-4-6`입니다.)
- **어떤 피해가 생기나**: 주간 자동 점검 리포트 생성이 "모델을 찾을 수 없음" 오류로 실패할 수 있습니다. 운영 담당자가 정기 리포트를 못 받게 됩니다.
- **권장 조치**: `scripts/weekly-review.mjs` 108번째 줄의 모델명을 실제 사용 가능한 모델(예: `claude-sonnet-4-6` 또는 Anthropic이 제공하는 유효한 최신 모델명)로 수정하세요. 간단한 수정입니다.

### AI 기본 모델명이 실존하지 않을 가능성

- **파일 위치**: `src/lib/anthropic.ts` (22번째 줄)
- **무슨 문제인가**: 채팅 응답을 만드는 기본 AI 모델이 `claude-sonnet-4-6`으로 하드코딩되어 있습니다. 주석에는 `claude-opus-4-7`로 바꾸라는 안내도 있습니다. 이 모델명들이 Anthropic의 실제 최신 모델명과 일치하는지 반드시 확인이 필요합니다. (모델명은 Anthropic이 수시로 바꾸며, 오타나 미래 추정 이름이면 호출이 실패합니다.)
- **어떤 피해가 생기나**: 모델명이 틀리면 모든 채팅 요청이 실패하여 사용자가 어떤 응답도 받지 못합니다. 서비스 전체가 먹통이 되는 수준의 피해입니다.
- **권장 조치**: 배포 환경 변수 `ANTHROPIC_MODEL`에 현재 실제로 유효한 모델명을 설정하고, 운영 중인 실제 서비스에서 채팅이 정상 응답하는지 확인하세요. 코드의 기본값도 유효한 모델명으로 맞추는 것이 안전합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 중복된 메모리 모듈 파일 (manna-memory.ts와 selah-memory.ts)

- **파일 위치**: `src/lib/manna-memory.ts`, `src/lib/selah-memory.ts`
- **무슨 문제인가**: 두 파일이 거의 완전히 동일한 코드(장기 대화 기억 기능)를 담고 있습니다. `selah-memory.ts`는 실제로는 어디에서도 사용되지 않는 것으로 보이며(채팅 라우트는 `manna-memory.ts`만 import), 과거 SELAH 앱에서 복사해 온 잔재입니다.
- **어떤 피해가 생기나**: 앞으로 메모리 로직을 수정할 때 두 파일을 모두 고쳐야 하는지 헷갈려, 한쪽만 고치고 다른 쪽은 방치되는 실수가 생깁니다. 유지보수 혼란과 버그의 원인이 됩니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하세요. 삭제 전에 전체 코드에서 이 파일을 import하는 곳이 없는지 한 번 더 확인하면 됩니다.

### 비로그인 사용자의 메시지가 조용히 사라짐

- **파일 위치**: `src/components/chat/chat-app.tsx` (190~200번째 줄 부근, `sendMessage` 함수)
- **무슨 문제인가**: 세션(대화방) 생성에 실패하면 `sessionId`를 `null`로 두고 "임시 메모리 대화"로 전환합니다. 이 경우 메시지가 데이터베이스에 저장되지 않아, 페이지를 새로고침하면 대화가 사라집니다. 사용자에게는 아무 안내도 없습니다.
- **어떤 피해가 생기나**: 사용자가 마음을 깊이 나눈 소중한 대화가 저장되지 않았다는 사실을 모른 채 잃어버릴 수 있습니다. 마음 동행 앱에서 이는 신뢰에 큰 타격입니다.
- **권장 조치**: 세션 생성에 실패했을 때 사용자에게 "지금은 기록이 저장되지 않을 수 있어요" 같은 안내를 보여주거나, 저장 실패를 로그로 남겨 운영팀이 빈도를 파악할 수 있게 하세요.

### 비로그인 사용자도 /journey, /reminders 페이지에 접근 가능

- **파일 위치**: `src/app/journey/page.tsx`, `src/app/reminders/page.tsx`, `src/middleware.ts` (matcher 설정)
- **무슨 문제인가**: 미들웨어(접근을 걸러주는 문지기)는 `/chat` 경로만 로그인 보호를 합니다. `/journey`와 `/reminders`는 보호 대상이 아닙니다. 데이터 조회는 안에서 다시 로그인 여부를 확인하므로 데이터가 새지는 않지만, 비로그인 사용자에게 빈 화면이 보이는 어정쩡한 상태가 됩니다.
- **어떤 피해가 생기나**: 데이터 유출은 없으나, 로그인하지 않은 사용자가 빈 감정 그래프 페이지를 보고 "앱이 고장났나?"라고 오해할 수 있습니다.
- **권장 조치**: `src/middleware.ts`의 보호 경로에 `/journey`, `/reminders`도 포함하거나, 각 페이지에서 비로그인 시 로그인 페이지로 안내하도록 처리하세요.

### 알림(Push) 전송이 순차적으로 처리되어 사용자 증가 시 느려짐

- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (135~160번째 줄 부근)
- **무슨 문제인가**: 매일 알림을 보낼 때, 사용자와 기기를 한 명씩 차례대로(`for` 반복 안에서 `await`) 처리합니다. 사용자가 적을 때는 괜찮지만, 수백·수천 명이 같은 시간대에 알림을 받도록 설정하면 순차 처리로 인해 시간이 오래 걸려 일부 알림이 제시간에 못 가거나 서버 실행 시간 제한에 걸릴 수 있습니다.
- **어떤 피해가 생기나**: 사용자가 설정한 시간에 "마음 다잡는 시간" 알림이 도착하지 않을 수 있습니다.
- **권장 조치**: 당장은 사용자 수가 적어 문제없으나, 사용자가 늘어나기 전에 알림 전송을 여러 건 동시에 처리(병렬화)하도록 개선하는 것을 권장합니다. 반나절 정도의 작업입니다.

### 개인정보처리방침의 외부 도메인이 실제 배포 도메인과 다름

- **파일 위치**: `src/app/business/page.tsx` ("서비스 도메인: manna.amov.kr"), `src/app/layout.tsx` (metadataBase: `https://themanna.netlify.app`), `src/components/chat/cross-link-card.tsx` (`https://selah.theamov.com`)
- **무슨 문제인가**: 사업자정보 페이지는 서비스 도메인을 `manna.amov.kr`로 안내하지만, 실제 메타데이터와 설치 안내는 `themanna.netlify.app`을 사용합니다. 또한 크로스링크 카드는 `selah.theamov.com`을 가리키는데, 다른 곳의 후원 안내는 `selah.theamov.com`과 `theamov.com`이 섞여 있습니다.
- **어떤 피해가 생기나**: 사용자가 공유하거나 방문할 때 도메인이 일관되지 않아 신뢰도가 떨어지고, 실제로 연결되지 않는 링크가 있을 수 있습니다.
- **권장 조치**: 최종 서비스 도메인을 하나로 확정하고(예: `manna.amov.kr`), 모든 페이지·메타데이터·링크를 그 도메인으로 통일하세요.

## 🟢 장기적으로 개선하면 좋은 점

### 요청 제한(Rate Limit)이 서버 인스턴스별로만 동작

- **파일 위치**: `src/lib/rate-limit.ts` (전체)
- **무슨 문제인가**: 한 사용자가 1분에 20번까지만 채팅할 수 있게 제한하는 장치가 있는데, 이 기록이 서버 메모리에만 저장됩니다. Netlify 같은 환경은 여러 서버가 번갈아 처리하므로, 사용자가 여러 서버로 분산되면 실제로는 제한을 우회할 수 있습니다. (코드 주석에도 이미 인지하고 있다고 적혀 있습니다.)
- **어떤 피해가 생기나**: 악의적 사용자가 AI 요청을 대량으로 보내 후원금으로 운영되는 API 비용을 급증시킬 수 있습니다. 지금 당장은 사용자가 적어 위험이 낮습니다.
- **권장 조치**: 사용량이 늘면 Upstash Redis 같은 공유 저장소를 이용한 분산 요청 제한으로 교체하는 것을 권장합니다.

### `any` 타입 사용이 많아 타입 안정성이 낮음

- **파일 위치**: `src/app/api/chat/route.ts` (47번째 줄 `let supabase: any`), `src/app/api/cron/send-reminders/route.ts`, `src/app/api/push/*` 등 다수
- **무슨 문제인가**: 여러 곳에서 데이터 형태를 "무엇이든 될 수 있음(any)"으로 처리합니다. 이러면 데이터 구조가 바뀌어도 코드가 미리 오류를 잡아주지 못합니다.
- **어떤 피해가 생기나**: 데이터베이스 컬럼명이 바뀌거나 응답 형태가 달라졌을 때 오류가 사용자에게 도달해서야 발견될 수 있습니다. (실제로 이번 리포트의 테이블명 불일치가 이런 유형의 사례입니다.)
- **권장 조치**: 시간이 될 때 주요 데이터 구조에 명확한 타입을 지정하면 장기적으로 버그가 줄어듭니다.

### 단위 테스트가 전혀 없음

- **파일 위치**: 프로젝트 전체 (테스트 파일 없음)
- **무슨 문제인가**: 의도 분류(`classifyIntent`), 위기 감지(`detectCrisis`), 감정 점수(`scoreEmotion`), AI 응답 파싱(`parseAI`) 등 핵심 로직에 자동 검증 코드가 없습니다.
- **어떤 피해가 생기나**: 코드를 수정할 때마다 기존 기능이 망가졌는지 수동으로 일일이 확인해야 하며, 놓치기 쉽습니다. 특히 위기 감지 같은 안전 기능은 조용히 고장나면 위험합니다.
- **권장 조치**: 위기 감지와 의도 분류처럼 안전·정확성이 중요한 함수부터 간단한 테스트를 추가하는 것을 권장합니다.
