# 만나(MANNA) 주간 점검 리포트 — 2026-07-20

## 📌 요약 (한 눈에 보기)
전체적으로 코드베이스는 잘 정돈되어 있고, 인증(로그인 검증)·데이터 접근 제어(RLS)·API 키 보호 등 보안의 핵심 골격은 견고합니다. 다만 이번 점검에서 **채팅 데이터 저장 로직이 실제 데이터베이스 테이블과 어긋나 있어, 사용자가 나눈 대화가 저장되지 않는 심각한 버그**를 발견했습니다. 이는 앱의 가장 핵심 기능(대화 기록 저장·복원)을 망가뜨릴 수 있어 최우선으로 확인이 필요합니다. 또한 동일한 코드가 두 파일에 중복되어 있고(`manna-memory.ts`/`selah-memory.ts`), 주간 점검 스크립트가 존재하지 않는 AI 모델 이름을 사용하는 등 정리·수정이 필요한 부분들이 있습니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 저장·조회가 실제 데이터베이스 테이블과 일치하지 않음
- **파일 위치**: `src/lib/chat-data.ts` (전체, 특히 42~72번째 줄), 대조: `supabase/migrations/0001_init.sql` (messages 테이블 정의)
- **무슨 문제인가**: 데이터베이스에는 대화 메시지를 담는 테이블 이름이 `messages`(그리고 사용자 구분 컬럼은 `session_id`)로 정의되어 있습니다. 그런데 화면 코드 곳곳에서 서로 다른 이름을 사용합니다.
  - `src/lib/chat-data.ts`는 `messages` 테이블을 사용합니다(정상).
  - 그러나 `src/app/journey/page.tsx` 105~106번째 줄은 `chat_messages` 테이블을 조회하며, `user_id` 컬럼으로 필터링합니다. 실제 `messages` 테이블에는 `chat_messages`라는 이름도, `user_id`라는 컬럼도 없습니다.
  즉, 같은 데이터를 두고 코드마다 **다른 테이블/컬럼 이름**을 부르고 있어 최소 한 쪽은 반드시 실패합니다.
- **어떤 피해가 생기나**: "마음의 흐름(journey)" 페이지가 항상 빈 화면으로 나오거나(데이터 조회 실패), 감정 그래프가 전혀 그려지지 않습니다. 사용자는 "내 대화 기록이 사라졌다"고 느끼게 되고, 이 앱의 핵심 가치(마음의 여정을 되돌아보기)가 작동하지 않습니다.
- **권장 조치**: 데이터베이스의 실제 테이블 이름(`messages`)과 컬럼(`session_id`)을 기준으로 **모든 코드를 한 이름으로 통일**하세요. 특히 `journey/page.tsx`의 `chat_messages`→`messages`, `user_id` 필터를 세션 기반 조회로 수정해야 합니다. 배포 전 실제 로그인 → 대화 → journey 페이지 확인 순서로 반드시 테스트가 필요합니다.

### journey 페이지가 사용자 구분 없이 데이터를 요청함
- **파일 위치**: `src/app/journey/page.tsx` 100~112번째 줄
- **무슨 문제인가**: journey 페이지는 `chat_sessions`와 `chat_messages`를 `user_id`로 필터링해서 가져옵니다. 하지만 데이터베이스 정의상 `messages` 테이블에는 `user_id` 컬럼이 없고(세션을 통해 소유자를 판별함), 위 문제와 맞물려 조회가 실패합니다. 설령 이름을 고치더라도, 감정 점수 계산이 클라이언트(사용자 브라우저)에서 전체 메시지를 내려받아 처리하는 구조라 대화가 많아지면 느려질 수 있습니다.
- **어떤 피해가 생기나**: 감정 여정 그래프가 비거나, 대화가 쌓인 사용자일수록 페이지 로딩이 느려져 이탈로 이어질 수 있습니다.
- **권장 조치**: 위 항목과 함께 테이블/컬럼 이름을 바로잡고, 데이터가 많은 사용자를 위해 조회 범위(최근 90일)를 데이터베이스 쿼리 단계에서 제한하는 방향을 검토하세요.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 동일한 기능 코드가 두 파일에 중복되어 있음
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts` (거의 동일한 내용 전체)
- **무슨 문제인가**: 장기 기억(사용자와의 대화를 기억하는 기능) 코드가 두 파일에 거의 똑같이 존재합니다. 실제로는 `manna-memory.ts`만 사용되고 `selah-memory.ts`는 아무 데서도 불러오지 않는 것으로 보입니다.
- **어떤 피해가 생기나**: 나중에 기억 로직을 고칠 때 한 파일만 고치고 다른 파일을 잊으면, 두 코드가 서로 달라져 혼란과 버그를 유발합니다. 코드가 무거워지고 유지보수 비용이 늘어납니다.
- **권장 조치**: 사용하지 않는 `selah-memory.ts`를 삭제하거나, 공통 로직을 한 파일로 합쳐 한 곳에서만 관리하세요.

### 주간 점검 스크립트가 존재하지 않는 AI 모델 이름을 사용
- **파일 위치**: `scripts/weekly-review.mjs` 100번째 줄 (`model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 리포트를 자동 생성하는 스크립트가 `claude-opus-4-8`이라는 모델을 호출합니다. 이는 실제로 존재하지 않는 모델명일 가능성이 높습니다(앱 본체는 `claude-sonnet-4-6`을 씁니다).
- **어떤 피해가 생기나**: 주간 점검 리포트 자동 생성이 매번 오류로 실패해, 운영자가 코드 상태를 정기적으로 파악하지 못할 수 있습니다.
- **권장 조치**: 앱에서 실제 사용 중인 유효한 모델명(예: `claude-sonnet-4-6` 또는 확인된 opus 모델명)으로 교체하세요.

### 대화 저장 실패가 사용자에게 조용히 넘어감
- **파일 위치**: `src/components/chat/chat-app.tsx` 249, 291번째 줄 부근 (`saveMessage(...).catch(() => {})`)
- **무슨 문제인가**: 대화를 데이터베이스에 저장하는 처리가 실패해도 오류를 무시하고 넘어갑니다(빈 catch). 위의 테이블 이름 불일치 문제와 겹치면, 저장이 계속 실패해도 화면상으로는 정상처럼 보입니다.
- **어떤 피해가 생기나**: 사용자는 대화가 저장된 줄 알지만, 다음에 로그인하면 기록이 없어 큰 실망과 신뢰 하락으로 이어집니다. 문제가 발생해도 운영자가 알아차리기 어렵습니다.
- **권장 조치**: 저장 실패 시 최소한 개발자 콘솔이나 운영 로그에 기록을 남기고, 반복 실패 시 사용자에게 부드럽게 안내하는 장치를 추가하세요.

### 크론(예약 실행) 알림이 하루 여러 번 발송될 수 있는 구조
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` 105~120번째 줄 부근
- **무슨 문제인가**: 알림 발송 시각이 사용자의 설정 시각과 ±4분 이내로 맞으면 발송하도록 되어 있습니다. 크론이 1분마다 실행되는 환경이라면, 같은 시간대 안에서 여러 번 조건에 맞아 발송될 수 있습니다. "하루 한 번" 중복 방지 로직이 있지만, `last_sent_at` 업데이트와 발송 사이의 시차로 인해 짧은 시간에 여러 번 겹쳐 나갈 여지가 있습니다.
- **어떤 피해가 생기나**: 사용자가 같은 알림을 하루에 여러 번 받아 불편해할 수 있고, 앱 알림 자체를 꺼버릴 수 있습니다.
- **권장 조치**: 크론 실행 주기를 5분 이상으로 두거나, 발송 직전에 `last_sent_at`을 먼저 갱신하는 방식으로 중복 발송 가능성을 줄이세요.

## 🟢 장기적으로 개선하면 좋은 점

### 인메모리 방식 요청 제한의 한계
- **파일 위치**: `src/lib/rate-limit.ts` (전체)
- **무슨 문제인가**: 사용자별 요청 폭주를 막는 장치가 "현재 실행 중인 서버 한 대의 메모리"에만 저장됩니다. Netlify 같은 서버리스 환경에서는 서버가 여러 개로 나뉘거나 자주 초기화되어, 이 제한이 완전하게 작동하지 않습니다. (코드 주석에도 이 점이 명시되어 있습니다.)
- **어떤 피해가 생기나**: 악의적 사용자가 여러 요청을 분산시키면 제한을 우회할 수 있어, 유료 AI 호출 비용이 예상보다 많이 나갈 수 있습니다.
- **권장 조치**: 사용량이 늘어나면 Redis(Upstash 등) 같은 공유 저장소 기반 제한으로 전환을 검토하세요. 당장 급하지는 않습니다.

### PWA 설치 안내 컴포넌트가 두 개로 중복
- **파일 위치**: `src/components/AddToHomePrompt.tsx` 와 `src/components/install-prompt.tsx`
- **무슨 문제인가**: 홈 화면 추가(앱처럼 설치)를 유도하는 팝업이 두 개의 서로 다른 컴포넌트로 존재합니다. 실제로는 `install-prompt.tsx`만 화면(layout)에 연결되어 있는 것으로 보이며, `AddToHomePrompt.tsx`는 사용되지 않는 듯합니다.
- **어떤 피해가 생기나**: 유지보수 시 혼동이 생기고, 실수로 둘 다 활성화되면 사용자가 비슷한 팝업을 두 번 보게 됩니다.
- **권장 조치**: 사용하지 않는 컴포넌트를 정리하세요.

### 데이터베이스 마이그레이션 파일의 테이블 명칭 혼재 정리
- **파일 위치**: `supabase/migrations/0001_init.sql` (messages) 및 앱 코드 전반
- **무슨 문제인가**: 최초 스키마는 `messages`를 쓰지만, 앱 코드 일부는 `chat_messages`를 기대합니다(🔴 항목 참조). 향후 데이터베이스 구조를 정리할 때 명칭 규칙을 하나로 확정해 두면 이런 불일치를 근본적으로 예방할 수 있습니다.
- **어떤 피해가 생기나**: 명칭 규칙이 흐릿하면 새 기능 추가 시 같은 종류의 버그가 반복됩니다.
- **권장 조치**: 테이블/컬럼 명명 규칙을 문서로 확정하고, 마이그레이션과 코드가 항상 일치하도록 관리하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)** — ✅ 양호: 채팅 API(`src/app/api/chat/route.ts`)는 요청 시작 시 로그인 여부를 검증하고, 미로그인 시 401로 차단합니다. 알림·리마인더 API들도 모두 로그인 확인을 거칩니다.
- **API 키 관리(Claude 등)** — ✅ 양호: Anthropic API 키는 서버에서만 사용되고 브라우저로 노출되지 않습니다. VAPID 개인 키(알림 서명 키)도 서버 전용으로 분리되어 있습니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: 모든 테이블에 행 수준 보안(RLS, 사용자가 자기 데이터만 접근)이 적용되어, 다른 사람의 대화·설정을 볼 수 없도록 구성되어 있습니다.
- **크론(예약 실행) 보호** — ✅ 양호: 알림 발송 크론은 비밀 키를 헤더로만 받도록 하여(쿼리스트링 노출 방지) 무단 호출을 차단합니다.
- **입력값 검증** — ⚠️ 주의: 대부분의 API가 기본 검증을 하지만, 리마인더 메시지(`reminders/route.ts`)는 길이 제한(300자) 외에 내용 필터가 거의 없습니다. 큰 위험은 아니나, 알림 문구가 그대로 저장·발송되므로 향후 검토 여지가 있습니다.
- **이미지 업로드 용량 제한** — ✅ 양호: 채팅 이미지에 대해 서버·클라이언트 양쪽에서 용량 상한을 두어 비용·메모리 남용을 방지합니다.
- **보안 헤더** — ✅ 양호: 클릭재킹 방지, MIME 스니핑 차단, HTTPS 강제 등 기본 보안 헤더가 설정되어 있습니다.
- **요청 폭주 방지** — ⚠️ 주의: 사용자별 요청 제한이 있으나 서버리스 환경에서 완전하지 않습니다(위 장기 개선 항목 참조).
