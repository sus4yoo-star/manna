# 만나(MANNA) 주간 점검 리포트 — 2026-10-05

## 📌 요약 (한 눈에 보기)
전반적으로 코드 품질이 높고, 인증·보안·다국어 처리가 성숙한 수준입니다. 다만 **데이터베이스 테이블 이름 불일치로 인한 치명적 버그**가 발견되었습니다. 코드는 `chat_messages`와 `messages` 테이블을 섞어 쓰고 있어, 대화 저장·복원이 일부 화면에서 작동하지 않을 가능성이 높습니다. 또한 주간 점검 스크립트에 **존재하지 않는 AI 모델명**이 하드코딩되어 있어 리포트 자동 생성이 실패할 수 있습니다. 이 두 가지가 이번 주 최우선 해결 대상입니다.

---

## 🔴 즉시 해결이 필요한 문제

### 데이터베이스 테이블 이름이 서로 맞지 않음 (대화 기록이 저장/표시 안 될 위험)
- **파일 위치**: `src/lib/chat-data.ts` (49번째 줄 `listMessages`, 62번째 줄 `saveMessage`는 `messages` 테이블 사용) vs `src/app/journey/page.tsx` (약 120번째 줄 `chat_messages` 테이블 사용)
- **무슨 문제인가**: 앱이 대화 내용을 저장하는 "서랍"(데이터베이스 테이블)의 이름이 코드마다 다릅니다. 실제로 데이터베이스에 만들어진 서랍 이름은 `messages`(파일 `supabase/migrations/0001_init.sql` 기준)인데, "마음의 흐름"(journey) 화면은 `chat_messages`라는 **존재하지 않는 서랍**에서 데이터를 꺼내려 합니다. 또한 journey 화면은 `chat_sessions`를 `user_id`로 필터링하는데, 메시지 테이블에는 `user_id` 컬럼 자체가 없습니다(메시지는 세션을 통해 소유자가 결정됨).
- **어떤 피해가 생기나**: "마음의 흐름" 그래프가 항상 비어 있게 보이고(사용자는 "기록이 없다"고 오해), 감정 추이·공유 이미지 기능이 전혀 작동하지 않습니다. 사용자가 실제로는 수십 번 대화했는데도 데이터가 하나도 없는 것처럼 보입니다.
- **권장 조치**: 테이블 이름을 하나로 통일해야 합니다. 실제 DB 스키마가 `messages`이므로 `journey/page.tsx`의 `chat_messages`를 `messages`로 바꾸고, 메시지를 가져올 때는 사용자의 세션 목록을 먼저 조회한 뒤 그 세션들의 메시지를 조회하도록 수정해야 합니다(메시지 테이블에 `user_id`가 없기 때문). 또는 DB에 `user_id` 컬럼을 추가하는 방법도 있습니다. 개발팀과 어느 쪽이 맞는지 먼저 확인이 필요합니다.

### 주간 점검 스크립트에 존재하지 않는 AI 모델명이 적혀 있음
- **파일 위치**: `scripts/weekly-review.mjs` (약 115번째 줄 `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 이 리포트를 자동으로 만드는 스크립트가 `claude-opus-4-8`이라는 모델을 호출하는데, 이는 실제로 존재하지 않는 이름일 가능성이 매우 높습니다(README에는 `claude-sonnet-4-6`을 쓴다고 명시). 마찬가지로 `src/lib/anthropic.ts`의 기본 모델명 `claude-sonnet-4-6`도 실제 Anthropic이 제공하는 공식 모델명과 일치하는지 확인이 필요합니다.
- **어떤 피해가 생기나**: 주간 자동 점검 리포트 생성이 매번 "모델을 찾을 수 없음" 오류로 실패합니다. 더 심각하게는, 챗봇 본체(`src/lib/anthropic.ts`)의 모델명도 틀렸다면 **사용자가 메시지를 보내도 AI가 전혀 응답하지 못합니다**.
- **권장 조치**: Anthropic 공식 문서에서 현재 사용 가능한 정확한 모델명을 확인하여 두 파일 모두 수정하세요. 환경변수 `ANTHROPIC_MODEL`로 운영 중 모델을 바꿀 수 있게 되어 있으므로, 당장은 환경변수에 올바른 모델명을 넣어 긴급 대응할 수도 있습니다.

### 메모리 관리 코드가 두 벌로 중복되어 혼선 위험
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts` (거의 동일한 내용)
- **무슨 문제인가**: 사용자별 "장기 기억"을 다루는 코드가 `manna-memory.ts`와 `selah-memory.ts` 두 파일에 거의 똑같이 복사되어 있습니다. 실제 사용되는 것은 `manna-memory.ts`(chat API에서 import)이고 `selah-memory.ts`는 아무도 쓰지 않는 유령 파일로 보입니다.
- **어떤 피해가 생기나**: 당장 오류는 아니지만, 앞으로 한쪽만 수정하고 다른 쪽을 놓치면 버그가 생기기 쉽습니다. 또한 두 파일 모두 `user_memories`라는 같은 테이블을 쓰므로, 과거 SELAH 데이터와 MANNA 데이터가 섞일 소지가 있습니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하세요(단, 다른 곳에서 import하는지 전체 검색 후 제거).

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 속도 제한(rate limit)이 서버 재시작 시 초기화됨
- **파일 위치**: `src/lib/rate-limit.ts` 전체, `src/app/api/chat/route.ts` (71번째 줄 근처)
- **무슨 문제인가**: 한 사용자가 1분에 20번까지만 AI 요청을 보낼 수 있게 제한하는 기능이 있는데, 이 제한 기록이 서버 메모리에만 저장됩니다. Netlify 같은 환경은 요청마다 다른 서버가 처리할 수 있어(서버가 여러 개로 흩어짐), 제한이 느슨하게 적용됩니다. 코드 주석에도 이미 이 한계를 인정하고 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자가 여러 요청을 동시에 보내 AI 비용(후원금으로 운영되는 API 예산)을 빠르게 소진시킬 수 있습니다.
- **권장 조치**: 후원 예산 보호가 중요하므로, 장기적으로 Upstash Redis 같은 공용 저장소나 Supabase 카운터로 제한을 옮기는 것을 권장합니다. 사용자 수가 적은 현 단계에서는 우선순위가 높지 않습니다.

### 이미지가 데이터베이스에 저장되지 않아 복원 시 사라짐
- **파일 위치**: `src/components/chat/chat-app.tsx` (약 205번째 줄, `saveMessage`에 이미지 미포함)
- **무슨 문제인가**: 사용자가 사진을 첨부해 대화하면, 대화 당시에는 화면에 보이지만 나중에 그 대화를 다시 열면 사진은 사라지고 "[사진을 보냈어요]" 같은 글자만 남습니다. 이는 저장 용량을 아끼기 위한 의도된 설계지만, 사용자는 혼란스러울 수 있습니다.
- **어떤 피해가 생기나**: 사용자가 "내가 올린 사진이 왜 없어졌지?"라고 느낄 수 있습니다.
- **권장 조치**: 의도된 동작임을 안내 문구로 알리거나, 중요 이미지는 Supabase Storage에 저장하는 방안을 검토하세요.

### 중복된 홈 화면 추가 안내 컴포넌트
- **파일 위치**: `src/components/AddToHomePrompt.tsx` 와 `src/components/install-prompt.tsx`
- **무슨 문제인가**: 앱 설치(홈 화면 추가)를 유도하는 팝업 컴포넌트가 두 개 존재합니다. 실제로 `layout.tsx`에서는 `install-prompt.tsx`(InstallPrompt)만 쓰이고, `AddToHomePrompt.tsx`는 어디에서도 사용되지 않는 것으로 보입니다.
- **어떤 피해가 생기나**: 유지보수 시 어느 것이 진짜인지 헷갈립니다. 만약 둘 다 활성화되면 팝업이 두 번 뜰 수 있습니다.
- **권장 조치**: 사용되지 않는 `AddToHomePrompt.tsx`를 삭제하세요.

### cron(정기 알림) 발송 시 사용자별 순차 처리로 느려질 수 있음
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (약 150번째 줄 이후 반복문)
- **무슨 문제인가**: 알림을 보낼 때 사용자 한 명 한 명, 기기 하나 하나에 대해 `await`로 순서대로 발송합니다. 사용자가 많아지면 한 번의 cron 실행이 오래 걸려 시간 초과(타임아웃)될 수 있습니다.
- **어떤 피해가 생기나**: 사용자가 수백 명 이상 늘어나면 알림이 제시간에 안 가거나 일부 사용자가 누락될 수 있습니다.
- **권장 조치**: 현재 사용자 규모에서는 문제없으나, 성장 시 발송을 묶음(배치) 또는 병렬 처리로 개선하세요.

## 🟢 장기적으로 개선하면 좋은 점

### TypeScript에서 `any` 타입 과다 사용
- **파일 위치**: `src/app/api/chat/route.ts` (46번째 줄 `let supabase: any`), 다수의 API 라우트
- **무슨 문제인가**: 코드에서 데이터 형태를 느슨하게(`any`) 처리하는 부분이 많습니다. 이러면 컴파일러(코드 오류를 자동 검사하는 도구)가 실수를 미리 잡아주지 못합니다.
- **어떤 피해가 생기나**: 당장 문제는 없지만, 향후 리팩터링 시 숨은 버그가 늦게 발견될 수 있습니다.
- **권장 조치**: 점진적으로 명확한 타입으로 교체하세요.

### 자동 삭제 기능이 UI에서 설정 불가능해 보임
- **파일 위치**: `src/lib/auto-delete.ts`, `src/components/chat/chat-app.tsx` (약 95번째 줄)
- **무슨 문제인가**: 오래된 대화를 30일/90일 후 자동 삭제하는 로직은 구현되어 있으나, 사용자가 이 옵션을 켜고 끄는 설정 화면은 코드에서 찾을 수 없습니다. 기본값이 "사용 안 함"이라 기능이 실질적으로 잠들어 있습니다.
- **어떤 피해가 생기나**: 완성된 기능이 사용자에게 노출되지 않아 활용되지 못합니다.
- **권장 조치**: 설정 메뉴에 자동 삭제 토글을 추가하거나, 미완성이면 추후 완료하세요.

### PIN 잠금의 해시 방식이 매우 약함
- **파일 위치**: `src/components/chat/pin-gate.tsx` (약 40번째 줄 `fnv1a` 함수)
- **무슨 문제인가**: 화면 잠금용 4자리 PIN을 FNV-1a라는 단순 방식으로 암호화합니다. 이는 보안용 암호화가 아니라 단순 해시라, 기술적으로 뚫기 쉽습니다. 다만 코드 주석에서 "진짜 인증 대체가 아니라 가족 등 주변인의 눈을 가리는 프라이버시용"이라고 명확히 밝히고 있습니다.
- **어떤 피해가 생기나**: 이 PIN을 진짜 보안으로 오해하면 위험하지만, 목적이 명확하므로 심각도는 낮습니다.
- **권장 조치**: 현재 목적에는 충분하나, PIN 설정 UI가 존재한다면 사용자에게 "이것은 간단한 가림막일 뿐"임을 안내하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)** — ✅ 양호: chat API(`src/app/api/chat/route.ts`)와 모든 push/reminders API가 요청 시작 시 `supabase.auth.getUser()`로 로그인 여부를 확인하고, 미로그인은 401로 차단합니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: `0001_init.sql`에 모든 테이블이 "자기 데이터만 읽고 쓸 수 있는" 정책(Row Level Security)이 꼼꼼히 설정되어 있습니다.
- **API 키 관리** — ✅ 양호: Anthropic 키(`ANTHROPIC_API_KEY`)는 서버에서만 사용되고 클라이언트에 노출되지 않습니다. VAPID 비밀키도 서버 전용으로 분리되어 있습니다.
- **cron 엔드포인트 보호** — ✅ 양호: 정기 알림 발송 주소는 비밀 키(`CRON_SECRET`)를 헤더로만 받도록 하여, 주소 유출을 방지합니다(쿼리스트링 방식을 의도적으로 제거).
- **입력값 검증** — ⚠️ 주의: 이미지 크기 제한(7MB), 메시지 개수 제한(최근 16개), 리마인더 시간 형식 검증 등은 잘 되어 있으나, 채팅 텍스트 길이 자체에 대한 서버 측 상한이 없습니다. 비정상적으로 긴 텍스트로 비용을 늘릴 여지가 있습니다.
- **속도 제한** — ⚠️ 주의: 위에서 설명한 대로 서버 메모리 기반이라 분산 환경에서 느슨합니다.
- **SQL 인젝션** — ✅ 양호: Supabase 클라이언트 라이브러리를 통해서만 DB에 접근하므로 직접적인 SQL 주입 위험은 낮습니다.
- **보안 헤더** — ✅ 양호: `next.config.mjs`에 클릭재킹 방지, HTTPS 강제 등 기본 보안 헤더가 잘 설정되어 있습니다.
