## 🔴 즉시 해결이 필요한 문제

### 채팅 메시지 저장/조회가 작동하지 않는 테이블 이름 불일치
- **파일 위치**: `src/lib/chat-data.ts` (49번째 줄, 65번째 줄) vs `supabase/migrations/0001_init.sql` (메시지 테이블 정의 부분)
- **무슨 문제인가**: 데이터베이스에 메시지를 저장하는 실제 테이블 이름은 `messages`(데이터베이스의 실제 테이블)인데, 코드 일부는 `messages` 테이블을 사용하고(`chat-data.ts`), 화면을 그리는 다른 코드(`src/app/journey/page.tsx` 137~138번째 줄)는 `chat_messages`라는 **다른 이름의 테이블**을 조회하고 있습니다. 또한 같은 곳에서 `eq("user_id", ...)`로 조회하는데, 실제 `messages` 테이블에는 `user_id` 컬럼(데이터 항목)이 없고 `session_id`만 있습니다.
- **어떤 피해가 생기나**: "마음의 흐름"(journey) 페이지에서 사용자의 감정 변화 그래프가 **항상 비어 있게** 됩니다. 사용자는 며칠 동안 대화했는데도 "아직 기록된 대화가 충분하지 않아요"라는 안내만 계속 보게 되어, 핵심 기능 하나가 통째로 죽은 상태가 됩니다.
- **권장 조치**: `src/app/journey/page.tsx`의 `chat_messages` 조회 부분을 실제 테이블 구조(`messages` 테이블, `session_id` 기준)에 맞게 수정하거나, 데이터베이스에 `chat_messages` 뷰/테이블을 추가해 일치시켜야 합니다. 개발팀이 두 곳의 테이블 이름과 컬럼을 통일하는 작업이 필요합니다.

### 주간 점검 스크립트가 존재하지 않는 AI 모델을 호출
- **파일 위치**: `scripts/weekly-review.mjs` (callClaude 함수 내 `model: 'claude-opus-4-8'`)
- **무슨 문제인가**: 자동 코드 점검 리포트를 만드는 스크립트가 `claude-opus-4-8`이라는 모델 이름을 사용하는데, 이는 실제로 존재하지 않는 이름일 가능성이 매우 높습니다. (앱 본체는 `claude-sonnet-4-6`를 사용 중)
- **어떤 피해가 생기나**: 주간 자동 점검 리포트 생성이 API 오류(모델을 찾을 수 없음)로 실패하여, 운영진이 정기 점검 결과를 받지 못하게 됩니다.
- **권장 조치**: 실제 사용 가능한 모델 이름(예: 앱과 동일한 `claude-sonnet-4-6` 또는 검증된 Opus 모델명)으로 교체해야 합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 중복된 메모리 코드 파일 방치
- **파일 위치**: `src/lib/selah-memory.ts` 와 `src/lib/manna-memory.ts`
- **무슨 문제인가**: 두 파일이 거의 동일한 내용(장기 기억 처리 로직)을 가지고 있습니다. 실제로 앱이 사용하는 것은 `manna-memory.ts` 하나뿐이고(`prompt.ts`와 `chat/route.ts`에서 import), `selah-memory.ts`는 어디에서도 사용되지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 당장의 오류는 없지만, 향후 메모리 로직을 수정할 때 어느 파일을 고쳐야 하는지 혼란이 생기고, 실수로 사용되지 않는 파일만 고치면 변경이 반영되지 않는 함정이 됩니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts` 파일을 삭제하세요.

### 사용되지 않는 컴포넌트 파일 방치
- **파일 위치**: `src/components/AddToHomePrompt.tsx`
- **무슨 문제인가**: 홈 화면 추가를 유도하는 컴포넌트인데, 실제로 앱에서 쓰이는 것은 `src/components/install-prompt.tsx`입니다. `AddToHomePrompt.tsx`는 어디에서도 불러오지 않는 미사용 파일로 보입니다.
- **어떤 피해가 생기나**: 코드베이스가 불필요하게 비대해지고, 두 개의 비슷한 "설치 안내" 컴포넌트 중 어느 것이 진짜인지 혼란을 줍니다.
- **권장 조치**: 미사용 여부를 확인 후 삭제하세요.

### 리마인더 발송 시 다중 행 업데이트 문제 소지
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (last_sent_at 업데이트 부분)
- **무슨 문제인가**: 리마인더 발송 후 `last_sent_at`을 업데이트할 때 `.eq("user_id", r.user_id)`로 조건을 거는데, 같은 사용자가 여러 알림 행을 가질 경우(현재 스키마상 user_id가 기본키라 1행이지만) 또는 향후 스키마 변경 시 의도치 않은 행이 갱신될 수 있습니다. 현재 스키마(user_id가 PRIMARY KEY)에서는 안전하나, 코드가 스키마 가정에 강하게 묶여 있습니다.
- **어떤 피해가 생기나**: 현재는 문제없지만, 향후 한 사용자가 여러 알림을 설정할 수 있도록 기능을 확장하면 중복 발송 방지(dedupe) 로직이 깨질 수 있습니다.
- **권장 조치**: 향후 다중 알림 기능을 계획한다면 알림 행의 고유 ID 기준으로 갱신하도록 미리 설계해두세요.

### 인메모리 방식의 요청 제한(rate limit)은 분산 환경에서 부정확
- **파일 위치**: `src/lib/rate-limit.ts` 및 `src/app/api/chat/route.ts` (rateLimit 호출 부분)
- **무슨 문제인가**: 사용자별 요청 횟수 제한이 서버 메모리에만 저장됩니다. Netlify 같은 서버리스 환경에서는 요청마다 다른 인스턴스(서버 복사본)로 갈 수 있어, 제한이 의도대로 작동하지 않을 수 있습니다. (코드 주석에도 이미 인지하고 있다고 명시됨)
- **어떤 피해가 생기나**: 악의적 사용자가 분산된 요청으로 1분에 20회 제한을 우회하여 AI API 비용(후원금으로 운영)을 과도하게 소모시킬 수 있습니다.
- **권장 조치**: 트래픽이 늘어나기 전에 Redis(예: Upstash) 같은 공유 저장소 기반 제한으로 전환을 검토하세요. 출시 초기에는 우선순위가 낮습니다.

### 이미지가 첨부된 메시지는 서버 인증 체크는 거치나 본문 비검증
- **파일 위치**: `src/app/api/chat/route.ts` (image 검증 부분)
- **무슨 문제인가**: 이미지 크기는 검증(최대 7백만 자)하지만, 클라이언트가 보낸 `messages` 배열 안의 각 항목의 형식(role이 올바른지 등)에 대한 엄격한 검증은 다소 느슨합니다. 코드가 방어적으로 잘 짜여 있어 큰 문제로 이어지진 않으나, 입력값 신뢰가 일부 클라이언트에 의존합니다.
- **어떤 피해가 생기나**: 변조된 클라이언트가 비정상적인 데이터를 보내면 예외 처리는 되지만, 입력 검증을 강화하면 더 안전합니다.
- **권장 조치**: messages 배열 항목의 role/content 타입을 명시적으로 검증하는 코드를 추가하면 좋습니다.

## 🟢 장기적으로 개선하면 좋은 점

### `any` 타입 광범위 사용
- **파일 위치**: `src/app/api/chat/route.ts` (`let supabase: any`), 여러 API 라우트의 `body: any` 등
- **무슨 문제인가**: 코드 곳곳에서 타입을 `any`(아무 타입이나 허용)로 지정해 TypeScript의 타입 안전성 이점을 일부 포기하고 있습니다.
- **어떤 피해가 생기나**: 당장은 문제없지만, 향후 데이터 구조가 바뀌었을 때 컴파일러가 오류를 미리 잡아주지 못해 버그가 운영 중에 발견될 위험이 있습니다.
- **권장 조치**: 시간이 날 때 점진적으로 명시적 타입으로 교체하세요. 우선순위는 낮습니다.

### 다국어 기능 문자열(feature-strings)의 제한적 번역
- **파일 위치**: `src/lib/feature-strings.ts`
- **무슨 문제인가**: 앱은 30개 언어를 지원한다고 표방하지만, 일부 기능 문자열(알림, 위기 안내 등)은 한국어/영어만 번역되어 있고 나머지 언어는 영어로 대체(fallback)됩니다.
- **어떤 피해가 생기나**: 영어를 모르는 비영어권 사용자가 위기 안내 카드나 리마인더 설정 화면에서 영어 안내를 보게 되어, 가장 도움이 필요한 순간에 이해하지 못할 수 있습니다.
- **권장 조치**: 위기 안내(crisis) 관련 문자열만이라도 주요 지원 언어로 우선 번역하는 것을 권장합니다.

### 위기 상황 핫라인이 한국·미국 중심
- **파일 위치**: `src/lib/feature-strings.ts` (hotlinesFor 함수)
- **무슨 문제인가**: 위기 상담 전화번호가 한국어는 한국 번호, 그 외 모든 언어는 미국 번호(988, 911)로 제공됩니다.
- **어떤 피해가 생기나**: 태국, 인도, 브라질 등 다른 국가 사용자가 위기 상황에서 자국에서 통하지 않는 미국 번호를 안내받게 됩니다.
- **권장 조치**: 주요 지원 국가별 핫라인 번호를 추가하세요. (글로벌 헬프라인 링크는 이미 fallback에 포함되어 있으나, 국가별 번호가 더 효과적입니다.)

## 🔒 보안 점검 결과

- **인증(로그인 검증)**: ✅ 양호 — `/api/chat`, `/api/reminders`, `/api/push/*` 등 모든 보호 대상 API가 요청 처리 전 `supabase.auth.getUser()`로 로그인 여부를 확인합니다. 미들웨어(`middleware.ts`)에서도 `/chat` 경로를 추가로 보호합니다.
- **API 키 관리**: ✅ 양호 — Anthropic API 키(`ANTHROPIC_API_KEY`)는 서버에서만 사용되며 클라이언트에 노출되지 않습니다. Supabase 공개 키(anon key)와 VAPID 공개 키만 클라이언트에 노출되며, 이는 설계상 안전합니다.
- **데이터베이스 접근 제어(RLS)**: ✅ 양호 — 모든 테이블에 Row Level Security가 활성화되어 있고, 사용자가 자신의 데이터만 읽고 쓸 수 있도록 정책이 잘 설정되어 있습니다.
- **크론(Cron) 엔드포인트 보호**: ✅ 양호 — `/api/cron/send-reminders`가 비밀 키(`CRON_SECRET`)를 헤더로만 받도록 하여 URL 노출 위험을 막았습니다. 좋은 설계입니다.
- **보안 헤더**: ✅ 양호 — 클릭재킹 방지(X-Frame-Options), HTTPS 강제(HSTS), MIME 스니핑 방지 등 기본 보안 헤더가 잘 설정되어 있습니다.
- **입력값 검증**: ⚠️ 주의 — 이미지 크기, 타임존, 시간 형식 등 일부는 검증하나, 메시지 배열 항목의 엄격한 타입 검증은 다소 느슨합니다.
- **SQL 인젝션**: ✅ 양호 — Supabase 클라이언트 라이브러리(쿼리 빌더)를 사용하므로 직접 SQL 문자열 조합이 없어 인젝션 위험이 낮습니다.
- **요청 폭주(DoS) 방어**: ⚠️ 주의 — 사용자별 요청 제한이 있으나 인메모리 방식이라 서버리스 환경에서 우회 가능성이 있습니다.
- **개인정보 처리**: ✅ 양호 — 개인정보처리방침·이용약관이 충실하게 작성되어 있고, 클라이언트 PIN 잠금 등 추가 프라이버시 기능도 제공됩니다.
