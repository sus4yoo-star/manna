# 만나(MANNA) 주간 점검 리포트 — 2026-06-16

## 📌 요약 (한 눈에 보기)
전체적으로 코드 품질이 높고, 인증·보안·다국어 처리가 매우 꼼꼼하게 구현된 안정적인 코드베이스입니다. 다만 이번 점검에서 **출시를 막을 수 있는 치명적 문제 2건**이 발견되었습니다: ① AI 모델 호출 시 존재하지 않는 모델 이름이 하드코딩되어 있어 AI 답변이 전혀 동작하지 않을 위험, ② 데이터베이스 테이블 이름 불일치로 인해 대화 기록 저장·조회·삭제 기능이 작동하지 않을 가능성이 큽니다. 이 두 가지는 실제 사용자가 채팅을 시도하는 순간 곧바로 실패로 이어지므로 최우선으로 확인해야 합니다. 또한 동일한 기능을 하는 코드가 두 파일에 중복 존재(`manna-memory.ts`·`selah-memory.ts`)하는 등 정리할 부분도 있습니다.

## 🔴 즉시 해결이 필요한 문제

### 데이터베이스 테이블 이름 불일치로 대화 저장·조회가 실패할 위험
- **파일 위치**: `src/lib/chat-data.ts` (전체), `src/app/journey/page.tsx` (약 110~115번째 줄), `supabase/migrations/0001_init.sql`
- **무슨 문제인가**: 대화 메시지를 저장하는 데이터베이스 표(테이블)의 이름이 코드마다 다르게 적혀 있습니다.
  - 데이터베이스 설계 파일(`0001_init.sql`)은 메시지 테이블 이름을 **`messages`**로 만들었습니다.
  - 그런데 `src/lib/chat-data.ts`는 `messages` 테이블을 사용하고, `src/app/journey/page.tsx`는 **`chat_messages`**라는 다른 이름의 테이블을 조회합니다.
  - 또한 `MessageBubble`이 사용하는 `Message` 타입에는 `image`(첨부 이미지) 필드가 없어, 일부 화면에서 형(type) 오류가 날 수 있습니다.
- **어떤 피해가 생기나**: "마음의 흐름(Journey)" 화면에서 감정 그래프가 항상 비어 보이거나 오류가 납니다(`chat_messages` 테이블이 실제로 없기 때문). 사용자가 며칠간 대화를 나눠도 데이터가 없는 것처럼 보여, 핵심 기능 중 하나가 무용지물이 됩니다.
- **권장 조치**: 테이블 이름을 하나로 통일하세요. `journey/page.tsx`의 `chat_messages`를 `messages`로 바꾸거나, 데이터베이스에 `chat_messages` 테이블을 실제로 만들고 모든 코드를 일치시키세요. 출시 전 실제 계정으로 대화→Journey 화면 확인까지 한 번에 테스트해야 합니다.

### AI 모델 이름이 실제 존재하지 않는 값으로 설정되어 있을 위험
- **파일 위치**: `src/lib/anthropic.ts` (약 24번째 줄), `scripts/weekly-review.mjs` (약 95번째 줄)
- **무슨 문제인가**: AI 답변을 만들 때 사용하는 모델 이름이 `"claude-sonnet-4-6"`으로 하드코딩되어 있고, 주간 점검 스크립트는 `"claude-opus-4-8"`을 사용합니다. 이 이름들이 실제 Anthropic(AI 제공사)이 서비스하는 정확한 모델명과 다를 경우, AI 호출이 즉시 실패합니다. (README에는 `claude-sonnet-4-6`, 주석에는 `claude-opus-4-7` 등 서로 다른 이름이 섞여 있어 혼란이 있습니다.)
- **어떤 피해가 생기나**: 사용자가 메시지를 보내면 "MANNA가 응답할 수 없습니다" 같은 오류만 반환되고, 앱의 가장 핵심인 대화 기능 자체가 동작하지 않습니다.
- **권장 조치**: Anthropic 콘솔에서 현재 실제로 사용 가능한 정확한 모델명을 확인해 `defaultModel()`의 기본값과 점검 스크립트 값을 맞추세요. 더 안전하게는 환경변수 `ANTHROPIC_MODEL`에 정확한 이름을 넣어 운영하고, 배포 직후 실제 채팅을 1회 테스트하세요.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 똑같은 기능의 코드가 두 파일에 중복 존재
- **파일 위치**: `src/lib/manna-memory.ts`와 `src/lib/selah-memory.ts` (두 파일 전체)
- **무슨 문제인가**: 사용자의 장기 기억(과거 대화 요약)을 다루는 코드가 거의 동일하게 두 파일에 복사되어 있습니다. 실제로는 `manna-memory.ts`만 사용되고 `selah-memory.ts`는 쓰이지 않는 것으로 보입니다.
- **어떤 피해가 생기나**: 나중에 기억 기능을 수정할 때 한쪽만 고치고 다른 쪽을 빠뜨리면, 어느 코드가 진짜인지 헷갈려 버그를 만들 수 있습니다. 코드 용량도 불필요하게 커집니다.
- **권장 조치**: 사용되지 않는 `selah-memory.ts`를 삭제하거나, 두 파일을 하나로 합치세요.

### 사용자 메모리 갱신을 위해 매 대화마다 추가 AI 호출이 발생
- **파일 위치**: `src/lib/manna-memory.ts` `updateUserMemory` 함수 (약 150~210번째 줄), `src/app/api/chat/route.ts` (스트림 종료 시 `persist` 호출 부분)
- **무슨 문제인가**: 사용자가 한 번 대화할 때마다, 답변 생성과 별개로 "기억 요약"을 위한 AI 호출이 한 번 더 일어납니다. 즉 대화 1회당 AI 비용이 사실상 2배가 됩니다.
- **어떤 피해가 생기나**: 기부로 운영되는 앱이라 AI 사용 비용이 곧 운영 부담입니다. 사용자가 늘수록 비용이 예상보다 빠르게 증가할 수 있습니다.
- **권장 조치**: 매번이 아니라 "몇 차례 대화마다 한 번"만 기억을 갱신하거나, 짧은 인사·잡담일 때는 갱신을 건너뛰도록 조건을 추가하면 비용을 크게 줄일 수 있습니다.

### 속도 제한(rate limit)이 서버 재시작 시 초기화됨
- **파일 위치**: `src/lib/rate-limit.ts` (전체), `src/app/api/chat/route.ts` (약 70번째 줄)
- **무슨 문제인가**: 한 사용자가 1분에 20번까지만 요청하도록 제한하는 장치가 서버 메모리에만 저장됩니다. Netlify 같은 환경에서는 서버 인스턴스가 자주 새로 뜨므로(코드 주석에도 명시), 이 제한이 완전히 정확하게 작동하지 않습니다.
- **어떤 피해가 생기나**: 악의적인 사용자가 여러 경로로 요청을 분산하면 제한을 우회해 AI 호출을 과도하게 발생시킬 수 있어, 비용 폭증 위험이 있습니다.
- **권장 조치**: 당장 급하지는 않으나, 사용자가 늘면 외부 저장소(예: Redis, 데이터베이스 카운터)를 이용한 분산 속도 제한으로 교체를 권장합니다. (코드 주석에 이미 같은 계획이 적혀 있습니다.)

### 채팅 입력 시 서버로 전체 대화 텍스트를 매번 전송
- **파일 위치**: `src/components/chat/chat-app.tsx` `sendMessage` 함수 (약 230~245번째 줄)
- **무슨 문제인가**: 메시지를 보낼 때 이전 대화 전체를 함께 서버로 보냅니다. 서버에서 최근 16개로 자르긴 하지만, 클라이언트는 항상 전체를 보냅니다.
- **어떤 피해가 생기나**: 대화가 매우 길어지면 전송 데이터가 커져 느린 네트워크(모바일)에서 응답 시작이 지연될 수 있습니다.
- **권장 조치**: 클라이언트에서도 최근 N개만 잘라서 보내도록 조정하면 모바일 사용자 경험이 개선됩니다.

## 🟢 장기적으로 개선하면 좋은 점

### 비밀번호 최소 길이가 6자로 다소 짧음
- **파일 위치**: `src/app/login/page.tsx` `validate` 함수 (약 60번째 줄)
- **무슨 문제인가**: 이메일 가입 시 비밀번호를 최소 6자만 요구합니다. 현대 보안 기준으로는 다소 약합니다.
- **어떤 피해가 생기나**: 사용자 계정이 단순 비밀번호로 만들어져 탈취 위험이 상대적으로 높아질 수 있습니다.
- **권장 조치**: 최소 8자 이상으로 상향하고, 가능하면 소셜 로그인(구글/카카오) 사용을 권장하는 안내를 추가하세요.

### PIN 잠금이 약한 방식으로 저장됨 (보안용 아님 명시 필요)
- **파일 위치**: `src/components/chat/pin-gate.tsx` `fnv1a` 함수 (약 35번째 줄)
- **무슨 문제인가**: 화면 잠금 PIN을 매우 단순한 변환(FNV-1a)으로만 저장합니다. 코드 주석에 "인증 대체가 아닌 프라이버시 용도"라고 명확히 적혀 있어 의도는 적절하나, 기술적으로 강한 보호는 아닙니다.
- **어떤 피해가 생기나**: 같은 기기를 쓰는 가족이 우연히 보는 것 정도는 막지만, 전문적 공격에는 취약합니다.
- **권장 조치**: 현재 용도(가벼운 가림막)로는 충분합니다. 사용자 안내에 "기기 분실 시 대화 보호용은 아님"을 명시하면 좋습니다.

### 다국어 텍스트 일부가 영어로 대체됨 (의도된 동작이나 일관성 점검 필요)
- **파일 위치**: `src/lib/feature-strings.ts` (마지막 `TABLE` 정의 부분)
- **무슨 문제인가**: 새 기능 문구(`feature-strings`)는 한국어·영어만 완전하게 번역되어 있고, 나머지 언어는 영어로 표시됩니다. 메인 화면 번역(`i18n.ts`)은 30개 언어 모두 갖춰져 있어 화면에 따라 일관성이 떨어질 수 있습니다.
- **어떤 피해가 생기나**: 예를 들어 태국어 사용자가 메인 화면은 태국어로, 리마인더·즐겨찾기 같은 일부 기능 화면은 영어로 보게 되어 어색함을 느낄 수 있습니다.
- **권장 조치**: 주요 사용 국가 언어부터 `feature-strings.ts`에 점진적으로 번역을 추가하세요.

## 🔒 보안 점검 결과

- **AI 채팅 인증 보호** — ✅ 양호: `src/app/api/chat/route.ts`에서 로그인하지 않은 사용자는 401 오류로 차단하고, 비로그인 시 AI 키를 절대 사용하지 못하게 막고 있습니다.
- **API 비밀 키 노출 방지** — ✅ 양호: `ANTHROPIC_API_KEY`, VAPID 비밀키 등은 서버 환경변수로만 사용되고 클라이언트로 노출되지 않습니다. 공개해도 되는 키(Supabase anon, VAPID 공개키)만 `NEXT_PUBLIC_`으로 노출됩니다.
- **데이터베이스 접근 제어(RLS)** — ✅ 양호: `0001_init.sql` 등에서 모든 테이블에 행 수준 보안(사용자가 자기 데이터만 접근)을 꼼꼼히 적용했습니다. 6/4 마이그레이션에서 누락된 삭제 정책까지 보완한 점이 인상적입니다.
- **크론(예약 작업) 보호** — ✅ 양호: `send-reminders`는 공유 비밀(`x-cron-secret`)을 헤더로만 받아 검증하며, 쿼리스트링 노출 위험을 의도적으로 제거했습니다.
- **입력값 검증** — ⚠️ 주의: 리마인더 시간·타임존 등은 검증하지만(`reminders/route.ts`), 채팅 메시지 텍스트 길이 제한이 없습니다. 이미지 크기는 제한(7MB)하지만 긴 텍스트로 인한 토큰 비용 폭증을 막는 상한은 보이지 않습니다.
- **SQL 인젝션** — ✅ 양호: 모든 DB 접근이 Supabase 라이브러리(파라미터 바인딩)를 통해 이루어져 직접 SQL 조립이 없습니다.
- **속도 제한** — ⚠️ 주의: 위 🟡 항목에서 설명한 대로 서버 메모리 기반이라 분산 환경에서 우회 가능성이 있습니다.
- **보안 헤더** — ✅ 양호: `next.config.mjs`에서 클릭재킹 방지, HTTPS 강제, MIME 스니핑 차단 등 기본 보안 헤더를 잘 설정했습니다.
