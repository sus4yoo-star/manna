# 만나(MANNA) 주간 점검 리포트 — 2026-06-04

## 📌 요약 (한 눈에 보기)
전체적으로 코드는 잘 정리되어 있고 인증·데이터 접근 제어(누가 어떤 데이터를 볼 수 있는지 막는 장치)는 견고하게 구현되어 있습니다. 다만 **출시 전 반드시 삭제해야 할 위험한 디버그(개발자 진단) 페이지가 살아있고**, **AI 모델 이름이 잘못 설정되어 채팅이 완전히 작동하지 않을 가능성**이 있습니다. 또한 채팅 기록을 저장하는 핵심 코드와 실제 데이터베이스 테이블 이름이 어긋나 있어, 대화 내용이 저장·복원되지 않는 심각한 버그가 의심됩니다. 이 세 가지가 이번 주 가장 중요한 발견입니다.

## 🔴 즉시 해결이 필요한 문제

### 1. 채팅 저장/불러오기 코드와 실제 DB 테이블 이름이 어긋남 (대화가 저장 안 될 가능성)
- **파일 위치**: `src/lib/chat-data.ts` (45번째 줄 `from("messages")`, 62번째 줄 `from("messages")`) vs `src/app/journey/page.tsx` (108번째 줄 `from("chat_messages")`)
- **무슨 문제인가**: 데이터베이스(데이터 보관 창고)에는 메시지를 저장하는 테이블 이름이 `messages`로 만들어져 있습니다(`supabase/migrations/0001_init.sql` 확인). 그런데 마음의 흐름(journey) 페이지에서는 `chat_messages`라는 **존재하지 않는 이름**으로 데이터를 읽으려 합니다. 또한 `messages` 테이블에는 `user_id`(사용자 식별값) 컬럼이 없는데, journey 페이지는 `eq("user_id", ...)`로 조회를 시도합니다.
- **어떤 피해가 생기나**: 사용자가 "마음의 흐름" 그래프를 열면 데이터가 전혀 나오지 않거나 오류가 발생합니다. 사용자는 며칠간 대화했는데도 "아직 기록이 충분하지 않다"는 빈 화면만 보게 됩니다. 핵심 기능 하나가 사실상 죽어 있는 상태입니다.
- **권장 조치**: journey 페이지의 `chat_messages`를 `messages`로 통일하고, `user_id`로 직접 거르는 대신 사용자의 세션(chat_sessions)을 먼저 조회한 뒤 그 세션들에 속한 메시지를 가져오도록 수정해야 합니다. 개발팀이 실제 테이블 구조를 다시 확인하는 것이 우선입니다.

### 2. AI 모델 이름이 존재하지 않는 값으로 보임 (채팅 응답 실패 위험)
- **파일 위치**: `src/lib/anthropic.ts` (24번째 줄 `claude-sonnet-4-6`), `scripts/weekly-review.mjs` (110번째 줄 `claude-opus-4-8`)
- **무슨 문제인가**: AI 회사(Anthropic)에 요청을 보낼 때 사용하는 모델(AI 두뇌) 이름이 `claude-sonnet-4-6`, `claude-opus-4-8` 등으로 적혀 있습니다. 이는 실제로 존재하지 않는 이름일 가능성이 매우 높습니다. 프롬프트 안내문에도 `claude-opus-4-7` 같은 표기가 섞여 있어 일관성이 없습니다.
- **어떤 피해가 생기나**: 모델 이름이 틀리면 AI가 응답 요청을 거부하여, 사용자가 메시지를 보내도 "잠시 문제가 생겼어요" 같은 오류만 반복적으로 나타납니다. 즉 앱의 가장 핵심 기능인 대화 자체가 작동하지 않을 수 있습니다.
- **권장 조치**: Anthropic 공식 문서에서 현재 유효한 모델 이름을 확인하여 정확한 값으로 교체하고, 운영 환경에서 실제로 한 번 응답이 오는지 반드시 테스트해야 합니다.

### 3. 누구나 접속 가능한 디버그(진단) 페이지가 살아있음 — 보안 위험
- **파일 위치**: `src/app/debug/page.tsx`, `src/app/debug/client.tsx`
- **무슨 문제인가**: `/debug` 주소로 접속하면 누구나 서버의 Supabase 설정 정보 일부(주소, 인증키 앞 20자리), 세션 상태, 그리고 **이메일/비밀번호 직접 로그인 테스트 입력창**까지 볼 수 있습니다. 코드 주석에도 "출시 전 삭제하라(DELETE before production)"고 명시되어 있습니다. 또한 `src/middleware.ts`의 보호 설정에서 `debug` 경로를 일부러 제외해 두어 접근이 더 열려 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자가 이 페이지에서 시스템 설정 정보를 엿보거나, 무차별 로그인 시도(여러 비밀번호를 반복 입력해 뚫는 공격)에 악용할 수 있습니다. 인증키 일부 노출만으로 즉각적인 침해가 일어나진 않지만, 운영 서비스에 진단용 도구를 노출하는 것은 명백한 보안 결함입니다.
- **권장 조치**: 출시 전에 `src/app/debug/` 폴더 전체를 삭제하거나, 최소한 미들웨어에서 차단하고 운영자만 접근 가능하도록 막아야 합니다.

### 4. 동일한 기능의 메모리 코드가 두 개로 중복되어 혼란 위험
- **파일 위치**: `src/lib/manna-memory.ts` 와 `src/lib/selah-memory.ts`
- **무슨 문제인가**: 사용자의 장기 대화 기억을 다루는 코드가 거의 동일하게 두 파일로 존재합니다. 실제 채팅 API(`src/app/api/chat/route.ts`)는 `manna-memory`만 사용하고 `selah-memory`는 아무 곳에서도 쓰이지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 향후 개발자가 어느 파일을 고쳐야 할지 헷갈려 잘못된 파일을 수정하면, 고쳤다고 생각한 버그가 그대로 남습니다. 유지보수 비용과 실수 가능성이 커집니다.
- **권장 조치**: 사용되지 않는 `src/lib/selah-memory.ts`를 삭제하여 코드를 하나로 정리해야 합니다.

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 1. 리마인더(알림) 발송 시 마지막 발송 시각 기록이 잘못 갱신됨
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (약 155~160번째 줄, `last_sent_at` 업데이트 부분)
- **무슨 문제인가**: 알림을 보낸 뒤 "오늘 보냈음" 표시(`last_sent_at`)를 갱신할 때 `update`로 처리하는데, 만약 해당 사용자의 리마인더 행(row)이 어떤 이유로 비어있으면 갱신이 실패할 수 있습니다. 또한 알림 발송과 기록 갱신 사이에 짧은 시간차가 있어, 드물게 같은 알림이 중복 발송될 가능성이 있습니다.
- **어떤 피해가 생기나**: 사용자가 하루에 같은 알림을 두 번 받아 거슬리거나, 반대로 갱신 실패 시 발송이 누락될 수 있습니다. 빈도는 낮지만 사용자 불만으로 이어질 수 있습니다.
- **권장 조치**: 발송 직전에 먼저 `last_sent_at`을 갱신하고 발송하거나, 데이터베이스에서 중복을 원천 차단하는 안전장치를 추가하는 것이 좋습니다.

### 2. 채팅 API에서 메모리 업데이트가 응답마다 추가 AI 호출을 발생시킴 (비용·속도)
- **파일 위치**: `src/app/api/chat/route.ts` (`persist` 함수 → `updateUserMemory` 호출), `src/lib/manna-memory.ts` (`updateUserMemory`)
- **무슨 문제인가**: 사용자가 메시지를 보내 답변을 받을 때마다, 백그라운드에서 AI를 한 번 더 호출하여 "장기 기억"을 갱신합니다. 즉 대화 1회당 AI 요청이 2회 발생합니다.
- **어떤 피해가 생기나**: AI 사용 비용이 약 2배로 늘어나고, 사용량이 많아지면 운영비 부담이 커집니다. 무료·후원 기반 서비스에서는 비용 관리가 중요합니다.
- **권장 조치**: 매번이 아니라 일정 대화 횟수마다 한 번씩, 또는 의미 있는 대화일 때만 메모리를 갱신하도록 빈도를 조절하는 것을 검토하세요.

### 3. 입력 메시지 길이·이미지 용량에 대한 서버 측 제한 부족
- **파일 위치**: `src/app/api/chat/route.ts` (요청 본문 `body` 처리 부분)
- **무슨 문제인가**: 클라이언트(사용자 화면)에서는 이미지 크기를 줄이지만(`src/components/chat/chat-input.tsx`), 서버는 들어오는 텍스트 길이나 메시지 개수에 대한 엄격한 상한을 두지 않습니다(메시지는 최근 16개로 자르지만 각 메시지의 길이는 무제한).
- **어떤 피해가 생기나**: 악의적 사용자가 매우 긴 텍스트를 반복 전송하면 AI 비용 폭증이나 서버 부하로 이어질 수 있습니다.
- **권장 조치**: 서버에서 각 메시지의 최대 글자 수를 제한하는 검증 코드를 추가하세요.

### 4. 빌드 시 타입·문법 검사를 모두 건너뜀
- **파일 위치**: `next.config.mjs` (`eslint: { ignoreDuringBuilds: true }`, `typescript: { ignoreBuildErrors: true }`)
- **무슨 문제인가**: 코드를 배포용으로 만들 때 타입 오류(데이터 형식 불일치 같은 잠재 버그를 잡아주는 검사)와 문법 검사를 모두 무시하도록 설정되어 있습니다. 위 🔴 1번의 테이블 이름 불일치 같은 문제가 빌드 단계에서 걸러지지 못한 이유 중 하나입니다.
- **어떤 피해가 생기나**: 명백한 버그가 검사 없이 그대로 배포되어, 사용자가 직접 마주칠 때까지 발견되지 않습니다.
- **권장 조치**: 최소한 타입 검사라도 켜고, 발견되는 오류를 점진적으로 정리하는 것을 권장합니다.

## 🟢 장기적으로 개선하면 좋은 점

### 1. 즐겨찾기·PIN 잠금 등이 브라우저에만 저장됨
- **파일 위치**: `src/lib/favorites.ts`, `src/components/chat/pin-gate.tsx`
- **무슨 문제인가**: 즐겨찾기한 글과 PIN 비밀번호가 기기 브라우저 저장소(localStorage)에만 보관됩니다. 다른 기기에서는 보이지 않고, 브라우저 데이터를 지우면 사라집니다. PIN 또한 가벼운 방식(FNV-1a)으로 처리되어 강력한 보안은 아닙니다(코드 주석에도 "인증을 대체하지 않는다"고 명시).
- **어떤 피해가 생기나**: 사용자가 폰을 바꾸거나 캐시를 지우면 즐겨찾기가 모두 사라져 실망할 수 있습니다. PIN은 가벼운 사생활 보호용일 뿐 보안 기능으로 오해되면 안 됩니다.
- **권장 조치**: 장기적으로 즐겨찾기를 서버(DB)에 저장하는 방안을 검토하고, PIN은 어디까지나 "사생활 가림막"임을 사용자에게 명확히 안내하세요.

### 2. 채팅 본문 코드에 영어 오류 메시지가 하드코딩됨
- **파일 위치**: `src/components/chat/chat-app.tsx` (예: "MANNA could not respond. Please try again.", "The connection is unstable for a moment.")
- **무슨 문제인가**: 30개 언어를 지원하는 앱인데, 일부 오류 메시지가 영어로 코드에 직접 박혀 있어 한국어·기타 언어 사용자에게 영어로 표시됩니다.
- **어떤 피해가 생기나**: 한국어 사용자가 갑자기 영어 오류 문구를 보면 혼란스럽고 완성도가 떨어져 보입니다.
- **권장 조치**: 이 메시지들도 다국어 번역 시스템(i18n)에 포함하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)**: ✅ 양호 — 채팅 API, 알림 API 모두 `getUser()`로 로그인 여부를 확인하고, 미인증 시 401(접근 거부)을 반환합니다.
- **데이터베이스 접근 제어 (RLS)**: ✅ 양호 — 모든 핵심 테이블에 행 수준 보안(사용자가 자기 데이터만 보도록 막는 장치)이 꼼꼼히 설정되어 있습니다.
- **비밀 키 관리**: ✅ 양호 — AI API 키, 서비스 역할 키, VAPID 비공개 키 모두 서버 환경변수로만 사용되고 클라이언트에 노출되지 않습니다.
- **크론(자동 작업) 엔드포인트 보호**: ✅ 양호 — 알림 발송 작업은 비밀 토큰(`CRON_SECRET`)으로 보호되어 외부 무단 호출을 차단합니다.
- **디버그 페이지 노출**: ❌ 위험 — `/debug` 페이지가 운영 환경에서 접근 가능하며 설정 정보 일부와 로그인 테스트 폼을 노출합니다 (🔴 3번 참조).
- **입력값 검증**: ⚠️ 주의 — 알림 시간/타임존 등은 검증하지만, 채팅 메시지 길이에 대한 서버 상한이 없습니다 (🟡 3번 참조).
- **SQL 인젝션**: ✅ 양호 — Supabase 클라이언트를 통한 안전한 쿼리만 사용하여 직접적인 SQL 인젝션 위험은 보이지 않습니다.
