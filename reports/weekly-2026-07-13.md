# 만나(MANNA) 주간 점검 리포트 — 2026-07-13

## 📌 요약 (한 눈에 보기)
전체적으로 안정적이고 성숙한 코드베이스입니다. 인증(로그인 검증), 사용자별 데이터 격리(Postgres RLS), API 키 보호가 잘 갖춰져 있으며, 보안 헤더와 크라이시스(위기) 감지 기능도 신중하게 설계되어 있습니다. 다만 **가장 중요한 문제는 채팅 데이터가 실제 데이터베이스 테이블과 어긋나 있다는 점**입니다. 코드는 `messages` 테이블을 쓰는데 일부 페이지는 존재하지 않는 `chat_messages` 테이블을 조회하고 있어, "마음의 흐름" 기능이 항상 빈 화면을 보여줄 가능성이 높습니다. 또한 자동 점검 스크립트에 존재하지 않는 AI 모델 이름이 하드코딩되어 있어 리포트 생성이 실패할 수 있습니다. 이 두 가지를 최우선으로 확인하시길 권장합니다.

## 🔴 즉시 해결이 필요한 문제

### 채팅 메시지 조회 테이블 이름 불일치 — "마음의 흐름" 기능이 항상 비어 보임
- **파일 위치**: `src/app/journey/page.tsx` (약 120~127번째 줄), `src/lib/chat-data.ts` (전체), `supabase/migrations/0001_init.sql`
- **무슨 문제인가**: 데이터베이스에 실제로 만들어진 대화 저장소 테이블 이름은 `messages`(메시지)입니다. 그런데 "마음의 흐름"(감정 여정) 페이지는 `chat_messages`라는 다른 이름의 테이블을 조회하고 있고, 세션도 `chat_sessions`를 조회합니다. `chat_sessions`는 존재하지만 `chat_messages`는 데이터베이스 정의에 없습니다. 반면 실제 저장 로직(`chat-data.ts`)은 `messages` 테이블에 저장합니다. 즉, **저장하는 곳과 읽는 곳의 이름이 다릅니다.**
- **어떤 피해가 생기나**: 사용자가 아무리 대화를 많이 나눠도 "마음의 흐름" 페이지는 항상 "아직 기록된 대화가 충분하지 않아요"라는 빈 화면만 보여줄 수 있습니다. 감정 그래프, 공유 카드 등 이 페이지의 모든 기능이 사실상 동작하지 않게 됩니다.
- **권장 조치**: `journey/page.tsx`의 `chat_messages`를 `messages`로 바꾸거나, 데이터베이스에 `chat_messages` 테이블을 별도로 만들어야 합니다. 또한 `messages` 테이블에는 `user_id` 컬럼이 없는데(세션을 통해 소유권을 확인함) journey 페이지는 `.eq("user_id", ...)`로 직접 필터링하고 있어, 테이블 이름을 고쳐도 이 부분(약 122번째 줄)까지 함께 수정해야 정상 동작합니다. 개발팀이 실제 배포 DB에서 두 페이지가 같은 테이블을 바라보도록 통일해 주세요.

### 자동 점검 스크립트에 존재하지 않는 AI 모델 이름 하드코딩
- **파일 위치**: `scripts/weekly-review.mjs` (약 108번째 줄), `src/lib/anthropic.ts` (약 20번째 줄)
- **무슨 문제인가**: 주간 리포트를 만드는 스크립트는 `claude-opus-4-8`이라는 모델(AI 엔진 버전)을, 채팅 기본값은 `claude-sonnet-4-6`을 사용하도록 되어 있습니다. 이 이름들은 실존하지 않는 미래형/가상의 이름일 가능성이 매우 높습니다(현재 Anthropic이 제공하는 실제 모델명과 다름).
- **어떤 피해가 생기나**: 존재하지 않는 모델을 요청하면 AI 서버가 오류(모델 없음)를 돌려주어, 주간 점검 리포트 생성이 완전히 실패하거나 채팅 자체가 응답하지 못할 수 있습니다. 채팅 쪽은 환경변수 `ANTHROPIC_MODEL`로 덮어쓸 수 있어 운영 중 실제 모델명이 설정돼 있다면 괜찮지만, 설정이 누락되면 즉시 장애입니다.
- **권장 조치**: 개발팀에 현재 Anthropic이 실제로 제공하는 모델명을 확인받아 스크립트와 기본값을 실존 모델로 교체하세요. 특히 배포 환경변수에 `ANTHROPIC_MODEL`이 유효한 값으로 설정돼 있는지 반드시 확인해야 합니다.

### 중복된 메모리 파일이 서로 다른 앱 이름을 참조
- **파일 위치**: `src/lib/selah-memory.ts` (전체), `src/lib/manna-memory.ts` (전체)
- **무슨 문제인가**: 사용자와의 대화를 장기 기억하는 기능이 거의 똑같은 두 개의 파일(`selah-memory.ts`, `manna-memory.ts`)로 중복 존재합니다. 실제로 채팅 API가 사용하는 건 `manna-memory.ts` 하나뿐이고, `selah-memory.ts`는 아무 데서도 쓰이지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 당장 장애를 일으키지는 않지만, 두 파일이 다른 앱(SELAH/MANNA) 이름을 언급하며 혼란을 줍니다. 나중에 한쪽만 수정하고 다른 쪽을 놓치면 버그의 원인이 됩니다. "즉시" 항목에 둔 이유는 위 두 문제를 고칠 때 함께 정리하는 것이 안전하기 때문입니다.
- **권장 조치**: 사용하지 않는 `selah-memory.ts`를 삭제하세요. (삭제 전 어디에서도 import되지 않는지 개발팀이 한 번 더 확인)

## 🟡 가까운 시일 내에 개선이 필요한 부분

### 사용량 제한(rate limit)이 서버 재시작 시 초기화됨
- **파일 위치**: `src/lib/rate-limit.ts` (전체), `src/app/api/chat/route.ts` (약 68번째 줄)
- **무슨 문제인가**: 한 사용자가 1분에 20번까지만 AI에 요청하도록 제한하는 기능은 서버 메모리에만 저장됩니다. Netlify 같은 서버리스 환경(요청마다 서버가 새로 뜨는 구조)에서는 이 카운트가 자주 초기화되고, 여러 서버 인스턴스 간에 공유되지 않습니다. 코드 주석도 이를 "기본적인 방어책일 뿐"이라고 명시하고 있습니다.
- **어떤 피해가 생기나**: 악의적 사용자가 요청을 분산시키면 제한을 우회해 AI 사용 비용(후원금으로 운영되는 예산)을 과도하게 소모시킬 수 있습니다. 정상 사용자에게는 문제없지만 비용 폭탄 위험이 있습니다.
- **권장 조치**: 사용자 규모가 커지기 전에 Upstash Redis나 Postgres 카운터 같은 공유 저장소 기반의 제한으로 교체하는 것을 검토하세요. 당장은 규모가 작다면 우선순위를 낮춰도 됩니다.

### 크론(정기 작업) 알림 발송 시 데이터베이스 부하 가능성
- **파일 위치**: `src/app/api/cron/send-reminders/route.ts` (약 100~180번째 줄)
- **무슨 문제인가**: 매분 실행되는 알림 발송 작업이 "활성화된 모든 리마인더"를 한 번에 다 불러온 뒤 서버에서 일일이 시간을 비교합니다. 또한 알림을 하나씩 순차적으로(한 번에 하나씩) 보냅니다.
- **어떤 피해가 생기나**: 사용자가 수천 명 이상으로 늘어나면 매분 전체 데이터를 읽는 것이 느려지고, 순차 발송으로 인해 알림이 제때 도착하지 않을 수 있습니다. 지금 규모에서는 문제없습니다.
- **권장 조치**: 사용자 증가 시 데이터베이스 쿼리에서 시간 필터링을 먼저 하도록 최적화하고, 알림 발송을 병렬 처리(여러 개 동시 발송)로 바꾸는 것을 고려하세요.

### 이미지가 포함된 요청의 대화 기록 손상 가능성
- **파일 위치**: `src/components/chat/chat-app.tsx` (약 200~210번째 줄)
- **무슨 문제인가**: 사용자가 사진과 함께 메시지를 보낼 때, 화면에 보이는 내용(`displayContent`, 예: "[사진을 보냈어요]")과 AI에게 실제로 전달되는 텍스트(`text`, 빈 값일 수 있음)가 다릅니다. 이 둘이 어긋나면 다음 대화 요청 시 히스토리에 저장된 텍스트와 화면 표시가 미묘하게 달라질 수 있습니다.
- **어떤 피해가 생기나**: 대화가 이어질 때 AI가 이전 맥락을 조금 다르게 받아들이거나, 저장된 기록과 화면이 불일치할 수 있습니다. 심각한 오류는 아니지만 사용자 경험을 흐릴 수 있습니다.
- **권장 조치**: 사진 전송 시 저장/표시/전송 텍스트의 일관성을 개발팀이 한 번 점검하도록 권장합니다.

### `AddToHomePrompt` 컴포넌트가 사용되지 않음(설치 안내 중복)
- **파일 위치**: `src/components/AddToHomePrompt.tsx` (전체), `src/components/install-prompt.tsx` (전체)
- **무슨 문제인가**: 홈 화면 추가를 안내하는 컴포넌트가 두 개(`AddToHomePrompt`, `InstallPrompt`) 있는데, 레이아웃에서 실제 사용되는 것은 `InstallPrompt` 하나입니다. `AddToHomePrompt`는 어디서도 불러지지 않는 죽은 코드입니다.
- **어떤 피해가 생기나**: 기능상 문제는 없지만, 유지보수 시 혼란과 불필요한 코드 부피가 늘어납니다.
- **권장 조치**: `AddToHomePrompt.tsx`가 정말 안 쓰인다면 삭제를 검토하세요.

## 🟢 장기적으로 개선하면 좋은 점

### AI 응답 스트림 저장(persist)이 두 번 호출될 수 있음
- **파일 위치**: `src/app/api/chat/route.ts` (약 245~310번째 줄, `persist` 함수)
- **무슨 문제인가**: AI 응답이 끝날 때 장기 기억을 저장하는 `persist()` 함수가 `message_stop` 이벤트에서 한 번, 그리고 스트림 종료 처리(`finally` 블록)에서 또 한 번 호출될 수 있는 구조입니다. `message_stop`에서 이미 `return`으로 빠져나가면 중복은 없지만, 예외 상황에서는 두 번 실행될 여지가 있습니다.
- **어떤 피해가 생기나**: 최악의 경우 AI 서버에 메모리 갱신 요청이 두 번 가서 약간의 추가 비용이 발생합니다. 기능 오류는 아닙니다.
- **권장 조치**: 이미 저장했는지 표시하는 플래그(한 번만 실행되도록)를 추가하면 더 안전합니다.

### 개인정보처리방침의 "비밀번호 미저장" 문구와 실제 기능 불일치
- **파일 위치**: `src/app/privacy/page.tsx` (제8조, "비밀번호 미저장 (소셜 로그인만 사용)")
- **무슨 문제인가**: 개인정보처리방침에는 "소셜 로그인만 사용"한다고 적혀 있지만, 실제 로그인 화면(`src/app/login/page.tsx`)에는 이메일+비밀번호 회원가입 기능이 활성화되어 있습니다.
- **어떤 피해가 생기나**: 법적 고지 문서와 실제 서비스 동작이 다르면 신뢰 문제나 법적 분쟁 소지가 있습니다.
- **권장 조치**: 이메일 로그인을 유지한다면 개인정보처리방침 제8조 문구를 실제에 맞게 수정하세요(비밀번호는 Supabase가 암호화 저장). 개발팀 및 법무 검토 권장.

### 로그인 후 세션 확인 대기 로직의 타임아웃
- **파일 위치**: `src/app/login/page.tsx` (약 30~45번째 줄, `waitForSession`)
- **무슨 문제인가**: 로그인 후 세션 쿠키가 준비될 때까지 최대 1.5초간 기다립니다. 네트워크가 느린 환경에서는 이 시간 안에 준비되지 않아 로그인 화면으로 되돌아갈 수 있습니다. (다행히 서버 측 `chat/page.tsx`에 이중 방어 로직이 있어 대부분 완화됩니다.)
- **어떤 피해가 생기나**: 아주 드물게 "로그인이 두 번 필요한" 현상이 재발할 수 있습니다.
- **권장 조치**: 현재 이중 방어가 있어 급하지 않지만, 사용자 신고가 들어오면 타임아웃을 늘리거나 재시도 로직을 강화하세요.

## 🔒 보안 점검 결과

- **인증(로그인 검증)**: ✅ 양호 — 채팅 API가 로그인하지 않은 사용자를 차단(`route.ts`)하고, 미들웨어가 `/chat` 경로를 보호합니다.
- **API 키 관리**: ✅ 양호 — Anthropic API 키는 서버 환경변수로만 접근하며 클라이언트에 노출되지 않습니다. VAPID 개인키도 서버에만 둡니다.
- **입력값 검증**: ✅ 양호 — 이미지 크기 상한(약 5MB), 리마인더 시간/시간대 형식 검증, 메시지 길이 제한 등이 적용돼 있습니다.
- **데이터베이스 접근 제어(RLS)**: ✅ 양호 — 모든 테이블에 Row Level Security가 설정되어 각 사용자가 자기 데이터만 읽고 쓸 수 있습니다.
- **SQL 인젝션**: ✅ 양호 — Supabase 클라이언트의 파라미터화된 쿼리만 사용하며 직접 SQL 문자열 조립이 없습니다.
- **보안 헤더**: ✅ 양호 — 클릭재킹 방지, HTTPS 강제, MIME 스니핑 차단 등 기본 헤더가 잘 설정돼 있습니다.
- **크론 엔드포인트 보호**: ✅ 양호 — 알림 발송 API는 비밀키(`CRON_SECRET`)를 헤더로만 요구하며, 쿼리스트링 방식을 의도적으로 제거했습니다.
- **위기(자살/자해) 감지**: ✅ 양호 — 서버·클라이언트 양쪽에서 감지하고, 전문 기관 안내를 우선 노출하는 신중한 설계입니다.
- **사용량 제한**: ⚠️ 주의 — 서버 메모리 기반이라 서버리스 환경에서 우회 가능(위 🟡 항목 참조). 비용 보호 측면에서 개선 여지 있음.
